# BUG-023: pumice reset-parity manifest was re-based at BUG-020 but the test floor was not — the gate has been red for every pumice RDL/manifest/regmap commit since

**Priority:** P2 — a gate that has been red for days stops gating: every
commit touching pumice `.rdl` / manifest / regmap walks past (or `--no-verify`
around) a failing pre-commit check, so the tripwire TASK-015 installed is
currently decorative.
**Status:** open 2026-10-04 — found while running the bin test suite during
site-audit TASK-002 work; no pumice lane item mentioned it.
**Owner:** TBD (pumice / mem-ctrl lane).

**Reproduction:**

    source venv/bin/activate
    python3 -m pytest bin/tests/test_check_csr_reset_parity.py -q

    FAILED test_the_pumice_manifest_covers_every_writable_field
    AssertionError: only 65 sw=rw fields -- did the regmap shrink?

**What is actually wrong — measured, in the history:**

The manifest and the regmap AGREE with each other; the floor is the liar.

- TASK-015 (14b6c932d, 2026-09-27) created
  `dv/csr_reset_parity.py` with **73** FIELDS and pinned the tripwire just
  under it: `assert len(fields) >= 70` in
  `bin/tests/test_check_csr_reset_parity.py`.
- BUG-020 (16d47cc28, 2026-09-28) retired 27 undriven `OBS_*` registers and
  re-generated the map. The manifest was correctly re-based in the SAME commit
  — FIELDS 73 -> 65, and the set-equality assertion still passes at HEAD —
  but the `>= 70` floor was never touched. Verified by exec'ing the manifest
  at each commit: 14b6c932d -> 73, 16d47cc28 -> 65, HEAD -> 65.

So the retirement was deliberate, complete, and correctly reflected in the
manifest; only the hard-coded count in the test still describes the
pre-retirement world.

**Fix (one of, owner's call):**

1. Re-base the floor to the post-BUG-020 reality (65) with a comment naming
   BUG-020 as the reason, e.g.
   `assert len(fields) >= 65  # post-BUG-020: 27 OBS_* registers retired`.
2. If the floor is meant to stay generic, derive it from the manifest's own
   documented population (the docstring still says "It is 73 decisions") and
   update that docstring line too — it went stale in the same commit.

Also sweep for the same pattern while there: any other count-assert pinned to
a pre-rework population (the `>= 70` form is exactly the "checker verdict
needs a count" failure mode the handbook warns about — the count must move
with the design, and nothing makes it).

**Done when:** the pytest file passes at HEAD, the pre-commit gate is green
again on a touched pumice RDL file, and the manifest docstring's field count
matches reality.
