# BUG-003: an arbiter pick rejected by its own final safety gate was pushed to the DRAM anyway

**Status:** CLOSED 2026-09-27 -- root-caused and FIXED in
`rtl/fub/pumice_cmd_arbiter.sv` (one line: `cmd_valid_o` is now gated by
`w_out_safe`). **Priority:** was P1 --
this is a real pumice RTL defect that lets the controller's model of the DRAM
and the DRAM itself diverge silently.

**Two earlier classifications were wrong and are kept below for the record:** it
was first written up as an RDS-DV `DFISlavePHY` modelling defect, then as "a
missing guard on the background precharge". Neither was the mechanism. Two
fixes written against those theories were a no-op and a revert.

## IT IS AN RTL BUG, IN THE SCHEDULER LAYER (2026-09-27, proven from the pins)

Two self-contained measurements, neither relying on the DRAM model or on
arbiter-internal sampling:

**1. The DFI PINS carry an illegal command.** Replayed the DUT's own output pins
(`phy_dfi_cs_n/ras_n/cas_n/we_n/bank/address`, sampled on dfi_clk, PREA via A10
and auto-precharge handled):

    commands on the pins        : 1046
    COLUMN OPS TO A CLOSED BANK :    1     RD bank=2 addr=0x70 @ t=30152696

Every `cs_n` assertion is exactly ONE dfi_clk edge long (1046 of them, phase 1
never selected), so there is no double-counting. pumice drives a READ to a bank
with no open row. **The DV model is exonerated** -- it reported the wires
faithfully; its 1046 decodes match the pins exactly.

**2. The SCHEDULER emits it; the DFI layer is exonerated.** The scheduler's own
output handshake (`cmd_valid_o && cmd_ready_i`) already contains it:

    scheduler output : 1047 cmds, 1 column op to a closed bank (RD bank=2)
    DFI pins         : 1046 cmds, 1 column op to a closed bank (RD bank=2)

Sequence at the scheduler output, bank 2:

    30032672  v/r=11  RD  bank2   legal, row open
    30046008  v/r=01  PRE bank2   presented, ready=0
    30086016  v/r=11  PRE bank2   PRE FIRES -> bank 2 CLOSED
    30099352  v/r=01  RD  bank2   presented
    30112688  v/r=11  RD  bank2   FIRES  <-- ILLEGAL
    30126024  v/r=01  ACT bank2   row re-activated

Note `tmoreq=0` throughout: the PRE in the failing window is a CONFLICT PRE, not
the timeout PRE -- even though the defect only appears with the timeout enabled
(both baselines, open-page-no-timeout and close-page, are clean).

### Why my earlier "the arbiter is legal" reading was wrong

It sampled the arbiter-internal `w_fire_out` / `r_op`, which UNDERCOUNTS: that
path reported 776 RDs where the scheduler output and the pins both show 777.
Any conclusion drawn from arbiter-internal sampling in this file is suspect.
Measure at `cmd_valid_o && cmd_ready_i`, or at the pins.

**The arbiter is legal. One extra READ appears on the DFI pins.**

    ARBITER fired stream, all banks   : 1026 commands, 776 RD fires
    column ops to a CLOSED bank       :    0
    MODEL decoded                     :  777 RDs   <- one more than was fired

The extra READ is properly ENCODED on the wires -- the decode log shows

One phantom explains BOTH symptoms:

* it lands between a real PRE and a real ACT, so the DRAM state model reports

* it queues a burst, producing extra serve cycles and one spurious
  `rddata_valid` with the ring empty -- `pumice_rd_return_ring.sv:273`.

Handshake FIRES remain exactly 1552 = 776 x 2, so no data is lost or duplicated,
which is why the board returns correct data across ~60 MB.

## Superseded: "pumice issues a READ to a CLOSED bank"

**It IS an RTL defect.** The decoded command stream at board parity, bank 2:

    cyc=4481  RD   addr=0x6c
    cyc=4489  PRE              <- background timeout precharge closes the row
    cyc=4493  RD   addr=0x70   <- READ TO A CLOSED BANK  (the JEDEC violation)
    cyc=4501  ACT  addr=0x3    <- row re-activated
    cyc=4511  RD   addr=0x70   <- the SAME read, re-issued

The controller issues a column op against a bank it has just precharged, then
re-activates and re-issues the same read. **That recovery is why the board's data
is correct** -- the erroneous read is followed by a correct one -- and the DRAM's
response to the bogus read is the unrequested return beat the ring reports.

Cycles are DFI cycles (2 per aclk), so PRE -> bad RD is 4 DFI = 2 aclk cycles.

### This REVERSES the "arbiter is exonerated" entry below

That replay found 0 illegal commands in 404 -- but it ran on the **100 MHz**
waveform, before the component TB was brought to board parity. It never applied
to the board configuration. At parity the arbiter demonstrably issues the illegal
read. **Do not trust that section.**

### Where the guard gap appears to be (NEEDS ONE MORE MEASUREMENT)

Columns check `!w_pre_col_guard[rb] && !w_preact_bank_guard[rb]`, and:

    r_preguard0 <= (w_fire_out && r_do_pre) ? (1 << r_bank) : 0   // 3-cycle, post-FIRE
    w_preact_bank_guard = w_prepick_guard | w_if_preact_out
    w_prepick_guard     = w_if_preact_sel | w_if_preact_pre

`r_preguard0/1/2` arms only when a PRE **fires**, and the `_sel`/`_pre` shadow
terms are built from the CONFLICT-PRE selection signals only (`rd_act`, `wr_act`,
`rd_pre`, `wr_pre`) -- **the timeout PRE contributes to `w_if_preact_out` alone.**
So the timeout PRE's coverage is output-stage plus post-fire, and whether those
two are continuous for a column selected in the cycle the timeout PRE is picked is
exactly what the bad read suggests they are not.

**The measurement that settles it**, and the next thing to do: capture
`w_if_preact_out`, `w_prepick_guard`, `w_pre_col_guard`, `r_do_pre`, `w_fire_out`,
`r_bank` and the read column's select/pick signals across the ~6 aclk cycles
around the bad RD (model cyc 4489-4493, bank 2) and identify which guard was low
when that column was selected. Do NOT patch a guard before that -- one guard I
proposed already existed (PUMICE-018) and a second fix I wrote was a no-op.

### Fix shape, once the gap is confirmed

Add the timeout PRE to the pre-fire shadow so it guards columns from the cycle it
is PICKED, not only from the cycle it fires -- i.e. include the timeout-PRE
selection in `w_if_preact_sel` / `w_if_preact_pre` the way the conflict-PRE paths
already are. Clamping `tr_init` is NOT an option: at board parity the defect
appears at TR=4 as well, so there is no safe TR.

## Superseded: "the DFI slave model double-decodes one READ"

Wrong. The model decoded 777 READs because the CONTROLLER issued 777 -- 776 good
plus the one to a closed bank. The single duplicated (bank, addr) pair,
bank=2/0x70, is the bad read and its retry, not a model artefact. RDS-DV needs no
change and was left clean.

Instrumented `DFISlavePHY._serve_reads` (the active server -- note
`_serve_reads_bl_anchored` is NOT used by this TB, which cost two wrong fixes
before I checked the dispatch) and counted per-burst serves:

    READ commands FIRED by the arbiter : 776
    ring notifies (rd_issue_valid_o)   : 776
    bursts the MODEL decoded           : 777     <- one too many
    serve events (777 x 2)             : 1554

`_rd_burst_seq` increments once per decoded READ command, and 777 distinct
`burst_id`s were served, each exactly twice. **The model decoded one READ command
twice.** The duplicate produces two extra serve cycles: one lands while the ring
still holds that burst's ticket and is absorbed, the other arrives with the ring
empty -> the single spurious `rddata_valid`, which is what
`pumice_rd_return_ring.sv:273` reports.

This accounts for every observation:

* **No data is lost or duplicated.** Handshake FIRES are exactly 1552 = 776 x 2;
  the ring accepts only what it expects and declines the extra (ready low).
* **Hardware is clean** -- a real PHY does not double-decode a command. The board
  ran the trigger config over ~60 MB with 0 mismatched beats.
* **Rare and PRE-correlated** -- the duplicate needs a particular phase alignment,
  and the background timeout PRE perturbs command placement enough to produce it.

The suspect area is flagged in the model's own comment: *"A command is present if
the chip is selected on ANY DFI sub-phase (cs_n active-low). The legacy gate only
tested phase 0 (& 1)"* -- scanning every sub-phase can decode one command twice
when its `cs_n` is visible on two samples.

**Where the fix belongs: RDS-DV, `DFISlavePHY` command decode** (de-duplicate a
command seen on more than one sub-phase / sampling edge). NOT pumice RTL: the
controller issues 776 reads, notifies 776, and every JEDEC check on the coherent
board config passes on open page.

### Two fixes I attempted and reverted -- do not re-try

1. **`packed_valid` only for written slots** in `deinterleave_read_window`. Wrong
   target (that server is unused here) AND actively harmful: partial windows with

2. **One burst per DFI cycle** in `_serve_reads`. Correct-sounding but not the

Reproduced under `WAVES=1` at rd_gap=8 (`shared_nr1_r2_b32_bl4/dump.fst`,
assertion at t=3420000; the repro script restores the RDL unconditionally).
These facts are read directly off single-signal transition lists and do not

| t (ns) | signal | event |
|---|---|---|
| 3190000 | `rd_issue_valid_o` | LAST read-issue notify to the ring ends. 60 notifies in the run |
| 3210000 | `timeout_pre_req` | background precharge requests (3rd and last of the run) |
| **3250000** | `r_do_rd` | goes 0 and NEVER RETURNS -- the arbiter issues no further read picks |
| 3370000 | `iq_rd_valid` | issue_q drains: no ticket at the head |
| **3410000** | `dfi_ret_valid` | a DFI read return beat arrives -> ASSERTION |

**The anomaly stated precisely: a DFI read return beat arrives 160 us after the

## Mechanism — hypothesis, NOT confirmed

**Revised, and NARROWER than the first guess.** The original hypothesis in this
report was "the PRE lands while a read is in flight and the ring loses its
ticket". The waveform does not support that as written: the ring's per-burst
accounting is correct and allocation never faults. What the waveform shows is a
return beat with no read pick behind it within any plausible latency.

Leading hypothesis now: **the background precharge perturbs the DFI read
pipeline's `rddata_en` timing, producing a late or extra return beat.** The DFI
read return is self-timed off a counter armed by a read command; a precharge
interleaved into that window is the kind of event that can shift or double it.
That places the fault in `pumice_dfi_rd_aligner` / the read-enable generation
rather than in `pumice_rd_return_ring`, which is merely the detector.

**This is NOT a comparator-sized fix.** The first estimate in this report
("gate `timeout_pre_req_o` on no outstanding ticket for this bank -- costs a
comparator") was based on the unconfirmed mechanism and should not be relied on.
If the fault is read-enable timing, the fix is in the DFI read path and needs its
own timing analysis.

## Superseded: root cause on the coherent bench at 100 MHz

**The controller issues a READ to a bank with no open row.**

    violation [no_act_before_rd]: RD bank=1 but state=idle @ cycle 3049

Measured on the `board_ddr2_300` operating point -- every timing derived from the
part's ns specs at the board's tCK, model and controller from the same source --
with the DRAM state model's HARD JEDEC checks armed. Only TR varies:

| tr_init | result | JEDEC violations |
|---|---|---|
| **2** | **FAIL** | `no_act_before_rd: RD bank=1 but state=idle` |
| 4 | PASS | **zero** |

Open page with the timeout OFF is JEDEC-clean on this bench (0 violations), so
this is not a bench artefact: it is the timeout path alone.

### Mechanism: a stale bank image, the known hazard family

The background timeout precharge closes the row, but the arbiter's REGISTERED
bank image still reports it open, so a read already classified as a row-hit is
issued against a row that has just been closed. The DRAM has no open row, hence
`no_act_before_rd`.

**The orphan return beat that this bug was filed for is the DOWNSTREAM SYMPTOM.**
The read went to a closed bank, so the data that came back corresponded to no
tracked burst -- which is why the ring saw a beat with no ticket (121 beats
against 120 issued). The ring was the detector twice over, and the earlier
"the background PRE injects an extra beat" framing had the causality backwards.

This is the same class as the in-flight shadow / AP stale-image work already done
in this controller -- the occupancy mask was re-diagnosed as an AP stale-image
guard, and the scheduler ceiling and a deadlock shared one root cause, "a stale
registered bank image". The AP close path was given a guard; **the background
timeout close path was not.**

Why TR<=2 and not TR>=3: at TR=2 the precharge fires early enough to land inside
the window where a read has already been classified or picked against the open
row. At TR>=3 it lands after that window.

### THE ARBITER IS EXONERATED -- do NOT add a guard there

Replayed all 404 commands the arbiter FIRED (`w_fire_out`, with op and bank) on
the coherent bench through a per-bank open/closed model:

    commands replayed            : 404
    column ops to a CLOSED bank  : 0

**The arbiter's command stream is legal.** Every RD/WR follows an ACT to that
bank; the failing bank-1 tail is PRE @12210000 -> ACT @12270000 (6 cycles, tRP=2
satisfied) -> RD @12320000 (5 cycles, tRCD=2 satisfied). Yet the model reports
`RD bank=1 but state=idle`.

So the divergence is BETWEEN the arbiter's output and the model's view of it. Two
candidates, and this is where the next session should start:

1. **DFI command path / phase placement.** At DFI_RATE=2 two commands share an MC
   cycle on different phases. If the formatter places an ACT and a following
   column such that the model decodes them in the wrong phase order, the model
   sees the column first. This is RTL, in `dfi_cmd_formatter` / the DFI cmd path.
2. **The model's bank/command decode** for this geometry (32b beat over x16). If
   its address decode differs from `ADDR_MAP.bank_lsb`, it attributes commands to
   the wrong bank and its state tracking diverges without the controller being
   wrong.

Distinguish them by dumping the DFI-side command stream (phase, op, bank) from
`DFIMonitor` and replaying THAT through the same per-bank model. If the DFI-side
replay is also clean, the fault is the model's decode; if it shows the inversion,
it is the RTL.

### WHAT NOT TO DO (both were my own earlier conclusions, both wrong)

* **Do not guard the timeout PRE against in-flight columns.** That guard ALREADY
  EXISTS and covers all three pipeline stages:
  `w_guarded` includes `w_prepick_guard = w_if_preact_sel | w_if_preact_pre` and
  `w_col_inflight_guard = w_if_col_sel | w_if_col_pre`, plus the `_out` terms.
  PUMICE-018 added it for exactly the scenario I re-hypothesised. Adding it again
  is a no-op.
* **Do not treat the orphan return beat as the defect.** It is a downstream
  symptom, and the bench it was measured on was incoherent.

### Superseded fix direction (kept so it is not re-tried)

Give the background timeout close the same stale-image protection the
auto-precharge close already has. Either:

* suppress `timeout_pre_req_o` for a bank while any column op for that bank is
  classified, picked, or in flight in the arbiter pipeline -- the in-flight
  shadow (`w_if_preact` / `w_if_col`) already tracks exactly this and is the
  natural place; or
* make the close invalidate the arbiter's bank image in the same cycle it is
  picked, so a pending read reclassifies as a miss and re-ACTs instead of
  issuing against a closed row.

The second is more robust (it fixes the class rather than one producer) and
matches how the explicit-PRE path already behaves. Rejected: clamping
`tr_init >= 3`, which costs 18 percentage points of the win (see the TR ladder
above) and leaves the hazard reachable from any other early close.

### Superseded framing (kept so it is not re-derived)

The analysis below was taken on the INCOHERENT bench -- timings 1.5x-3.8x below
the modelled part, JEDEC checks disabled -- and its conclusion that the defect
lay in the DFI read-return path does NOT hold. The beat-count arithmetic
(121 vs 120) is still correct as an observation; only the attribution was wrong.

## Superseded: the background PRE injects ONE extra return beat

Isolated with single-test runs at rd_gap=8, using new TEST_PAGE_POLICY /
TEST_POLICY_MODE / TEST_TR_INIT env overrides:

| page policy | policy_mode | tr_init | result |
|---|---|---|---|
| CLOSE (the suite default) | 0 | - | PASS |
| **OPEN** | 0 | - | **PASS** |
| OPEN | 3 `fixed_open` | 2 | **FAIL** |

**Open page is innocent.** The trigger is specifically the background timeout
precharge. Bounded by a TR sweep, same stimulus:

| tr_init | 1 | 2 | 3 | 4 | 6 | 8 | 16 |
|---|---|---|---|---|---|---|---|
| | FAIL | FAIL | PASS | PASS | PASS | PASS | PASS |

TR <= 2 fails, TR >= 3 passes -- ONE CYCLE separates them. gap=0 passes at every
TR.

**The accounting, clock-sampled over the whole run** (every signal read at the
rising aclk edge, which is what the two retracted passes got wrong):

    read bursts notified (rd_issue_valid_o) :  60
    DFI return beats delivered              : 121
    expected, 60 bursts x 2 beats (BL4 x16) : 120
    ORPHAN beats (ret_v & !iq_v)            :   1  @ 3450000
    background PREs fired                   :   3

**121 = 120 + 1. The background precharge injects exactly ONE spurious DFI read
return beat.** The ring's bookkeeping was correct the entire time -- it is the
DETECTOR, not the culprit. Cycle detail at the violation:

    time      ret_v iq_v do_rd op
    3390000     1     1    0   ACT
    3400000     1     1    0   ACT     <- last beat, ticket pops
    3410000     0     0    0   ACT     <- queue drained, correctly
    3420000     0     0    0   WR
    3450000     1     0    0   WR      <- EXTRA beat, 40 ns late, no read outstanding

`do_rd` and `rd_issue_valid_o` are 0 across the whole window: no read was issued
here, so this beat belongs to a burst that had already completed.

### Why TR <= 2 and not TR >= 3

`tRTP` is 4 and the PRE is gated on `r_preblk == 0`, so the precharge is
**JEDEC-legal** when it issues -- that gate is doing its job. But the
CONTROLLER's read-return pipeline is longer than tRTP (`rddata_delay` is 7 on
the board, and the DFI read path adds its own latency), and **nothing gates the
background PRE against that pipeline still draining.** At TR <= 2 the PRE lands
inside the return window; at TR >= 3 it lands after it.

So the defect is not a missing JEDEC timing. It is a missing gate between the
background precharge and the controller's own in-flight read RETURN -- a
controller-internal hazard that no DRAM timing parameter covers.

### Is it just a bad config? NO -- measured 2026-09-27

Asked directly (Sean): *"What is the fix for 003? Or does it fail due to bad cfg
settings?"* The honest answer is that the failing config is ALSO the optimal one,
so "avoid that setting" is not available.

Board, txn_scale=1000, hot/cold 2-bank stimulus:

| config | rd MB/s | vs open page | integrity | sim |
|---|---|---|---|---|
| open_page | 327.6 | - | ok | pass |
| **fixed_open_tr1** | **436.8** | **+33.3%** | ok | **FAIL** |
| **fixed_open_tr2** | **436.8** | **+33.3%** | ok | **FAIL** |
| fixed_open_tr3 | 376.7 | +15.0% | ok | pass |
| fixed_open_tr4 | 368.6 | +12.5% | ok | pass |

**TR=3, the smallest SAFE value, loses more than half the win** -- +15.0% against
+33.3%, i.e. 60 MB/s left on the table. The only two values that deliver the full
+33.3% are TR=1 and TR=2, and those are exactly the two that break.

**So clamping tr_init to a floor is NOT an acceptable fix.** It would cost 18
percentage points of the largest runtime win on the controller. This is a defect
to fix in RTL, not a setting to document away.

Three further reasons it is a bug and not misconfiguration:

1. Nothing in the RTL, the RDL, or the docs states a minimum TR. The field is
   8-bit `rw` with reset 0 and no documented constraint.
2. The failure mode is SILENT CORRUPTION, not a refusal. The assertion's own
   comment: a lost ticket means "every later read would fill the wrong slot". An
   out-of-range configuration should error, never corrupt.
3. **On the board the broken config looks PERFECT** -- fastest AND `ok=1`, zero
   mismatched beats, because hardware carries no `ifndef SYNTHESIS` check. Without
   the sim assertion this ships looking like a free 33%. That is the whole
   argument for keeping accounting assertions in the RTL ([[TASK-015]] layer 2a).

### THE FIX

Gate the background timeout precharge on **outstanding read RETURN beats for
that bank**, and nothing weaker:

* `timeout_pre_req_o` (or the arbiter's PRE pick on the timeout path) must be
  suppressed while any read beat for that bank is still in the return pipeline.
* Per-bank is required, not a global "any read outstanding": the win comes from
  page-hostile traffic where reads are in flight continuously, so a global gate
  would suppress the background PRE exactly when it pays and give back the 33%.
* The ring already has most of what is needed -- `occ_o` is exported and the
  issue_q head carries the ticket -- but per-BANK outstanding-read tracking has to
  be added or derived. That is the actual work in this fix.
* Rejected: clamping `tr_init >= 3` (costs 18 points, see above) and gating on
  tRTP alone (already satisfied -- the PRE is JEDEC-legal when it issues; the
  hazard is the controller's own pipeline, which no DRAM parameter covers).
* Still to check: whether the perturbation requires the PRE to be to the SAME
  bank as the returning read. The measurement does not distinguish, and it decides
  whether per-bank gating is sufficient or the read-enable generation itself needs
  the guard. Determine this BEFORE implementing.

### Superseded fix direction (kept so it is not re-tried)

* **Preferred:** gate `timeout_pre_req_o` (or the arbiter's PRE pick for the
  timeout path) on "no read beats still outstanding for this bank". The ring
  already knows -- `occ_o` is exported for observability and the issue_q head
  carries the bank. This is the guard the first version of this report guessed
  at, and the guess was right for the wrong reason: the hazard is the RETURN
  pipeline, not the DRAM-side read.
* **Not sufficient:** clamping `tr_init >= 3`. It hides the hazard at the
  measured latency and breaks silently the moment `rddata_delay` changes, which
  is a board bring-up knob (see the bring-up tuple: rddata_delay 7).
* **Check the same exposure** on `bank_timer`'s `r_ap_pending` auto-precharge
  path, which can also close a row without consulting the read ring.

### Why it stayed latent

The component suite brings up `page_policy=2` (CLOSE) for every test except
three named ones, so **`gen_replica` had never run open page at all**, and the
whole mode-3/4/5 engine was reachable from a single test. Exactly the
config-coverage hole [[TASK-015]] is about.

## Superseded diagnostic step (kept so it is not re-tried)

Do NOT continue by inference from the existing dump -- two cross-signal replay

`w_fire_out && r_rd_issue`). Instead instrument directly:

2. Diff the two lists. That names the orphan beat's origin in ONE run, with no

## Superseded hypotheses (kept so they are not re-tried)

`gen_replica`'s docstring explains what a non-zero gap does, and it is the key:
`cfg_rd_gap > 0` pauses AR **and deasserts RREADY** on every RLAST, so read data
already in flight is backpressured while a concurrent writer keeps running.

Original proposed chain (NOT supported by the waveform as written -- the ring's
accounting is correct and allocation never faults):

1. At gap >= 8 the reader stalls mid-return and the bank stops receiving commands.
2. The bank therefore goes IDLE with a read still in flight in the DFI pipeline.
3. `fixed_open` with TR=2 expires almost immediately in that window and raises
   `timeout_pre_req_o`; the arbiter issues the background PRE.
4. The precharge lands while the read is still in flight, and the ring sees a
   return beat for a ticket it no longer has.

**Supporting evidence for the TR-magnitude part:** a test that explicitly
programs a timeout policy with a LONG TR passes today --
`test_pumice_top.py:460` sets `policy_mode=4` with `tr_init=24 / tr_min=8 /
tr_max=96` and is green. So a timeout policy per se is NOT the trigger; a
timeout short enough to fire inside a read's DFI return latency appears to be.
TR=2 against a `rddata_delay` of 2 in sim (7 on the board) is exactly that
regime.

**Not yet tested, and it is the first thing to do:** sweep the reset `tr_init`
(2, 4, 8, 16, 24) against rd_gap 8 and 15 and find where it goes green. If the
boundary tracks read latency, the fix is a guard; if it fails at every TR, the
background-precharge path ignores in-flight reads entirely and the guard has to
be unconditional.

## Why it was never seen before

`fixed_open` has ALWAYS been selectable, so this exposure is not new -- but
nothing ever ran mode 3 out of RESET. Every prior campaign either left the reset
at 0 (legacy) or programmed a long TR. The bug is latent today for any
integrator who sets `policy_mode=3` with a short TR, and it only became blocking
when [[TASK-013]] proposed mode 3 as the default.

## Interaction with the board evidence — read this before trusting either

The board measurements in [[TASK-013]] that recommend `fixed_open` TR=2 INCLUDE
a gap=8 scenario: `col_major_bl8_gap` at MEDIUM level returned `ok=1`, no
mismatched beats, 213.0 MB/s (+9.1%) under `fixed_open_tr2`. So on real silicon,
at the same nominal stimulus shape, the data came back correct.

That does **not** clear the hardware. The assertion is `ifndef SYNTHESIS`, so the
board has no equivalent check -- a lost ticket that happens to refill in the
right order, or a run that never hits the window, produces a clean integrity
result either way. Treat the board's pass as "did not corrupt in that run", not
as "cannot corrupt". Until this is understood, the +9.1% / +41.2% numbers should
be quoted as measured-but-unqualified, not as shippable.

## ROOT CAUSE (2026-09-27, measured at the macro level, board config)

`pumice_cmd_arbiter.sv` has a final safety gate on the output register that
re-checks the freshest bank-timer state before a pick is issued:

    assign w_out_safe   = (r_do_rd || r_do_wr) ? bank_rdwr_ready_i[RK0][r_bank] : ...
    assign w_out_reject = r_pick_valid && !w_out_safe;
    assign w_out_ready  = !r_pick_valid || cmd_ready_i || w_out_reject;
    assign w_fire_out   = r_pick_valid && cmd_ready_i && w_out_safe;

`w_out_reject` forces `w_out_ready`, so the unsafe pick is overwritten by the
next one. The module's own comment calls that "Dropping is lossless". **It was
not dropping anything.** The push output was

    assign cmd_valid_o = r_pick_valid;     // no w_out_safe term

so while the rejected pick sat in the output register the cmd FIFO accepted it
(`gaxi_fifo_sync`: `w_write = wr_valid && wr_ready`) and the DRAM executed it.
And because `w_fire_out` *does* include `w_out_safe`, `evt_*_o` never strobed --
so `pumice_bank_timers` and the `r_guard0/1` + `r_preguard0/1/2` chains never
learned the command had been issued. The gate detected the hazard perfectly and
then leaked the command out the side.

### The measurement

`dv/tests/macro/test_pumice_mem_cmd_scheduler.py::cocotb_test_timeout_pre_vs_pending_column`,
scheduler layer only (no AXI front end, no CAMs, no DFI layer), sweeping the
inter-read gap 0..12 x 3 reps.

**CORRECTION, and it matters because of what this bug cost to find.** The
original root-cause run was NOT at the board config, and the first version of
this writeup said it was. The macro TB clocked `aclk` at 100 MHz (`freq=10,
units='ns'`) and programmed `t_rcd=3 t_rp=3 t_ras=5 t_rc=8 t_faw=6` -- a timing
set belonging to no part at no frequency. The mechanism is structural (a missing
term in `cmd_valid_o` is wrong at any clock) so the conclusion survived, but the
claim about how it was measured was false. The TB now derives its clock AND its
timings from a named operating point, and the numbers below are re-measured at
`board_ddr2_300` (75 MHz, tRCD=2 tRP=2 tRAS=4 tRC=5, BL4) with the fix reverted:

| arm | pushes | `w_out_safe==0` | illegal column ops |
|-----|--------|-----------------|--------------------|
| open page, timeout OFF (mode 0)   | 169 | 0 | 0 |
| static close / AP (mode 2)        | 319 | **1** | 0 |
| **fixed_open TR=2 (mode 3)**      | 470 | **10** | **9** |

The board config exposes MORE than the invented one did, not less: at 100 MHz it
showed 9 unsafe pushes in one mode, and at the board it shows 10 in that mode
plus **one in static_close** -- a leaked PRE (`op=OP_PRE`, `do_pre=1`, bank 2,
cycle 4105). That one is not an illegal column op, because a PRE to an idle bank
is legal on DDR2, which is exactly why the JEDEC replay stayed clean for that
arm. It is still a command the controller issued after deciding not to, and
because `w_fire_out` withheld `evt_*` the bank timers never started that bank's
tRP. A second mode was exposed and the wrong-config run could not see it.

The nine illegal column ops in the TR=2 arm are all column RDs to bank 2 and are
**exactly** the commands the JEDEC legality replay flagged -- 1:1, no others in
either direction.

Cycle by cycle at bank 2 (arbiter-internal, one coordinate system):

| cyc | pv | crdy | safe | fire | rowact | pg0 | col_infl | what |
|-----|----|------|------|------|--------|-----|----------|------|
| 5686 | 0 | 1 | 1 | 0 | 1 | 0 | 0 | `timeout_pre_req_i` for b2, unguarded -> PRE picked |
| 5687 | 1 | 1 | 1 | 1 | 1 | 0 | 1 | PRE b2 pushed AND fired; registered image still open |
| 5688 | 0 | 1 | 1 | 0 | 1 | 1 | 1 | preguard arms; a column is already past selection |
| 5689 | 1 | 1 | **0** | **0** | 0 | 0 | 1 | RD b2 at OUT: gate says unsafe, fire=0 -- **pushed anyway** |

The `r_preguard` chain armed exactly as designed. It gates *selection*, and this
column had already been selected against the then-valid open-row image; the
final gate is the mechanism that exists to catch precisely that, and it did.

### The fix

    assign cmd_valid_o = r_pick_valid && w_out_safe;

`w_fire_out` then equals `cmd_valid_o && cmd_ready_i` identically, so the fire
IS the push by construction and the two cannot diverge again. Retraction of
`cmd_valid_o` is safe: `gaxi_fifo_sync` drives `wr_ready` from a registered
`!r_wr_full`, so there is no combinational path back to `wr_valid` and no loop.
Forward progress is unchanged -- `w_out_reject` still frees the output register,
the pick is re-evaluated, and once the bank image updates the column classifies
as a miss and an ACT is picked instead.

### Why it hid for so long

The leak needs a close that the arbiter initiates *without* a column request
driving it, so that a column can already be in flight against the pre-close
image: the background `timeout_pre_req_o` path (modes 3 and 4). In open page
with the timeout off there is no such close, and under auto-precharge the close
rides with the column itself -- which is why both baselines measure 0. It also
needs the cmd FIFO to have room in that cycle; back-pressure would have made
the "drop" real. On the board it surfaced as a single illegal `RD bank=2` in
1046 commands.
