# BUG-002: a command can fire inside the tZQCS window

`scoria_cmd_arbiter` blocks commands during tZQCS in the PICK CONE (priority 2,
`else if (w_zq_busy)`), but `r_zqcs_cnt` loads on the ACCEPTED FIRE of the
ZQCS. So during the ZQCS's own fire cycle `w_zq_busy` is still 0 and the cone
picks freely. That pick lands in the output register and fires one cycle later,
**inside the window** -- and JESD79-3F 3.10 forbids EVERY command while the
device calibrates its output drivers.

**Priority:** P2. The violation is real and it is a JEDEC one, but see
Reachability below: formal finds it under a free CAM environment and
simulation could not reproduce it in 10 alignments, so the evidence that it
occurs in the assembled controller is weaker than BUG-001's.
**Status:** FIXED 2026-10-01, in the session that found it. Found by the
formal proof written for BUG-001 -- the first thing it did was fail on a
property nobody had written before.

## This is BUG-001's shape, on a different window

| | BUG-001 | BUG-002 |
|---|---|---|
| window | tRRD / tFAW, rank-global | tZQCS, device-global |
| checked at | STAGE-1b pre-pick | pick cone, priority 2 |
| fire gate re-validates it | no (before the fix) | no (before this fix) |
| what the per-bank timers see | nothing: not a bank window | nothing: not a bank window |
| shown by | simulation, 3/3 seeds | formal only |

Both are the same error: a window that is not a per-bank property, checked at a
stage upstream of the fire, with `w_out_safe` not re-checking it. Fixing
BUG-001 added the tFAW/tRRD terms to that gate; this adds the tZQCS one.

## The counterexample

`formal/scoria/cmd_arbiter`, assertion `a_zqcs_quiet`, BMC depth 30 (bitwuzla),
failed at step 4 with `t_zqcs = 2`:

| cycle | `zq_grant_o` | `r_zqcs_cnt` | `w_zq_busy` | `evt_pre_o` |
|---|---|---|---|---|
| 2 | **1** (the ZQCS fires) | 0 | 0 | 0 |
| 3 | 0 | 2 (just loaded) | **1** (window open) | **1** |

The PRE at cycle 3 was picked at cycle 2, when the counter had not loaded. The
covers `c_act_in_zqcs` and `c_col_in_zqcs` are also reached, so it is not
specific to PRE: an ACT or a column command can take the same slot.

## Reachability -- state this honestly

The formal environment leaves the CAM side free, which is the strongest
environment and also admits CAM states the real CAMs never produce. So the
counterexample proves the GATE is missing; it does not by itself prove the
assembled controller reaches that state.

Simulation says it does not reach it easily.
`dv/tests/fub/test_scoria_cmd_arbiter.py::probe_zq_shadow_alignment` sweeps the
offset at which a demand entry appears relative to `zq_req`, 10 alignments, and
**0 of 10** land a command in the window. The pick pipeline is 3-4 stages, so
the demand has to already be in flight at the instant the ZQCS fires.

That is the same position pumice BUG-021 was in -- the same mechanism in the
same block, which pumice could only ever show in formal. The argument for
fixing it anyway: the window is a device-global JEDEC obligation, the cost is
one AND term on a gate that already carries two from BUG-001, and the shape has
now produced two bugs in this block.

The argument that it IS reachable, which is why this is P2 and not P3: the
arbiter precharges every bank to issue a ZQCS, so traffic is NORMALLY queued
behind one, and `zq_req` outranks demand. "Pending read, all banks idle,
zq_req high" is what the real controller looks like every time it calibrates --
only the pipeline alignment is in question, not the traffic pattern.

## The fix, as applied

Two gates, one AND term each.

```systemverilog
// scoria_cmd_arbiter.sv -- the final fire gate
if      (r_do_act)            w_out_safe = bank_act_ready_i [RK0][r_bank]
                                        && tfaw_ok_i[RK0] && trrd_ok_i[RK0]
                                        && !w_zq_busy;
else if (r_do_rd || r_do_wr)  w_out_safe = bank_rdwr_ready_i[RK0][r_bank]
                                        && !w_zq_busy;
else if (r_do_pre)            w_out_safe = bank_pre_ready_i [RK0][r_bank]
                                        && !w_zq_busy;
```

Rejecting at the fire is the proven path: `w_out_reject` returns the slot to
the CAM, every commit/issue is qualified by `w_fire_out`, and the window is a
countdown so a closed gate cannot livelock. That is the same argument the
tFAW/tRRD terms already rest on.

The second gate is the REFRESH path, which had the same hole by a different
route:

```systemverilog
assign w_ref_safe = ... && !w_rfc_busy && !r_grant && !r_zq_grant;
```

`w_zq_safe` already carried `!r_grant && !r_zq_grant` -- it guards against the
symmetric race. `w_ref_safe` had only `!r_grant`, and the RTL comment at the
tZQCS counter says so explicitly: "a refresh is kept out of the tZQCS window by
the cone's priority-2 block, not by a term on w_ref_safe". Priority-2 is the
check that is one cycle late, so that comment was describing the bug. Adding
`!r_zq_grant` makes the two paths symmetric.

The declarations of `r_zqcs_cnt` / `w_zq_busy` moved up above `w_out_safe`,
which now uses them.
