# BUG-016: 14 bridge FULL-level tests fail with AXI4 write B-timeouts — pre-existing, blocks FULL sign-off

**Date:** 2026-10-04
**Severity:** HIGH
**Status:** open
**Affects:** fabric-gen-ip bridge DV, REG_LEVEL=FULL only — `test_bridge_1x3_wr_boundary_probe`, `test_bridge_1x4_wr_{basic_connectivity,boundary_probe}`, `test_bridge_1x5_wr_{basic_connectivity,boundary_probe}`, `test_bridge_mix_{a,c,d}_{basic_connectivity,boundary_probe}`, `test_bridge_mix_b_boundary_probe`, `test_bridge_4x4_rw_boundary_probe`, `test_bridge_5x3_channels_boundary_probe` (14 tests)
**Filed from:** tooling TASK-025 (cocotb 2.x migration), where the controls established this is NOT a cocotb-version regression

## Summary

At `REG_LEVEL=FULL`, 14 of 438 bridge tests fail: every one is an AXI4 write
transaction that never receives its B response. The gate and func levels of
the SAME configurations pass. The identical 14 fail under cocotb 1.9.2 with
the identical signature, so this predates the 2.x migration and exists at
exact parity between versions — it was surfaced, not caused, by TASK-025's
BKM matrix.

## Symptoms

From the FULL runs (both cocotb 2.1.0 and the 1.9.2 control):

```
ERROR - AXI4 write transaction failed: addr=0x0000A800, data=0xDE0000A1, ... 
        error: AXI4 write timeout after 5001 cycles: waiting for B response 
        at address 0x0000A800 (id=0)
ERROR - AXI4 write transaction failed: addr=0x80005CA8, data=0xDE03000F, ...
        (same signature)
```

- The `0xDE`-patterned data identifies these as boundary-probe writes.
- Affected configs cluster on write-only bridges (1xN_wr) and the mix_* set;
  all gate/func variants of the same bridges pass.
- Deterministic: fails 4/4 attempts (pytest `--reruns 3`) under both versions.

## Reproduction

```
cd projects/components/fabric-gen-ip/bridge/dv/tests
source $REPO_ROOT/env_python            # shared venv, cocotb 1.9.2
PYTHONPATH=/mnt/data/github/RTLDesignSherpa-DV-dev/src:$PYTHONPATH \
REG_LEVEL=FULL python3 -m pytest \
  "test_bridge_1x3_wr.py::test_bridge_1x3_wr_boundary_probe[full]" -q
```

(fails identically without the PYTHONPATH line and under `venv-cocotb2`.)

## Evidence it is not the cocotb version

- Same 14 tests, same addresses, same timeout signature under cocotb 1.9.2
  with the DV dev tree on PYTHONPATH (control run 2026-10-04, 14 failed in
  780 s).
- The 2.x migration fixes (cancellation, bool casts, handle naming, imports)
  took bridge from 52 passed / 94 failed to 424 passed / 14 failed, all of
  those gains staying green on 1.9.2 as well.

## What is not yet known

- Where the write stalls: the boundary probe writes to `0x0000A800` /
  `0x80005CA8` — whether the address maps to a slave that never responds, or
  the response is dropped/routed away at FULL-level traffic.
- Whether FULL-level probe counts (16 connectivity offsets, seeded probe
  pages, overflow probes) or slave_delay=24 timing pushes a specific bridge
  config past a real RTL corner, or the BFM's timeout accounting is wrong at
  these lengths.
- Why write-only configs dominate: the rd/rw variants mostly pass, except
  `4x4_rw_boundary_probe` — consistent with a write-path-specific condition.

## Suggested starting point

One failing test, `COCOTB_SCHEDULER_DEBUG=1 COCOTB_LOG_LEVEL=DEBUG`, compare
the AW/W/B channel traces of a passing func run vs the failing full run at
the same address — the answer is in the slave-select decode or the B-channel
routing, and the FULL/grid params tell you which.
