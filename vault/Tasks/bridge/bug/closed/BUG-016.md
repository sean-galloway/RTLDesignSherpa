# BUG-016: 14 bridge FULL-level tests fail with AXI4 write B-timeouts — pre-existing, blocks FULL sign-off

**Date:** 2026-10-04
**Severity:** HIGH
**Status:** RESOLVED 2026-10-04 — root cause found in `axi4_dwidth_converter_wr`'s B-response CAM; fixed and re-verified (see Resolution)
**Affects:** fabric-gen-ip bridge DV, REG_LEVEL=FULL only — `test_bridge_1x3_wr_boundary_probe`, `test_bridge_1x4_wr_{basic_connectivity,boundary_probe}`, `test_bridge_1x5_wr_{basic_connectivity,boundary_probe}`, `test_bridge_mix_{a,c,d}_{basic_connectivity,boundary_probe}`, `test_bridge_mix_b_boundary_probe`, `test_bridge_4x4_rw_boundary_probe`, `test_bridge_5x3_channels_boundary_probe` (14 tests)
**Filed from:** tooling TASK-025 (cocotb 2.x migration), where the controls established this is NOT a cocotb-version regression

## Summary

At `REG_LEVEL=FULL`, 14 of 438 bridge tests fail: every one is an AXI4 write
transaction that never receives its B response. The gate and func levels of
the SAME configurations pass. The identical 14 fail under cocotb 1.9.2 with
the identical signature, so this predates the 2.x migration and exists at
exact parity between versions — it was surfaced, not caused, by TASK-025's
BKM matrix.

## Symptoms

From the FULL runs (both cocotb 2.1.0 and the 1.9.2 control):

```
ERROR - AXI4 write transaction failed: addr=0x0000A800, data=0xDE0000A1, ... 
        error: AXI4 write timeout after 5001 cycles: waiting for B response 
        at address 0x0000A800 (id=0)
ERROR - AXI4 write transaction failed: addr=0x80005CA8, data=0xDE03000F, ...
        (same signature)
```

- The `0xDE`-patterned data identifies these as boundary-probe writes.
- Affected configs cluster on write-only bridges (1xN_wr) and the mix_* set;
  all gate/func variants of the same bridges pass.
- Deterministic: fails 4/4 attempts (pytest `--reruns 3`) under both versions.

## Reproduction

```
cd projects/components/fabric-gen-ip/bridge/dv/tests
source $REPO_ROOT/env_python            # shared venv, cocotb 1.9.2
PYTHONPATH=/mnt/data/github/RTLDesignSherpa-DV-dev/src:$PYTHONPATH \
REG_LEVEL=FULL python3 -m pytest \
  "test_bridge_1x3_wr.py::test_bridge_1x3_wr_boundary_probe[full]" -q
```

(fails identically without the PYTHONPATH line and under `venv-cocotb2`.)

## Evidence it is not the cocotb version

- Same 14 tests, same addresses, same timeout signature under cocotb 1.9.2
  with the DV dev tree on PYTHONPATH (control run 2026-10-04, 14 failed in
  780 s).
- The 2.x migration fixes (cancellation, bool casts, handle naming, imports)
  took bridge from 52 passed / 94 failed to 424 passed / 14 failed, all of
  those gains staying green on 1.9.2 as well.

## What is not yet known

- Where the write stalls: the boundary probe writes to `0x0000A800` /
  `0x80005CA8` — whether the address maps to a slave that never responds, or
  the response is dropped/routed away at FULL-level traffic.
- Whether FULL-level probe counts (16 connectivity offsets, seeded probe
  pages, overflow probes) or slave_delay=24 timing pushes a specific bridge
  config past a real RTL corner, or the BFM's timeout accounting is wrong at
  these lengths.
- Why write-only configs dominate: the rd/rw variants mostly pass, except
  `4x4_rw_boundary_probe` — consistent with a write-path-specific condition.

## Suggested starting point

One failing test, `COCOTB_SCHEDULER_DEBUG=1 COCOTB_LOG_LEVEL=DEBUG`, compare
the AW/W/B channel traces of a passing func run vs the failing full run at
the same address — the answer is in the slave-select decode or the B-channel
routing, and the FULL/grid params tell you which.

## Resolution (2026-10-04)

**Root cause.** The write timeout was the last symptom. Instrumented
per-cycle tracing of the B response path during the hanging write showed:
the slave issued B, the xbar consumed it at the periph port, and the
64->32 `axi4_dwidth_converter_wr` (u_wr_conv_32b) accepted it on its
m_axi side but NEVER asserted `conv_32b_bvalid` toward the master side.
The upstream master adapter's AW->B tracker therefore kept one entry
forever (`aw_trk_wptr=32, aw_rptr=31`), which is the persistent
"1 write outstanding" state the post-hang dump first exposed.

Inside the converter, downsize B responses are folded through a CAM of
outstanding slave bursts (the BUG-008 rewrite, depth 16). Each push
stamps a 5-bit age from a free-running counter; the "oldest matching
AWID" search initializes `w_b_cam_best_age` to all-ones and requires a
STRICTLY smaller entry age. Ages run 0..31, so the entry whose age is
exactly 31 -- pushed once per 32 bursts -- can never beat the '1
init: no match. `int_b_valid` needs the match, and the no-match arm of
`m_axi_bready` is 1'b1, so that B is acknowledged to the slave and
SWALLOWED. Exactly every 32nd downsize write hangs the master on a B
that has already been consumed. Deterministic, seed-independent,
address-independent -- matching all fourteen failures' signatures.

**Why FULL only.** The count is per converter since reset, so any test
issuing >= 32 downsize writes trips it. gate/func issue fewer; the FULL
level's seeded-page walk crosses 32 on the first (master, slave) pair.

**Fix.** `axi4_dwidth_converter_wr.sv`, the oldest-match search:
`w_b_cam_best_age` widened one bit beyond the entry age field
(`[B_CAM_AW+1:0]`), with the compare/assign made width-explicit. The
'1 init is now 63 > any 5-bit age (31), so every live entry matches.

**Invariant (owner, 2026-10-04): same-ID bursts will ALWAYS be
serialized** — AXI same-ID ordering, enforced here by the AW splitter.
At most one entry per ID is ever live in this CAM, so the age order
within an ID is unobservable and the counter's wrap at 32 is moot. This
is recorded in the RTL comment at the search; it is a design premise,
not an implementation detail, and revisiting it (e.g. parallel same-ID
issue) requires revisiting this CAM first.

**Verified.**
- Repro test `test_bridge_1x3_wr_boundary_probe[full]`: failed in 3.3 s
  before, passes after.
- The 14-test FULL control set (the original failing list) re-run:
  all pass under cocotb 2.1.0; bridge FULL BKM regression re-run clean
  (see the closing commit message for the final tally).
- The 1.9.2 control path is untouched by construction (pure RTL width
  change); no cocotb-version involvement at any point, consistent with
  the parity evidence in this filing.

**Lesson recorded for the lane.** The BUG-009 fix added the not-full
gating and an overflow `$error` guard, but this failure mode is an
age-compare boundary, not an overflow: the slot was free, the push
landed, the B just never matched. Defense-in-depth guards the case
that was imagined; the strict-`<` against an all-ones init was the
case that wasn't.
