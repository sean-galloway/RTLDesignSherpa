# BUG-003: a short page timeout precharges under an in-flight read — ring loses a ticket at rd_gap >= 8

**Status:** open 2026-09-26  **Priority:** P2 — **nothing shipped is broken.**
Latent: it needs `policy_mode = 3` with a short TR, and the reset is 0, so no
build or board flow reaches it today. It is filed as P2 rather than P1 for that
reason. What it DOES block is making `fixed_open` the default ([[TASK-013]]),
which is the largest measured runtime win on this controller (+41.2%) -- so it
gates a win rather than breaking a shipped feature.

**Not a regression.** The RTL was not changed. The only edit was two RDL reset
values (`policy_mode` 0->3, `tr_init` 0->2), since reverted. The hazard was
already present for any integrator selecting mode 3 with a short TR; moving the
reset made it REACHABLE, which is how it was found. Mode 3 has been selectable
for some time and had never been run from reset by any test or campaign.

Context: pumice's bug lane was EMPTY before this (BUG-001 and BUG-002 both
closed, correctness backlog clear). This is the only open bug.

## Symptom

```
%Error: pumice_rd_return_ring.sv:273: Assertion failed in
        pumice_top_csr_tb_top.u_top.u_core.u_ifc.u_rd_ring:
        RD_RING @2600000: DFI return beat with NO ticket in flight
```

The assertion's own comment states the consequence: *"a read reached the DFI
that the ring never saw issued -- a lost ticket, and every later read would
fill the wrong slot."* So this is a data-integrity alarm, not a performance one.

`test_pumice_top.py::test_pumice_top_gen_replica`, which replicates the two
HARDWARE generators through the AXI4 BFMs and is the test that was built to
catch the PUMICE-037 class.

## Reproduce, and the controlled A/B that proves the cause

`gen_replica` sweeps `rd_gap ∈ [0, 4, 8, 15]` and does **NOT** program the page
policy -- it runs on whatever `PAGE_POLICY_CFG` resets to. That is the variable.

| `PAGE_POLICY_CFG.policy_mode` reset | `PAGE_TIMEOUT_CFG.tr_init` reset | rd_gap 0 | 4 | 8 | 15 |
|---|---|---|---|---|---|
| 0 (legacy) | 0 | pass | pass | **pass** | **pass** |
| 3 (`fixed_open`) | 2 | pass | pass | **FAIL** | **FAIL** |

Same tree, same build flow, only the two RDL reset values differ; reverting them
and regenerating makes the identical two tests pass (2 passed, 143s). Nothing
else changed.

**gap >= 8 is PUMICE-037's signature** (concurrent R/W corruption at gap >= 8,
clean at 0-7, closed via the tRTW derivation). This is very likely the same
hazard class resurfacing through a different trigger.

## Mechanism — hypothesis, NOT yet confirmed

`gen_replica`'s docstring explains what a non-zero gap does, and it is the key:
`cfg_rd_gap > 0` pauses AR **and deasserts RREADY** on every RLAST, so read data
already in flight is backpressured while a concurrent writer keeps running.

Proposed chain:

1. At gap >= 8 the reader stalls mid-return and the bank stops receiving commands.
2. The bank therefore goes IDLE with a read still in flight in the DFI pipeline.
3. `fixed_open` with TR=2 expires almost immediately in that window and raises
   `timeout_pre_req_o`; the arbiter issues the background PRE.
4. The precharge lands while the read is still in flight, and the ring sees a
   return beat for a ticket it no longer has.

**Supporting evidence for the TR-magnitude part:** a test that explicitly
programs a timeout policy with a LONG TR passes today --
`test_pumice_top.py:460` sets `policy_mode=4` with `tr_init=24 / tr_min=8 /
tr_max=96` and is green. So a timeout policy per se is NOT the trigger; a
timeout short enough to fire inside a read's DFI return latency appears to be.
TR=2 against a `rddata_delay` of 2 in sim (7 on the board) is exactly that
regime.

**Not yet tested, and it is the first thing to do:** sweep the reset `tr_init`
(2, 4, 8, 16, 24) against rd_gap 8 and 15 and find where it goes green. If the
boundary tracks read latency, the fix is a guard; if it fails at every TR, the
background-precharge path ignores in-flight reads entirely and the guard has to
be unconditional.

## Why it was never seen before

`fixed_open` has ALWAYS been selectable, so this exposure is not new -- but
nothing ever ran mode 3 out of RESET. Every prior campaign either left the reset
at 0 (legacy) or programmed a long TR. The bug is latent today for any
integrator who sets `policy_mode=3` with a short TR, and it only became blocking
when [[TASK-013]] proposed mode 3 as the default.

## Interaction with the board evidence — read this before trusting either

The board measurements in [[TASK-013]] that recommend `fixed_open` TR=2 INCLUDE
a gap=8 scenario: `col_major_bl8_gap` at MEDIUM level returned `ok=1`, no
mismatched beats, 213.0 MB/s (+9.1%) under `fixed_open_tr2`. So on real silicon,
at the same nominal stimulus shape, the data came back correct.

That does **not** clear the hardware. The assertion is `ifndef SYNTHESIS`, so the
board has no equivalent check -- a lost ticket that happens to refill in the
right order, or a run that never hits the window, produces a clean integrity
result either way. Treat the board's pass as "did not corrupt in that run", not
as "cannot corrupt". Until this is understood, the +9.1% / +41.2% numbers should
be quoted as measured-but-unqualified, not as shippable.

## Fix directions

* **Guard the background precharge on in-flight reads to that bank.** The
  scheduler already tracks read tickets (`pumice_rd_return_ring`); gating
  `timeout_pre_req_o` on "no outstanding ticket for this bank" is the direct fix
  and costs a comparator.
* **Clamp `tr_init` to a read-latency floor.** Cheaper and weaker: refuse a TR
  below `rddata_delay + margin`. Hides the bug rather than fixing it, and the
  floor is geometry-dependent, so prefer the guard.
* Check whether `bank_timer`'s `r_ap_pending` path has the same exposure -- it is
  the other place a close can be initiated without consulting the read ring.

## Blocks

* [[TASK-013]]'s recommendation to default `policy_mode = 3` / `tr_init = 2`.
  The RDL resets were changed and then REVERTED on 2026-09-26 pending this bug;
  the measurement, the docs and the recommendation all stand, the default does
  not ship.

Related: [[TASK-013]] (the campaign and the measured win), [[TASK-014]] (the
adaptive-mode disposition, which also routes closes through this path).
