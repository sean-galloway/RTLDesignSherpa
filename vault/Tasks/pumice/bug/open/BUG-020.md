# BUG-020: all 35 OBS_* observation registers are undriven and read zero forever

**Status:** open 2026-09-27  **Priority:** P2 -- they are documented, readable,
and cannot report anything. Any analysis built on one is built on a constant.
**Owner:** TBD
**Found by:** [[TASK-015]] layer 2b, on its first run against the BOARD.
**Related:** [[ISSUE-014]] (the hit derivation, which exists because these are dead)

## Expected vs actual

`pumice_csr.rdl` defines 35 `OBS_*` registers and the MAS/HAS document them as
live telemetry. `pumice_top.sv` drives **zero** of them: there is not one
`hwif_in.OBS_*` assignment in the file. The regblock input struct exists, nothing
connects to it, so every one reads 0 permanently.

    $ grep -c 'hwif_in\.OBS_' rtl/top/pumice_top.sv
    0

For contrast, the seven `*_STATS_*` counters ARE driven at
`pumice_top.sv:132-136` and work correctly.

| register group | count | what it claims to report |
|---|---:|---|
| `OBS_ROW_HIT[0..7]` | 8 | per-bank row-hit count (`onread = rclr`) |
| `OBS_WORDS[0..8]` | 9 | word counters |
| `OBS_REF_LATENCY[0..7]` | 8 | per-bank refresh blocking time |
| `OBS_REFRESH_DEFER_HIST_0..3` | 4 | refresh deferral histogram |
| `OBS_AXI_R_LATENCY_AVG` / `_P99` / `OBS_AXI_W_LATENCY_AVG` | 3 | AXI latency |
| `OBS_TXN_QUEUE_DEPTH_AVG` / `_MAX` | 2 | transaction queue depth |
| `OBS_REFRESH_PENDING_MAX` | 1 | peak pending refreshes |
| **total** | **35** | |

## How it was caught

`seq_telemetry` on the board (Nexys A7-100T 210292BFA3EE, fresh bitstream,
`policy_mode=3`/`tr_init=2` at reset), `incremental` family, 32000 transactions:

    [telemetry] incremental: col_ops=32000 ACT=184 PRE=184 miss=176 empty=8
                per_bank_hits=0 ACT-col_ops=-31816

32000 column ops against 184 activations is a ~99.4% row-hit workload, so the
eight per-bank hit counters should total about 31816. They totalled **0**, and
the layer-2b rule `hits_at_least_col_ops_minus_act` (hits >= col_ops - ACT)
fired. `activation_causes_account` held exactly (176 + 8 = 184), which is what
said the ACT/miss/empty side is fine and localised the fault to the OBS block.

This is the first time anything read these registers. The sim suites never did
(the telemetry was exported and only the board host looked at it, and the board
host only ever read the `*_STATS_*` seven), so 35 dead registers sat in the map
and in the published docs without a single consumer to notice.

## Why pumice has these at all -- and why most should be DELETED

Sean, 2026-09-28: *"why would pumice have any obs registers???"*. Investigated;
the 35 split into three groups with different answers, and only one group has a
case for being wired up.

**Group A -- 5 registers that duplicate shared blocks, on the wrong side of the
interface.** `OBS_AXI_R_LATENCY_AVG`, `_P99`, `OBS_AXI_W_LATENCY_AVG`,
`OBS_TXN_QUEUE_DEPTH_AVG`, `_MAX`. The char harness already instantiates
`rtl/amba/shared/axi_bus_meter.sv` and `rtl/amba/shared/axi_perf_latency_hist.sv`
directly at `char_engine_block.sv:608-712`. [[TASK-025]] was DROPPED on exactly
this ground -- adopting the observer "buys no measurement pumice does not already
have" -- and the same argument retires these: AXI latency and occupancy are
properties of the interface, measured better from outside it by a block that sees
what the system sees. **Delete.**

**Group B -- 9 registers whose source was deleted two months ago.**
`OBS_WORDS[0..8]`, described in the RDL as "Packed obs_* signals from FUB
internals (see csr_obs_layout.md)". That doc specifies the packing as
`command_scheduler_macro.obs_words_o[6:0]` + `axi_frontend_macro.obs_words_o[1:0]`.
Both macros were rearchitected, and the aggregator was removed in **e8908eebf
(2026-07-21, "retire three dead code trees")** -- `obs_words` now appears nowhere
in `rtl/`, not even in `rtl/OLD/`. The RDL window was left behind when its driver
was retired. **Delete, or restore the aggregator if the debug window is wanted --
but it has been unavailable for two months and nobody noticed.**

**Group C -- 21 registers nothing outside the controller can see.**
`OBS_ROW_HIT[8]`, `OBS_REF_LATENCY[8]`, `OBS_REFRESH_DEFER_HIST_0..3`,
`OBS_REFRESH_PENDING_MAX`. Per-bank row hits and refresh behaviour are genuinely
invisible from outside pumice, so these cannot be replaced by a shared block.
But the AGGREGATES already exist and already work: `PAGE_STATS_{HIT,MISS,EMPTY}`,
`SCHED_STATS_{ACT,PRE}`, `REF_STATS_{REF,REF_BUSY}`. Nothing has ever consumed
the per-bank detail.

**`OBS_ROW_HIT[8]` is the one group with a concrete consumer.** [[ISSUE-014]]
established that the documented `hits = col_ops - ACT` derivation is unsound
under a background-close mode -- it goes negative -- so the eight per-bank
counters are the ONLY sound way to get a row-hit count on the shipping default.
Wiring those 8 would close ISSUE-014 properly instead of leaving a clamp with a
wrong explanation. The other 13 in this group need a named consumer or they go
the way of Group A.

**Stale doc.** `docs/csr_obs_layout.md` says *"Status (refreshed 2026-08-27):
IMPLEMENTED. The obs_* window is live in the PeakRDL CSR at 0x1C0-0x1E3"*. That
was already false when written -- the aggregator had been gone since 2026-07-21.
Corrected in the same commit as this note; the layout body is kept because it is
the authority for the bit packing if Group B is ever restored.

## Done when

1. Group A (5) and Group B (9) are **removed from the RDL and the docs**;
   `OBS_ROW_HIT[8]` is driven, closing [[ISSUE-014]]'s derivation problem at
   source; the remaining 13 of Group C are each given a named consumer or
   removed with them.
   A documented register that reads zero is worse than an absent one: ISSUE-014
   exists only because the hit rate had to be back-derived from `col_ops - ACT`
   instead of read from `OBS_ROW_HIT`, and that derivation is itself unsound.
2. Whichever way it goes, the docs are regenerated in the same pass (handbook:
   docs sync with configs) and the MAS register map stops advertising dead ones.
3. `seq_telemetry`'s skip of `hits_within_col_ops` /
   `hits_at_least_col_ops_minus_act` is removed, and
   `test_obs_row_hit_counters_are_dead` (which currently PINS the broken state so
   the workaround cannot silently outlive the fix) is deleted with it.

## Note on the workaround

`seq_telemetry` now skips the two per-bank rules and asserts the counters are
still zero, naming this bug. That keeps the board sequence usable while the
defect stands, and makes the sequence FAIL the moment someone wires the counters
up -- so the skip cannot quietly survive its reason.
