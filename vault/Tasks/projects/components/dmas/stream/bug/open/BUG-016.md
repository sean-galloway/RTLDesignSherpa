# BUG-016: the monitor PKT_MASK registers say "1 = enable" and default to 0xFFFF, but the group drops on 1

**Priority:** Medium -- the board tooling already programs the mask correctly
(`projects/fpga-systems/Genesys2/stream/bin/mon_configs.py`: "1 = drop that
packet type at monbus entry"), so measurements are not affected; the register
description and the reset default are what is wrong.
**Status:** OPEN 2026-09-27. Found from rapids BUG-008, the same inversion in
the RAPIDS copy of the register file, which is fixed there.

## Mechanism

`rtl/macro/stream_mon_regs.rdl` declares `DAXMON_PKT_MASK`, `RDMON_PKT_MASK` and
`WRMON_PKT_MASK` as "Packet type mask [15:0] - 1=enable, 0=disable" with a
default of `16'hFFFF`. `stream_top_ch8` feeds them to `monbus_axil4_axil4_group`
(`cfg_axi_pkt_mask` <- DAXMON, `cfg_axis_pkt_mask` <- RDMON) and to the
monitors (`axi_monitor_filtered`, `axi_monitor_lite`), all of which implement
`pkt_drop = cfg_*_pkt_mask[pkt_type]`. So at reset every packet type is dropped,
and a host that follows the register description writes 0xFFFF to "enable" and
silences the monitors. The per-event `*_MASK1/2/3` fields are documented and
defaulted as suppress masks and are consistent.

## Fix (not applied here)

Mirror rapids BUG-008: change the three descriptions to "DROP mask - bit[type] =
1 drops that packet type, at the monitor and again at the monbus group",
default `16'h0000`, regenerate through `bin/peakrdl_generate.py`, and reword the
HAS register map. Check `mon_configs.py` and the char host still write the mask
explicitly (they should; the default change only removes the surprise), then a
clean full STREAM regression.
