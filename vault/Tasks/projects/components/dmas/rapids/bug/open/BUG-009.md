# BUG-009: the sink wedges when a write burst equals the per-channel SRAM depth (WR_XFER_BEATS = SRAM_DEPTH - 1)

**Priority:** Medium -- a legal register value (AWLEN 255 is inside the field's
range) deadlocks a channel with no error, no timeout escalation and no monitor
packet; the host sees `beat_total = 0` and a stuck STATUS. A host that never
programs bursts this long never sees it.
**Status:** OPEN 2026-09-29. Found on the Genesys 2 (build 2 of 2026-09-28,
monitors in, `SRAM_DEPTH = 256`, `AW_MAX_OUTSTANDING = 8`) while measuring the
single-channel window knobs.

## What happens

`run_characterization.py --suite --suite-channels 1 --suite-beats 4096
--suite-xfer 7,15,31,63,127,255 --suite-delay 0,256,512` (data:
`reports/perf/json/genesys_one_channel_xfer_latency.json`): every row with
`WR_XFER_BEATS = 255` (256-beat bursts) fails the same way, at every latency:

- SINK AXIS-in meter: `prod = 256`, then backpressure for the rest of the
  window -- the ingress accepted exactly one SRAM-depth of beats and stalled.
- SINK AXI4-wr meter: `prod = 0`, starvation for the whole window -- no AW was
  ever issued.
- host: `timeout: status=0x0000000A beat_total=0 (expected 4096)`,
  `wr_crc_valid = 0`.

Bursts of 8..128 beats pass on the same bitstream (128-beat bursts: 97.9 %
AXI4-wr at 0, 256 and 512 cycles of injected latency). The SOURCE half with
`RD_XFER_BEATS = 255` on the same 256-deep SRAM does not wedge: one 256-beat AR
in flight, 99.8 % at zero latency.

## Where to look

`axi_write_engine_beats.sv` issues an AW only when
`w_has_data = (w_effective_avail >= transfer_size + 1)`, i.e. the whole burst
is already in the SRAM. With the burst equal to the depth that needs
`axi_wr_drain_data_avail == 256` while the ingress, having filled every
segment (`ALLOC_SIZE = 16` x 16), is stalled by the sink allocator -- so either
the availability count never reports the full depth (the accounting FIFO and
the `[ADDR_WIDTH:0]` port carry 0..DEPTH, but the doubled virtual depth in
`sram_controller_unit` and the "occupancy + bridge" headroom note are worth
re-reading with DEPTH-sized bursts in mind), or the sink allocator refuses the
last segment. Either way the channel is stuck with nothing outstanding, which
the scheduler's write-progress timeout should have escalated and did not (the
timeout counts B responses against issued AWs, and none was issued).

## Done when

- [ ] the mechanism is named (count saturation vs. allocator vs. the has_data
      compare) and either the burst is allowed to equal the depth or the
      register description and the HAS state the limit (`WR_XFER_BEATS + 1 <
      SRAM_DEPTH`) and the engine refuses/escalates instead of hanging
- [ ] a sink test at `WR_XFER_BEATS + 1 == SRAM_DEPTH` (the OFF state of the
      limit) passes or fails loudly, never hangs
- [ ] the board row above passes or reports an error
