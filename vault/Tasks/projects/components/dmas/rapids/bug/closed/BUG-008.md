# BUG-008: the monitor PKT_MASK registers were documented as "1 = enable"; the hardware masks on 1

**Priority:** Medium -- documentation only. A host following the register
description would write 0xFFFF to "enable" and silence the monitors instead.
**Status:** CLOSED 2026-09-28 (closing note at the end); was OPEN 2026-09-27.
Found while wiring the AXIS monitor-lites (rapids TASK-015).

## Mechanism

`rapids_mon_regs.rdl` described `DAXMON_PKT_MASK`, `RDMON_PKT_MASK` and
`WRMON_PKT_MASK` as "Packet type mask [15:0] - 1=enable, 0=disable". Both
consumers treat a set bit as MASKED (dropped):

- `axi_monitor_lite` / `axis_monitor_lite`: `type_allowed(t) = !cfg_*_pkt_mask[t]`
- `monbus_group_core`: `pkt_drop = cfg_*_pkt_mask[pkt_type]`

The reset value of 0xFFFF (everything masked until the host unmasks the
classes it wants) is the intended behaviour (Sean, 2026-09-28), consistent with
the per-event `*_MASK1/2/3` suppress masks. A first version of this fix also
changed the reset to 0; that was wrong and was reverted in the same day.

## Fix

`rapids_mon_regs.rdl`: the three descriptions now read "bit[type] = 1 MASKS
(drops) that packet type, at the monitor-lite and again at the monbus group.
Reset = all masked". Regenerated through `bin/peakrdl_generate.py`
(`rapids_regs.rdl` for the RTL and docs, `rapids_regmap.rdl --regmap` for
`rtl/rapids_regmap.py`); the generated RTL is unchanged against the pre-fix
tree. The HAS register map and the MAS config-block page state the polarity
and the reset.

## Verification

`test_rapids_beats_top_axis_mon` (rapids TASK-015) clears the masks explicitly
before it looks for packets; with the masks at reset it sees none, as designed.
STREAM's `stream_mon_regs.rdl` carries the same "1=enable" description: stream
BUG-016, description-only.
