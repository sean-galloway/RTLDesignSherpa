# BUG-003: the source path stops 3-4 beats short of a long transfer and drains at 50%

**Priority:** High -- every SOURCE-path characterization row at >= 1024 beats fails on the
Genesys 2, and the ones that pass read AXI4-rd / AXIS-out at ~50% where the July report
had 96-100%. **Status:** CLOSED 2026-09-27 -- root-caused by bisect, two fixes, sim and
board signatures gone.

## Symptom

`run_characterization.py` SOURCE rows: `timeout: beat_total=1020 (expected 1024)` at 1 ch,
`8185 (expected 8192)` at 8 ch, then a golden mismatch on the truncated CRC. Small transfers
(<= 256 beats) pass but the source egress sits at 49-51% engaged utilization (AXIS-out
`prod == starv`), on the bare meters and the interface observers alike. Bare and
`USE_OBSERVERS=1` bitstreams fail identically, so the observers were not the cause.

Sim reproduces it exactly: `test_rapids_char_harness_source` at `TEST_NUM_ACTIVE=1
TEST_NUM_BEATS=1024` reports `beat_total=1021`; the macro conservation cell
`test_src_data_path_axis_test_beats::test_beat_conservation` with
`TEST_CONS_DESCS=1 TEST_CONS_BEATS=1024` on the `default` slave profile reads 1024 beats
from AXI and sends 1020 (`high_throughput` passes -- the loss needs the SRAM to fill).

## Root causes (two, both introduced by bdf4e0dff)

1. **Stranded beats -- in STREAM's shared `sram_controller_unit`.** `stream_drain_ctrl`
   is an accounting counter (FIFO writes minus reservations) but is built as a virtual FIFO
   of depth `SD` whose own `wr_ready` gates its write count. `stream_alloc_ctrl` bounds
   written minus DRAINED to `SD`, and the latency bridge holds up to 5 beats outside the
   FIFO, so written minus RESERVED legitimately reaches `SD` while the real FIFO still
   accepts. At that boundary the FIFO takes the write and the counter refuses to count it:
   the beat exists, is never reservable, and stays in the channel. Waveform: `wr_ptr` ended
   at 1020 for 1024 FIFO writes, 4 beats left in FIFO + bridge with `data_available == 0`.
   Latent in STREAM (stream BUG-011); rapids hit it because of cause 2.
2. **50% cadence -- in rapids' `src_data_path_axis_beats` arbiter.** The rewrite took a
   grant, drained its reserved block, retired, and only then re-arbitrated: one reservation
   pulse plus one beat every other cycle at `cfg_drain_size == 1` (the shipped setting).
   STREAM's write engine never has that bubble -- its AW issue (reservation) and W phase
   (drain) are separate stages joined by an in-order FIFO, and the next block loads on the
   last beat.

## Fixes

- `projects/components/dmas/stream/rtl/fub/sram_controller_unit.sv`: the drain accounting
  gets `DEPTH(2 * SD)` (its rd pointer relies on power-of-2 wrap) and the wider count is
  truncated back to the unit's `[ADDR_WIDTH:0]` port -- the value can never exceed `SD` +
  bridge occupancy. STREAM's own file; flagged as such.
- `projects/components/dmas/rapids/rtl/macro_beats/src_data_path_axis_beats.sv`: the
  arbiter is now two stages -- a round-robin RESERVATION stage (one decision per cycle,
  registered into the one-cycle `drain_req` pulse, STREAM's two-cycle in-flight
  compensation kept) feeding a 4-deep in-order queue, and a DRAIN stage that pops it and
  loads the next block on the last accepted beat.
