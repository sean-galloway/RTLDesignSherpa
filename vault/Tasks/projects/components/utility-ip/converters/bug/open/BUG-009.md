# BUG-009: dwidth read converter does not support beat-level R interleaving across IDs

**Priority:** P3 — latent. Needs a downstream slave that interleaves R beats of
different ARIDs, which no integration in this repo generates today (pumice's
return ring is AR-ordered; the bridge slave adapters return R per-ID in order,
burst-atomic; APB/AXI-Lite downstreams are in-order across IDs).
**Status:** open 2026-10-04. Filed closing BUG-008 (the rd half of its
investigation).

**Contract that IS supported (verified 2026-10-04).** The read converter
(`axi4_dwidth_converter_rd.sv`) regenerates the slave-side RID/RUSER from the
most recent master R beat (`r_rid_held`/`r_ruser_held`). Under AXI4's per-ID
ordering, this is EXACT whenever each master R burst returns burst-atomic
(all its beats contiguous): the held value at any group-complete or skid
capture is that burst's own ID, and the data primitives back-pressure the
master R stream while a converted beat is stalled, so a later burst's beats
cannot slip in mid-group. Whole R bursts completing out of order ACROSS IDs
is fine under this contract.

**What breaks it.** If a downstream slave interleaves R beats at BEAT level
across ARIDs (permitted by AXI4), the `axi_data_*` primitives merge beats of
different IDs into one wide word — corrupted data, and `r_rid_held` reports
the most recent beat's ID. No warning; silent misattribution.

**Candidate fix shape.** Per-ID R assembly before the data primitives: demux
master R beats by RID into per-ID buffers, reframe per slave AR split record,
and emit slave R in AR order per ID. This is a redesign of the R path, not a
fold tweak — fund it only if a real integration needs beat-level interleave.

**Test that would catch it.** Two ARIDs whose downstream R beats interleave
one-beat-per-ID round-robin; assert slave-side data and RID attribution per
beat.
