# BUG-008: dwidth converter split-fold assumes in-order B across IDs -- CLOSED (wr fixed + DV regressions, 2026-10-04)

> Migrated 2026-09-27 from `vault/Tasks/projects/components/utility-ip/converters/open.md` as **CONV-010** (tooling TOOL-001). The flat page did not record a lane; this item was placed by hand. Body preserved as written -- only the H1 and this line are new.

*Renumbered from CONV-001 on 2026-09-14. It was filed in `vault/Tasks/amba/`,
where CONV-001 was free; moving it to the area it belongs to put it against the
converters' own CONV-001 (a resolved dnsize LAST fault). The area is the ID
namespace, so the clash only appeared once the task was in the right place.*

**Priority:** P3 — latent, needs an interleaving downstream AND a master using
multiple write IDs through the converter at once.
**Status:** closed 2026-10-04. **Write side fixed; read side investigated and
cleared** (analysis below) — the remaining read restriction is tracked as
[[BUG-009]].

**What the RTL did.** `axi4_dwidth_converter_wr.sv` split one oversized slave
burst into several master bursts and recorded each in a single FIFO:

    logic [9:0]         splitq_mem [SPLITQ_DEPTH];
    logic [SPLITQ_AW:0] splitq_wptr, splitq_rptr_w, splitq_rptr_b;
    assign split_b_final = splitq_mem[splitq_rptr_b[SPLITQ_AW-1:0]][9];

The B fold popped one entry per downstream response and forwarded a B to the slave
only on the record marked final.

**Why it was only sometimes correct.** All pieces of one split burst carry the
AWID of the burst they came from, and AXI4 guarantees same-ID B responses come
back in order — so within one ID the FIFO fold was exact. Across IDs AXI4 places
no such ordering requirement. If two slave bursts with different IDs were both
split and the downstream interleaved their responses, the FIFO could not tell them
apart and decremented the wrong record: one burst's B was released early, the
other's never completed. Reachability in this repo (2026-10-04 survey): generated
multi-master bridge adapters (`bridge_4x4_rw`, `bridge_mix_b`, `bridge_2x2_wb4`,
`bridge_5x3_channels` on its 256b path) place the converter in front of CAM-backed
AXI4 slaves that deliberately preserve cross-ID out-of-order response routing, and
the pumice/scoria host-width gearing feeds it a FR-FCFS multi-ID controller — the
2026-09-01 "no shipped integration does both" premise is stale.

**Fix applied (write side, `axi4_dwidth_converter_wr.sv`).** The split queue
keeps only its W-framing role (one read pointer, full-check against it). The
B fold is a per-burst CAM keyed by AWID: each outstanding slave burst gets an
entry holding its split count and worst BRESP seen so far; every master B
searches for the oldest matching AWID, decrements, folds (worst wins), and
forwards a slave B only when the count reaches zero. Same-ID bursts stay in
order; cross-ID bursts can complete in any order. Because the CAM drains on B
return while the split queue drains on W framing, split-queue space alone does
not bound CAM occupancy — a flood of unsplit bursts with slow B return would
overflow the CAM and drop pushes (found in review; the 20-burst flood
regression below fails RED without it). The burst's FINAL master AW is
therefore gated on a free CAM slot (`w_b_cam_slot_free`), restoring the
back-pressure the old B-laggard full-check provided; a `SIMULATION`-guarded
$error remains as defense in depth.

**Read side — investigated, no fix warranted (ruling, recorded 2026-10-04).**
An implementation of this bug's rd half (sideband-carry of {RID,RUSER} through
the `axi_data_*` primitives, new `SB_BROADCAST_WIDTH` parameter, dedicated
OOO-R test) was built and then REVERTED after its own regression test passed
against the PRE-FIX RTL — i.e. the claimed burst-level misattribution does not
exist. Analysis: `r_rid_held` is exact under the module's documented contract
(master R bursts return burst-atomic per ID; the primitives back-pressure the
master R stream while a converted beat is stalled, so a later burst's beats
cannot slip in mid-group; at any group-complete or skid capture the held value
IS that burst's ID). Whole R bursts overtaking each other across IDs was
already correct. What the rd converter genuinely does not support is BEAT-LEVEL
R interleaving across IDs (AXI4-permitted, and the data primitives would merge
beats of different IDs into one wide word) — that was true before this bug and
remains true; it is filed as [[BUG-009]] rather than silently assumed closed.

**Verification (all evidence from 2026-10-04).**
- `test_axi4_dwidth_converter_wr_ooo_b`: concurrent split write bursts on
  distinct AWIDs, Bs returned cross-ID out of order. RED: FAILS on the pre-fix
  RTL (early/missing B). GREEN: passes on the fix.
- `test_axi4_dwidth_converter_wr_b_cam_flood`: 20 unsplit single-beat bursts
  (> B_CAM_DEPTH 16) with all Bs held back 200 cycles, then one B per AW.
  RED: FAILS on the fix without the CAM-slot gate (4 pushes dropped; 4 slave

- Full `test_axi4_dwidth_converter_wr.py` + `test_axi4_dwidth_converter_rd.py`
  suites: all configurations pass (gate/func/full); the rd suite passes on the
  reverted (parent) rd RTL.
