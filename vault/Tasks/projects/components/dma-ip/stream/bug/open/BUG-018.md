# BUG-018: both AXI engines wrap a 256-beat burst to 0 beats (8-bit "AxLEN + 1")

**Priority:** P2 -- a legal register value (`WR_XFER_BEATS` / `RD_XFER_BEATS`
= 255 is inside the 8-bit field) corrupts the SRAM bookkeeping of the channel
that uses it, silently, and `CHANNEL_RESET` does not reach that state. A host
that never programs 256-beat bursts never sees it; the characterization
campaigns stop at 128 beats.
**Status:** OPEN 2026-09-29. Found in rapids (rapids BUG-009, on the Genesys 2
with an ILA); the STREAM engines carry the same lines, untouched since the
port. Not yet reproduced on STREAM hardware -- the same code, same widths.

## What the code does

`axi_write_engine.sv`:

```
w_has_data[i]  = (SCW'(w_effective_avail[i]) >= SCW'(w_transfer_size[i] + 8'd1));   // line 427
w_drain_size[r_aw_channel_id] = m_axi_awlen + 8'd1;                                  // line 611, [7:0]
w_phase_txn_fifo_din.beats    = m_axi_awlen + 8'd1;                                  // line 778, [7:0]
b_phase_txn_fifo_din[..].beats = m_axi_awlen + 8'd1;                                 // line 845, [7:0]
```

`axi_read_engine.sv`:

```
w_space_ok[i] = (w_effective_space[i] >= SCW'(w_transfer_size[i] + 8'd1));   // line 370
r_alloc_size <= w_transfer_size[w_arb_grant_id] + 8'd1;                       // line 517, [7:0]
```

`w_transfer_size` is the AxLEN (0..255). The `+ 8'd1` is evaluated in 8 bits
BEFORE the `SCW'()` cast, so AxLEN 255 makes it 0:

- write side: `has_data` passes on `avail >= 0`, the AW for 256 beats goes out
  on an empty buffer, `drain_ctrl` reserves 0 beats, and the W phase pulls 256
  beats that were never reserved. On rapids' ILA (`trace_A_x255.csv`) the AW
  fired at `w_effective_avail = 48`; by the end of the run
  `drain_data_available` sat at 0 with 50 beats in the FIFO, and stayed at 0
  for every later run on that channel (`trace_B_x127_after_x255.csv`: the
  buffer fills to 128, `w_has_data` never rises, `s_axis_tready` drops -- the
  BUG-009 "one buffer accepted, no AW" wedge). Only a reprogram clears it.
- read side: `space_ok` passes on any free count and the AR for 256 beats
  allocates 0: the engine over-fetches past the buffer (rapids board: 4103
  R beats for a 4096-beat descriptor, golden mismatch).

The `sram_controller` size ports are `[7:0]` as well, so 256 cannot be
carried to it even with the sum widened.

## The fix rapids took (2026-09-29)

Clamp the configured AxLEN in the engine to what the buffer holds and to 254
beyond it (`XFER_MAX = SD_BEATS < 256 ? SD_BEATS - 1 : 254`, with
`SD_BEATS = 2^(SCW-1)`), and gate/size everything from the clamped value. A
burst larger than the buffer can never be fully available, so the clamp costs
nothing; the last AxLEN value (256 beats) is given up so every count fits the
8-bit ports. Unit cells `test_axi_*_engine_beats[cap-...]` (AxLEN 255 against
a 128-deep model) fail on the old lines and pass on the clamp.

The same three-line change applies to `axi_write_engine.sv` /
`axi_read_engine.sv` here. It is NOT applied: STREAM's engines are Sean's
reference implementation and this file is the confirmation-of-scope step
before a shared-methodology edit.

rapids BUG-009's two further findings (whole-segment-only ingress allocation,
and the allocation-view race behind the partial allocation that fixed it) are
in rapids' AXIS ingress (`snk_data_path_axis_beats.sv`), which STREAM does not
have; nothing of those applies here.
