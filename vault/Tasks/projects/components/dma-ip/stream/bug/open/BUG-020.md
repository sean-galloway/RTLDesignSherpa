# BUG-020: arming the obs error cone makes the monlite shared output queue lossy (ERR_EVENT_DROPPED flood)

**Priority:** P2
**Status:** open
**Owner:** TBD
**Filed:** 2026-10-08
**Refs:** stream BUG-019 closure (board re-pin 2026-10-08, commit bff808b68); results footer in build-obs/results/obs_board_2026-10-08.txt

## Reproduction

Board: Genesys 2, build-obs image from main (commit bff808b68 notes the
bitstream). Host campaign `make -C build-obs host-obs_campaign`.

Board A/B isolation (same image, per /tmp/bug019_board.log):
- arm COMPL only (0x84): 0 drops.
- arm COMPL|TMO (0x86): 0 drops.
- any arm with ERROR_EN (0x85/0x87): ~90% of completion events dropped
  by the monlite shared output queue; the tallies then report
  monitor-lite `AXI_ERR_EVENT_DROPPED` packets (type 0, event 0x0E,
  data = drop count) — ~1,969/iter/tally — which land in the campaign's
  UNEXPECTED (~78,560) and trip its hard fail (exit 1).
- error TYPE source-masked via AXI_PKT_MASK with ERROR_EN still armed:
  0 drops (2,193 keyed). CAM width/content irrelevant.

## What is correct

Unclear — that is the bug. Two open questions: (1) WHY does err_en
poison the shared queue (backpressure interaction? error-event
priorities bypassing the queue discipline?) — RTL investigation in the
stream monitors/monlite area; (2) campaign-side disposition: should the
campaign key `(0/16, 0, 0, 0x0E)` drop-reports as a first-class expected
class, or leave the error cone unarmed when no error stimulus is driven?
The honest-instrument behavior (dropped events ARE reported as 0x0E, not
silently lost) is working as designed; the rate is the anomaly.
