# BUG-019: stream obs/mon host campaigns still arm and report lite-taps-retired cones

**Status:** CLOSED 2026-10-08 — host side DONE 2026-10-04; board
re-pin of the results files is parked (needs a Genesys 2 session, same
shape as misc TASK-003's board matrix).
**Priority:** P3
**Filed from:** closing stream TASK-016 (sdpram re-measurement).

78cddb5e2 (2026-09-27) wrapped the shared observers in the lite monitors: the
perf and debug cones are no longer built, and OBS_CAPS0 bit4/bit5 now read 0
honestly. The stream host campaigns predate that rework:

- `build-obs/host/host_obs_campaign.py` arms the `rd_perf`/`wr_perf` tally
  classes unconditionally, so on a current build ~89% of live-traffic packets
  land in `UNEXPECTED` (see `build-obs/results/obs_board_2026-10-03.txt` —
  stream total 43,920 vs 5.69M on the pre-rework instrument, with the caps
  lines showing `perf=0`). The campaign still exits clean (CRC PASS), but the
  class accounting is misleading.
- `build-mon`'s `host-mon_coverage` legal tuple set includes
  `rd_perf`/`wr_perf` (and `sched_desc_complete` / `desc_loaded`), which the
  current monitors never produce — 4/8 tuples seen, 0 unexpected
  (`build-mon/results/mon_coverage_2026-10-03.txt`).
- `host-obs-matrix`'s `debug` class reads keyed=0 (cone retired; pre-rework
  baseline was 13,212). Matrix now reports 5/7 vs 6/7 pre-rework, with the
  delta explained entirely by the instrument change, not any RTL defect.

**What to do:** re-baseline the three campaigns against OBS_CAPS0 (skip or
redefine classes for absent cones; make `UNEXPECTED` a hard fail only for
classes the caps say exist), and re-pin the campaign expectations the same
way. The sdpram fix (71d48b6f7) is NOT implicated — datapath behavior is
cycle-identical (TASK-016).

**Done when:** the three campaigns derive their expected-class sets from
OBS_CAPS0 at runtime, and their pass/fail criteria no longer depend on
retired cones; the obs/mon results files carry the new expectations.

## Progress (2026-10-04)

Host side implemented; the "results files carry the new expectations" leg is
the parked board re-pin. One deliberate deviation from the letter of "derive
from OBS_CAPS0", documented here so the next reader does not "fix" it:

- **build-obs campaigns** (`host_obs_campaign.py`, `host_obs_matrix.py`):
  OBS_CAPS0 per observer is exactly right and is now the contract. Helpers in
  `bin/obs_addrs.py` (`read_caps0`, `filter_legal_by_caps`, `mon_ctrl_arm`)
  filter each observer's legal set from its own caps and DERIVE the MON_CTRL
  arm word from what is keyed ("arm what you key"). Two measured behaviours
  fell out of that: (1) the ~89% UNEXPECTED flood was THRESHOLD packets — the
  old arm word 0x9F enabled THRESHOLD_EN while no threshold tuple was ever
  keyed; the derived arm drops it. (2) `host_obs_matrix` rows now SKIP when
  their PRIMARY class has no emit path (`plan_class`) — the perf row must not
  read "OK" off its companion completion tuples. Rows can also run with a
  reduced set (addrmatch loses debug_side on the lite taps). UNEXPECTED is a
  hard fail in the campaign (exit 1) and demotes a matrix row to LOW.
- **build-mon campaigns** (`host_mon_coverage.py`, `host_mon_matrix.py`):
  OBS_CAPS0 is the WRONG register here — it describes the observer instances,
  which build-mon disarms (OBS_ENABLE_MON_TAPS=0), so it reads all-zero cones.
  The honest build-mon sources are `BUILD_CONFIG.GEN_MON` (CORE emitters are
  tied off in stream_harness.sv — explains sched/desc) plus the monlite
  retirement, which NO register exposes (the TAP_ENABLE_* params are still
  plumbed, inert). That retirement lives once, as
  `stream_monitors.LITE_RETIRED_TYPES`; swap the datapath monitors back to the
  full monitor and that frozenset is the one line to update. Retired tuples
  are dropped from the CAM so a retired cone emitting again lands in
  UNEXPECTED, loudly.

Unit coverage: `bin/tests/test_monbus_legal_caps.py` (19 tests, synthetic
caps words including the measured 0x42CF/0x424F) plus the stream bin suite
235 passed. Board leg: re-run the three named campaigns on their bitstreams
and commit fresh results files — expect obs_campaign UNEXPECTED=0, matrix
perf/debug rows SKIP (summary "3/5 …; 2 skipped"), mon_coverage "tuples seen
4/4" with perf/sched/desc printed retired.

## Closure (2026-10-08) — board re-pin DONE, with one measured surprise filed forward

Board leg completed on the Genesys 2 (commit bff808b68):
build-obs (WNS +3.344 ns, 36.2% LUT) and build-mon (WNS +1.011 ns,
42.6% LUT) bitstreams from main; three campaigns re-run; fresh results
files committed (obs_board_2026-10-08.txt, mon_coverage_2026-10-08.txt).

Measured vs this record's expectations:
- mon_coverage: EXACT match — tuples seen 4/4, UNEXPECTED=0, all four
  retired lines (perf/sched/desc) printed.
- host-obs-matrix: 4/5 with 2 skipped (perf/debug SKIP — expected); the
  record predicted 3/5 because the error row was not expected to key —
  it keyed 13,140 (same as Oct-3) and reported OK, so 4/5.
- obs_campaign: UNEXPECTED=78,560, exit 1 — NOT the expected 0. The
  Oct-3 "threshold packets" attribution predates the first-event readout;
  root cause measured today (board A/B isolation, evidence in the
  results-file footer and /tmp/bug019_board.log): arming the
  caps-promised ERROR cone makes the monlite shared output queue drop
  ~90% of completion events, which are then honestly reported as
  monitor-lite AXI_ERR_EVENT_DROPPED packets (type 0, event 0x0E) — and
  the campaign's new hard-fail wiring (confirmed live) does its job.
  Masking the error TYPE while keeping ERROR_EN armed: 0 drops.

The DONE-WHEN criteria hold: all three campaigns derive expected classes
from live state (OBS_CAPS0 / GEN_MON / LITE_RETIRED_TYPES), no criterion
depends on a retired cone, and the results files carry the 2026-10-08
expectations. The exposed monlite queue behavior is a DIFFERENT defect,
filed as BUG-020; campaign-side disposition (key 0x0E drop-reports or
leave the error cone unarmed without stimulus) rides with it.
