# BUG-017: the in-core monbus group filtered every packet with DAXMON's registers (the "order-dependent addr_error" of amba BUG-036)

**Status:** CLOSED 2026-09-28 (fix at 201babbb5; Sean: STREAM is complete). Was: FIXED 2026-09-28 in `rtl/top/stream_top_ch8.sv`; regression in progress (see below). Filed
and fixed from the amba BUG-036 hunt; that entry closes against this one.
**Priority:** P2 -- the monitor campaign's ERROR class read as order-dependent for three weeks,
and any scenario that programs DAXMON differently from RDMON/WRMON loses packets at the group.

## Root cause

`monbus_axil4_axil4_group` filters by the packet's PROTOCOL field and has three
configuration slots (AXI, AXIS, CORE). Since `916115f12b` (2026-07-02) STREAM's
top wired the AXI slot from DAXMON's registers and parked RDMON's and WRMON's
register sets on the AXIS and CORE slots under a "protocol reuse" comment. No
monitor -- full or lite, then or now -- tags anything but PROTOCOL_AXI, so the
AXIS and CORE slots never see a packet and DAXMON_PKT_MASK (plus DAXMON's
event masks and ERR_SELECT) silently governed EVERY in-core packet at the
group. RDMON's and WRMON's masks worked only inside their own monitors.

The host program's `addr_error` scenario switches DAXMON off with a drop-all
mask (`MonitorProgram(monitors=DATAPATH_MONITORS)`), so its ADDR_RANGE errors
died at the group. Earlier host programs left DAXMON's mask at whatever the
previous scenario wrote, which is where "works first after programming, zero
after perf" came from: the state that survived was a REGISTER the next
scenario never rewrote, not reset-domain state -- and the 2026-09-08 cosim
that "proved registers are cleared by SOFT_RESET" was right, which is why the
hunt moved on to reset fanout and never came back to the mask wiring.

## How it was found

`cocotb_test_scenario_order` in `Genesys2/stream/build-mon/dv/tests/test_stream_mon.py`
runs the board's own `host_mon_matrix.run_scenario` through the cosim
`CharacterizationRunner` (basic, addr_error, perf, addr_error) and reads the
datapath CSRs back after each: after addr_error, RDMON/WRMON `ENABLE=0x3
PKT_MASK=0xfffe ADDR_RANGE_CTRL=0x54 RANGE2=FFFFFFF0..FFFFFFFF` -- armed
correctly -- yet ZERO in-core monbus handshakes, while `basic` (all three
monitors on) put 210 records in the tally. The TB's own miss-mode test
(`TEST_MISS=1`, all three masks open) emits 8/8 ADDR_RANGE errors on the same
RTL. Register readback plus the group's source (`pkt_drop =
cfg_axi_pkt_mask[pkt_type]` with `cfg_axi_pkt_mask` = DAXMON's) closed it.

## Fix

`stream_top_ch8.sv`: the AXI slot passes what ANY monitor allows -- drop masks
are the AND of the three monitors' masks (dropped only if all three drop),
`ERR_SELECT` is the OR. Each monitor still applies its own mask inside itself,
so per-monitor filtering is intact; the group stops being a second filter keyed
to one monitor. The AXIS and CORE slots are tied to drop-nothing (no in-core
source emits those protocols). No register changed; `MonitorProgram` needs no
change.
