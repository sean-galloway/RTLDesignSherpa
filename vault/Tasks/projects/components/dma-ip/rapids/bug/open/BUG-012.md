# BUG-012: the beats engine proofs assume away the region BUG-009 lived in, so they are vacuous for it

**Priority:** Medium -- the proofs are green and cannot fail for the defect
class they most need to cover. Worse than an absent proof, because an absent
proof does not claim anything.
**Status:** open, filed 2026-10-01 out of rapids BUG-011.
**Owner:** TBD

## Mechanism

Both harnesses constrain the transfer-size config to a small range:

    formal_axi_read_engine_beats.sv:147
      // Constrain cfg_axi_rd_xfer_beats to valid range (1..15 for tractability)
      assume (cfg_axi_rd_xfer_beats >= 1 && cfg_axi_rd_xfer_beats <= 15);

    formal_axi_write_engine_beats.sv:160
      assume (cfg_axi_wr_xfer_beats >= 1 && cfg_axi_wr_xfer_beats <= 15);

rapids BUG-009 was a 256-beat burst (AxLEN 255) wrapping its size to 0. The fix
clamps through `XFER_MAX = (SD_BEATS < 256 ? SD_BEATS - 1 : 254)`, which can
only engage when the config exceeds 15. So under these assumptions the clamped
and unclamped engines are the SAME DESIGN, and no property over them can
distinguish the two.

## Measured, not argued

The same `.sby` and the same properties, run against both flats:

| Flat | Result |
|---|---|
| regenerated (clamped, post-BUG-009) | PASS |
| `HEAD` version (unclamped, pre-BUG-009) | **PASS** |

A proof that passes identically on the buggy and the fixed design is not
evidence about the fix. (Method: recover the old flat with `git show`, run
`sby -f <mod>.sby prove` in a COPY of the proof dir.)

## What correct looks like

- a property that fails on the unclamped flat and passes on the clamped one --
  the old flat is a ready-made mutant, so the mutation check is already set up;
- the natural candidates are the invariants BUG-009 violated: the issued AxLEN
  never exceeds the SRAM-derived maximum, and a non-zero beat count never
  produces a zero-length transfer;
- the `<= 15` assume has to move for either to be reachable. "For tractability"
  is an honest reason, so the trade is real: BMC depth 25 with a wider config
  range may not close. Options are a wider assume with a shallower depth, a
  targeted property with the config pinned near the boundary (e.g. exactly
  `XFER_MAX`, `XFER_MAX + 1`), or an induction-mode task.

## The general shape

Twice in one day in this area a green result turned out not to constrain
anything: rapids BUG-010 (a checker that could not tell a reported drop from a
lost packet) and this one. An assume that narrows for tractability is the
standard way a formal proof quietly stops covering what it names -- and unlike
a stale flat, nothing about it looks wrong from outside. Any `assume` added
"for tractability" should name what it excludes, because that is the coverage
the proof no longer has.
