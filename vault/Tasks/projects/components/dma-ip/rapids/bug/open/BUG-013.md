# BUG-013: no data-path AXI monitor, so a response error emits no monbus packet -- and WRMON/RDMON configure nothing

**Priority:** Medium -- the DUT handles a response error correctly (the sticky
per-channel flag and channel-reset recovery are proven on silicon, rapids
TASK-020). What is missing is TELEMETRY: nothing reports the error on monbus, so
a system integrator watching the monbus stream cannot see it happen.
**Status:** open, filed 2026-10-01 while finishing rapids TASK-020.
**Owner:** TBD

## Measured, on hardware

With the `mon` bitstream (`USE_AXI_MONITORS=1 GEN_MON=1 MON_CAPTURE=1`), the
monitors enabled, the scheduler's ERR_EN on and every packet class unmasked, an
injected SLVERR on the sink's write master produces:

| | |
|---|---:|
| words captured | 6 |
| records decoded | 2 |
| **Error-class packets** | **0** |
| what WAS captured | `PROTOCOL_AXIS/PktTypeChannel/0x05/ch1`, `.../ch0` |

The source half captured 0 words. So the capture path works -- it returns the
AXIS monlites' channel events from the same window -- and there is simply no
error packet to find.

## Mechanism

The byte tree's only AXI monitor is `u_desc_axi_monitor` (an `axi_monitor_lite`
at `macro/scheduler_group_array.sv:947`, gated `USE_MONITOR(USE_AXI_MONITORS==1)`),
and it watches the DESCRIPTOR interface. The data-path masters `m_axi_rd` and
`m_axi_wr` -- the ones an injected RESP error lands on -- have no AXI monitor at
all. The stream side has `axis4_*_monlite`, which is why AXIS packets appear and
AXI ones do not.

**WRMON and RDMON configure nothing.** Their registers exist, and
`rapids_top.sv` wires 32 `reg_wrmon_*` / `reg_rdmon_*` connections per tree into
the shared config block (`u_cfg_src` / `u_cfg_snk`), but no AXI monitor in this
tree consumes the result. Writing `WRMON_ENABLE.MON_EN=1` and
`WRMON_PKT_MASK=0` reads back correctly and changes nothing observable. A host
configuring them is configuring a monitor that does not exist -- which is how
this was mistaken for a host-side problem for several runs.

## What correct looks like

Either of these, and it is a design decision rather than a test fix:

- an `axi_monitor_lite` on each data-path master (the cost is measured: the
  observers variant is +21,970 LUTs, the in-core monitors +5,764 -- see the
  byte perf report section 8.2), or
- route the engines' existing per-channel error flags into the monbus stream as
  a CORE Error packet, which is cheaper and is what the scheduler's packet
  format already has room for (`scheduler.sv:1065` documents
  PktTypeCompletion / PktTypeError).

Whichever is chosen, the WRMON/RDMON registers should either gain a consumer or
be removed. A register that reads back its own write while driving nothing is
worse than an absent one.

## Not a blocker for the error path itself

rapids TASK-020 proved on silicon that the DUT DETECTS and RECOVERS from an
injected SLVERR on both halves: the sticky per-channel flag raises on the
targeted channel only, `CHANNEL_RESET` clears it, and the channel is golden
afterwards. This bug is about reporting it on monbus, not about handling it.

## Infrastructure is already in place to verify a fix

The monbus capture buffer added for TASK-020 (`MON_CAPTURE=1`, `MONCAP_*` CSRs,
host readout through the shared `TBClasses.monbus` decoder) works on hardware
and is proven: 18 words / 6 records captured and decoded in a directed run. The
moment a data-path monitor exists, the `axi_resp_error` sequence's skip becomes
an assertion -- the check is written and currently records the gap by name.
