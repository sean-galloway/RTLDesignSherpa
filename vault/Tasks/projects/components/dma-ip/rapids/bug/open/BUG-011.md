# BUG-011: two rapids formal proofs check pre-BUG-009 RTL -- their sv2v flat files were never regenerated

**Priority:** Medium -- the proofs pass, which is the problem: they are passing
against RTL that no longer exists. The engine fixes they would most want to
check are the ones missing from them.
**Status:** open, filed 2026-10-01 while answering "what is next for rapids".
**Owner:** TBD

## Mechanism

`formal/rapids/<mod>/` proves a `<mod>_flat.v` produced by sv2v from the
SystemVerilog source. The flat is a COMMITTED SNAPSHOT, so a source change with
no re-flatten leaves the proof checking the old design, silently and green.

Two are stale. Both are the engines rapids BUG-009 fixed in `37455c992`
(2026-09-29, "a 256-beat burst wrapped to 0 beats, and two ingress defects
under it"):

| Proof | Flat vs regenerated |
|---|---|
| `axi_read_engine_beats` | **10 changed lines** |
| `axi_write_engine_beats` | **12 changed lines** |
| the other 9 dirs | identical |

So the AxLEN-255 wrap fix, the partial-allocation fix and the stale-view
allocation race fix are all absent from the proofs of those two engines.

Timing worth noting: rapids TASK-016 ("re-prove the rapids and stream formal
suites after the engine fixes") closed on 2026-09-29, the same day BUG-009's
engine fixes landed. The proofs went stale immediately after the task that
existed to make them current closed -- the same shape as the stale regression
counts found in the rapids TASK-019 close-out: evidence recorded just before
the last change, and then trusted.

## How it was measured, and why the cheap check is not enough

A date comparison (last commit touching the flat vs the source) reports FOUR
stale: the two above plus `alloc_ctrl_beats` and `latency_bridge_beats`. Those
two are FALSE POSITIVES -- their sources moved only in `794c29b8f`, the
`dmas/` -> `dma-ip/` directory rename, which changed no logic.

The decisive check is regenerate-and-diff: re-run each dir's own flatten recipe
to a TEMP path and diff against the committed flat. That is what produced the
table above, and it cleared both rename-only cases. Two notes for whoever
repeats it:

- `descriptor_engine_beats` post-processes its flat with `patch_flat.py`, which
  writes the final filename directly, so retargeting the sv2v redirect is not
  enough -- run it in a COPY of the dir, with `REPO_ROOT` passed explicitly
  (its Makefile derives REPO_ROOT from `git rev-parse`, which fails outside the
  repo and silently yields `/projects/...` paths).
- `axi_write_engine_beats` has a `sed`/`.sv2v_prep` preparation step before
  sv2v; running only the sv2v line produces an empty file that looks like a
  tooling failure.

## Result (2026-10-01)

Both flats regenerated; the diffs are exactly BUG-009's AxLEN clamp
(`XFER_MAX = (SD_BEATS < 256 ? SD_BEATS - 1 : 254)` and `cfg_axi_*_xfer_beats`
routed through the clamped `w_xfer_cfg`), 10 and 12 lines, matching the audit.
So the staleness was material, not cosmetic: the proofs had been checking
engines without the fix.

Both proofs then PASS -- `axi_read_engine_beats` in 1 s, `axi_write_engine_beats`
in 46 s. No property had encoded the old behaviour.

**But the pass means less than it appears, and that is a second defect:
rapids BUG-012.** The same proofs were re-run against the OLD unclamped flats
recovered from `HEAD`, and those PASS TOO. The properties cannot tell the two
designs apart, because both harnesses assume the defect region away:

    assume (cfg_axi_rd_xfer_beats >= 1 && cfg_axi_rd_xfer_beats <= 15);  // "for tractability"

BUG-009 was a 256-beat burst; the clamp only engages above 15. Under the
harness's own assumption the clamped and unclamped designs are identical, so
the proofs are vacuous with respect to the bug they would most want to catch.
Filed separately as BUG-012 so this item can close on the staleness it is about.
