# BUG-009: a 256-beat burst (AxLEN 255) wraps its size to 0 and poisons the channel's SRAM bookkeeping

**Priority:** Medium -- a legal register value (AWLEN 255 is inside the field's
range) deadlocks a channel with no error, no timeout escalation and no monitor
packet, and the damage outlives the run: every later run on the channel wedges
until the bitstream is reprogrammed. A host that never programs 256-beat
bursts never sees it.
**Status:** CLOSED 2026-09-29. Three mechanisms, each root-caused on the
Genesys 2 with an ILA (`capture_ila_bug009.tcl`) and each fixed: the burst
clamped to the buffer in both engines; the sink ingress allocating the
remainder when less than a segment is free; and that allocation settling
three cycles (with `s_axis_tready` gated by `fill_ready`) so it never runs
against a stale space view. Proven by unit and macro cells that fail on the
old lines, three gate/func regressions, and on build 3 (WNS +0.286 ns) the
board replay of the exact run history that wedged builds 1 and 2, every
short-run/full-burst sequence, the 36-row knob sweep and the 180-row matrix
(no cell moved more than 0.5 pt from v2.0). Was: OPEN 2026-09-29, found on
the 2026-09-28 build 2 (`SRAM_DEPTH = 256`) while measuring the
single-channel window knobs.

## What happens

`run_characterization.py --suite --suite-channels 1 --suite-beats 4096
--suite-xfer 7,15,31,63,127,255 --suite-delay 0,256,512`: every row with
`WR_XFER_BEATS = 255` (256-beat bursts) fails the same way, at every latency
and on both the 256-deep and the 128-deep build:

- SINK AXIS-in meter: `prod = 256`, then backpressure for the rest of the
  window; SINK AXI4-wr meter: `prod = 0`, no AW ever issued.
- SOURCE with `RD_XFER_BEATS = 255`: 4103 R beats for a 4096-beat descriptor
  and a golden mismatch -- the read engine over-fetched past its buffer.

And then the aftermath, which is what made the bug look like "a burst equal to
the SRAM depth": after one AxLEN 255 run, later runs on that channel with
bursts of 120 beats and up accepted one buffer of ingress and never issued an
AW (`sin prod = 128..132, wr prod = 0`); 112-beat bursts and below still ran.
`CHANNEL_RESET` before every run did not clear it; reprogramming did. Today's
sequence on the 4 KB observers build, from a clean program: x255 (sink CRC
passes, source fails) -> x127 wedges (132 accepted, 0 AW) -> x111, x7, x127
all accept 0 beats -> reprogram -> x127 passes at 84 %. Before the x255 run,
x127 passed on the same bitstream (sink-only, both halves, and the exact
suite replay), so the 128-beat rows in the 2026-09-29 threshold sweep were
the poisoned aftermath, not a second mechanism.

## Root cause (ILA, no-observers build, `trace_A_x255.csv` / `trace_B_x127_after_x255.csv`)

`axi_write_engine_beats.sv` gated the AW with

```
w_has_data[i] = (SCW'(w_effective_avail[i]) >= SCW'(w_transfer_size[i] + 8'd1));
```

`w_transfer_size` is the AWLEN; the `+ 8'd1` is evaluated in 8 bits BEFORE the
`SCW'()` cast, so AWLEN 255 makes it 0 and the gate passes on `avail >= 0`.
The trace shows the AW firing at `w_effective_avail = 48` with
`w_transfer_size = 255`. The same 8-bit sum feeds `axi_wr_drain_size`
(`m_axi_awlen + 8'd1`, an 8-bit port), so `drain_ctrl` reserved 0 beats while
the W phase pulled 256, and `sram_controller_unit`'s drain count went wrong for
good: at the end of the run `drain_data_available = 0` with 50 beats in the
FIFO, and in the next run it never left 0 while the FIFO filled to 124 + 4 in
the bridge and `s_axis_tready` dropped -- the wedge. `sram_controller` is on
`rst_n` only, which is why `CHANNEL_RESET` could not clear it.

`axi_read_engine_beats.sv` has the mirror image: `w_space_ok` with the same
8-bit sum (passes on any free count) and `r_alloc_size <= w_transfer_size +
8'd1` (allocates 0), hence the over-fetch.

STREAM's `axi_write_engine.sv` / `axi_read_engine.sv` carry the identical
lines: stream BUG-018, filed for Sean's scope call, not touched.

## Second mechanism: a partial segment makes the full-depth burst impossible (ILA, fixed-RTL build, `trace_C_x127_after_4b.csv`)

With the clamp in, the poisoning sequence, smoke and every single run passed
on the fixed bitstream -- and the 18-config knob sweep still wedged its
128-beat rows, because the board script had run a 4-beat smoke before it.
Bisected on the board: ANY run whose beat count is not a multiple of the
allocation segment (4 or 20 beats; 16 and 128 are clean) is followed by a
wedge of a 128-beat-burst run; 112-beat bursts still ran.

The sink ingress (`snk_data_path_axis_beats.sv`, rapids-only) allocates SRAM
in `cfg_alloc_size` segments (16) and only when a whole segment is free. A
packet that ends mid-segment leaves the rest of its segment allocated
(`r_pending_alloc = 12`, `alloc_space_free = 116`); the next packet consumes
those 12 beats first, then allocates 7 more segments, and stops with
`alloc_space_free = 4 < 16`: 124 beats in the channel, the last 4 slots of
the buffer unreachable until something drains, and the write engine waiting
for `avail >= 128`. A deadlock for any burst longer than
`depth - (segment - 1)` = 113 beats. Fixed in the ingress: when less than a
segment is free it allocates the remainder (`fill_alloc_size = min(segment,
space_free)`), so the buffer can always be filled to the top and a burst up to
the depth is always satisfiable. STREAM has no AXIS ingress of this shape.

Regression: `test_residue_full_burst` in
`dv/tests/macro_beats/test_snk_data_path_axis_test_beats.py` (8 ch, 256-bit,
128 deep per channel, every level): a 4-beat transfer, then 32 buffers'
worth with the burst set to the depth. FAIL on the old ingress (the second
transfer never lands), PASS on the fix.

## Third: the partial allocation raced the space view (ILA, `trace_E_history_last_burst.csv`)

With the partial allocation in, the same board history (six 4096-beat runs,
a 4-beat run, then 128-beat bursts) still wedged -- now at the LAST burst:
4096 accepted, 3968 written. The trace shows why: `fill_space_free` reaches
the ingress three cycles after an allocation handshakes. A whole-segment
allocation keeps `r_pending_alloc` above zero for longer than that, so the
stale view was never consulted; a partial allocation of one or two beats is
consumed before the view moves, and the next allocation was made against the
old count. `alloc_ctrl`'s count ran past the depth, its 8-bit `space_free`
wrapped (255 with the FIFO full at 128 and 4 in the bridge, `drain_data_available`
cycling 20..132), the ingress kept allocating 16 at a time, and on every
allocation cycle with the FIFO full a beat was accepted from AXIS and dropped
(`s_axis_tready` did not include `fill_ready` on allocation cycles): 30 beats
lost in that run, hence 98 present for 128 accounted and no last AW.

Two more ingress changes: a per-channel three-cycle settle after every
allocation (`r_alloc_settle`) so no allocation is made against a stale view,
and `s_axis_tready` gated by `fill_ready` on allocation cycles too, so a beat
is never taken that the FIFO cannot store. The race did not reproduce in the
macro test (the write slave's drain rhythm never lands a partial allocation on
a stale view, back-to-back AXIS or not); the board replay of that history on
the third build is the evidence.

## The fix (both engines)

A burst can never be larger than the buffer that stages it, so the configured
AxLEN is clamped in the engine:

```
localparam int SD_BEATS = 1 << (SCW - 1);                          // buffer depth SEG_COUNT_WIDTH encodes
localparam int XFER_MAX = (SD_BEATS < 256) ? SD_BEATS - 1 : 254;   // AxLEN cap
assign w_xfer_cfg = (cfg_axi_wr_xfer_beats > 8'(XFER_MAX)) ? 8'(XFER_MAX) : cfg_axi_wr_xfer_beats;
```

and every transfer-size decision reads `w_xfer_cfg`. On the 128-deep Genesys 2
build AxLEN 255 runs as 128-beat bursts; on a 512-deep build as 255-beat
bursts (the single 256-beat value is given up so every count fits the 8-bit
size ports shared with `sram_controller`). With the burst bounded by the
buffer the `+ 1` can no longer wrap, `has_data` / `space_ok` can always be
satisfied, and the wedge is impossible by construction rather than escalated.
The register description (`AXI_XFER_CONFIG.{RD,WR}_XFER_BEATS`, regenerated
through `bin/peakrdl_generate.py`) and the MAS engine chapters state the cap;
`run_characterization.py` flags a request above the cap and records
`xfer_axlen_effective` in every results row.

## Evidence

- `test_axi_write_engine_beats[...-cap-4-256-1-255-default]` and
  `test_axi_read_engine_beats[...-cap-...]` (`SEG_COUNT_WIDTH = 8`, AxLEN 255,
  every level): FAIL on the old lines (`len 255 > cap 127`, AW reserving 256
  beats with fewer unreserved / AR allocating 256 with 128 free), PASS on the
  clamp with every AW/AR at 127 and the transfers complete.
- Board, fixed 4 KB observers build, from a clean program: the poisoning
  sequence above (x255 -> x127 -> x111 -> x7 -> x127) -- see the campaign
  note in report v2.2 section 7.7.
