# BUG-005: the write engine runs two AWs per channel at PIPELINE=0

**Priority:** High -- the PIPELINE=0 contract (one burst outstanding per channel)
is what the sink data path and the harness are built and characterized on.
**Status:** CLOSED 2026-09-27 (closing note at the end); was OPEN 2026-09-27. Found by the write engine's first direct test
(`dv/tests/fub_beats/test_axi_write_engine_beats.py`, rapids TASK-010 part B),
the day after the read-engine twin (BUG-004).

## Symptom

`test_axi_write_engine_beats` `single` at GATE, seed 7:

```
AW #2 ch0: ch0 already has 1 burst(s) outstanding (limit 1)
AW #3 ch0: ch0 already has 1 burst(s) outstanding (limit 1)
AW #4 ch0: ch0 already has 1 burst(s) outstanding (limit 1)
```

Every AW after the first issued while the previous one had no B yet. Data and
addresses were right (the `w_pending_drain` pipeline keeps the W data honest),
which is why the data-path and board runs never saw it.

## Mechanism

Same shape as BUG-004's second form. `r_arb_request` is a cycle stale, and the
AW load (`r_aw_valid <= 1` on `w_arb_grant_valid && sched_wr_valid[grant]`) and
the stale-grant release both keyed on `sched_wr_valid` alone. With one channel
eligible the round-robin re-granted it the cycle after its AW; the live
`w_no_outstanding` term was never consulted, so a second AW issued at
PIPELINE=0. `r_outstanding_limit` is a single bit there, so the first B cleared
it while the second burst was still open, and the channel settled at two in
flight for the rest of the transfer.

## Fix

`axi_write_engine_beats.sv`: the AW load and `w_stale_grant` key on the live
`w_arb_request[grant]` (scheduler valid, data net of in-flight drains, below the
outstanding limit). No new pipeline is needed: the data side already had one.
STREAM's `axi_write_engine.sv` is the same file modulo the header -- stream
BUG-013.

## Verification

See the closing note.
