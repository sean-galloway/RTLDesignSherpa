# BUG-010: top_beats axis_mon counts only completions, so a REPORTED dropped monitor event reads as a lost packet

**Priority:** Medium -- the test is wrong, not the design, but it fails the
`top_beats` full suite on some seeds and so blocks any close-out that requires
that suite green (it blocked rapids TASK-019's sign-off on 2026-09-30).
**Status:** CLOSED 2026-10-01 (fix and proof below); filed the same day, found by
the rapids TASK-019 close-out regression.
**Owner:** TBD

## Reproduction

```bash
source env_python
cd projects/components/dma-ip/rapids/dv/tests/top_beats
SEED=49998 REG_LEVEL=FULL pytest test_rapids_beats_top.py -k 'axis_mon and full'
```

Deterministic on SEED=49998 (13.85 s against a warm build). It PASSES on other
seeds -- an isolated re-run of the same cell at a fresh seed gave 32/32 -- which
is why the earlier TASK-019 record shows `top_beats 36/0`. That green was a
luckier seed, not a different design.

Failure text:

```
source-egress AXIS monitor (agent 0x0A): completion beat counts [1 x 31],
expected [1 x 32] (records for it: 32)
```

## Mechanism

Nothing is lost by the DUT, and nothing is lost by the monitor silently:

| Evidence | Value |
|---|---|
| source-egress monitor-lite's own counters | `packet_count=32 error_count=0 dropped_count=0` |
| records captured for agent 0x0A | **32** |
| of those, AXIS Completion | **31** |
| the 32nd record | `type=PktTypeError evt=0x0E ch=0 data=0x1` |

`0x0E` is `AXIS_ERR_EVENT_DROPPED` -- `monbus_types.py`: "monitor-lite: events
lost to monbus backpressure (data = count)". So the egress monitor decided 32
completion events, monbus backpressure cost it one, and it REPORTED that as an
error packet carrying the count. `dropped_count` reads 0 at sample time because
the RTL port is documented "events lost to a full queue or a lost pick,
**since the last report**" -- it had already reported and cleared. (Which of
those two mechanisms fired is measured below; the enum's "monbus backpressure"
wording is the cause of the full queue, not a second mechanism.)

So the trace is self-consistent and complete: 31 completions + "I dropped 1" =
32 events accounted for, out of 32 packets moved. The test's expectation
(`cnts != sorted(want)` over completion records only, in
`rapids_beats_top_tb.py`) does not model the monitor's documented
backpressure behaviour, so a correctly-reported drop is indistinguishable from
a genuinely missing completion.

Seed dependence follows: whether backpressure bites hard enough to cost an
event depends on traffic timing.

## What correct looks like

The check should account for reported drops rather than demanding an exact
completion count -- e.g. require `len(compl) + sum(EVENT_DROPPED counts) == 32`
with the beat counts of the completions that did arrive still exact. That keeps
the test able to catch a real loss (which would show as a shortfall with NO
drop report) while tolerating the design's documented behaviour.

Worth deciding at the same time: whether an event should be lost at all at this
traffic rate. See "Where the drop actually happens" below for the measurement --
the stage to size is the monitor-lite's own `OUT_DEPTH` queue, NOT the SRAM
capture path (which already has compression) and not the tally path (which
cannot drop).

## Diagnostic gap found on the way

`rapids_beats_top_tb.py` logs an "other record: ..." line only for agents it is
NOT tracking, so a non-completion record from a TRACKED agent is invisible in
the output. That is why the failure reads like a lost packet: the error packet
sitting in the trace is never printed. Printing every record for the tracked
agents (a temporary diagnostic was enough to find this in one run) would have
made the cause obvious from the regression log alone.

## Not caused by the byte-RAPIDS work

None of the blocks touched for rapids TASK-020 (`axi4_slave_wr_crc_check`,
`axi4_slave_rd_pattern_gen`, `axi4_dma_slaves`) are in `rapids_beats_top`'s
compile closure (69 sources, zero matches), and this is a cocotb test of the
beats top that never instantiates the FPGA harness.

## Fix (2026-10-01)

The accounting moved into the shared monbus package rather than being written
three times -- `bin/TBClasses/monbus/monbus_validators.py`, exported from
`TBClasses.monbus`:

- `axis_completion_accounting(records)` -> `(completions, dropped_event_count)`,
  reading the drop count out of the AXIS_ERR_EVENT_DROPPED reports;
- `axis_completions_consistent(arrived, want, dropped)` -> exact equality when
  nothing was dropped; otherwise every arrived beat count must still be an
  expected one (multiset, so a WRONG count is still caught) and the arithmetic
  must close, `arrived + dropped == expected`.

All three rapids TBs carried the same flawed check and all three now call it:
`rapids_beats_top_tb.py`, `rapids_core_beats_tb.py`, `rapids_core_tb.py`. The
two core TBs had a second symptom -- their "N unexpected packets" list counted
the drop report as well, so one reported drop produced two complaints; drop
reports are excluded there now. The log line gained ", N event(s) dropped and
reported", which is the diagnostic whose absence made this hard to read.

## Proof it is not merely silenced

A test fix that only stops a failure is worth nothing, so the fix was checked
in both directions:

| Check | Result |
|---|---|
| `SEED=49998` (the failing seed) with the fix | 3 passed, 13.6 s; log reads `32 records, 31 completion [...], 1 event(s) dropped and reported` |
| **Mutation: `w_drop_rpt = 1'b0` in `axis_monitor_lite.sv`** -- the event is still dropped but NEVER reported, i.e. a genuine silent loss | **FAILS**: `completion beat counts [1 x 31], expected [1 x 32] (records for it: 31, monitor reported 0 dropped event(s))` |
| the mutated shared monitor afterwards | restored, `cmp` clean, `git status` clean |
| helper truth table (exact / genuine loss / reported drop / wrong beat count / over-report) | 5 of 5 as intended |
| `bin/TBClasses/monbus/tests/` after the package change | 55 passed |
| `top` and `top_beats`, full, from `clean-all` | **42/0** and **36/0** |

The mutation is the load-bearing one: with drops reported the test passes, with
a drop hidden it fails. That is exactly the distinction the original check could
not make.

## Where the drop actually happens (measured, 2026-10-01)

An earlier draft of this note said "monbus backpressure" and pointed at the
monbus group's depth. That named the wrong stage, and Sean caught it: the SRAM
capture path already has compression to make drops less likely, and the tally
block exists so that counts cannot be dropped at all.

Neither of those is where this drop occurred. The reporter is the monitor-lite
itself, one stage UPSTREAM of the group:

- `rtl/amba/monitor/axis_monitor_lite.sv`, whose `dropped_count` port reads
  "events lost to **a full queue or a lost pick**, since the last report";
- `w_lost = w_ev_n - w_take1 - w_take2`: the lite can enqueue at most TWO
  events per cycle (write slots `wp` and `wp+1`) into an `OUT_DEPTH`-entry
  output queue, and counts everything it could not place;
- the instance that dropped is `u_axis_egress_mon` in `rapids_src_beats.sv`,
  built **`OUT_DEPTH(4)`**.

Those are two different mechanisms with two different fixes, so they were
separated by experiment rather than by argument: `OUT_DEPTH` 4 -> 16 on that
instance alone, same SEED=49998, nothing else changed.

| Build | Result |
|---|---|
| `OUT_DEPTH(4)` (as shipped) | 32 records, **31** completion + 1 dropped-event report |
| `OUT_DEPTH(16)` (probe, reverted; `cmp` clean) | 32 records, **32** completion, no drop report |

So it is **queue-full, not a lost pick**: the 4-entry queue backs up while
`monbus_ready` is low, and the event with nowhere to go is counted. Drain rate
and queue depth are both live knobs; the 2-per-cycle enqueue limit is not
implicated.

That also means the compression already in this path is pulling in the right
direction -- `monbus_compressor.sv` IS in `rapids_beats_top`'s closure, with the
arbiter, CAM, group core and halfbeat packer -- it just cannot protect a
4-entry queue sitting in front of the group. The tally block is **not** in this
closure at all (zero tally sources among its 69 files), so the no-drop
guarantee it provides does not cover this path.

## Not done here

Whether to raise this instance's `OUT_DEPTH`, improve the group's service rate
for that agent, or extend the tally approach to this path is a design decision,
left open deliberately. The drop is legal and reported, so nothing is broken --
but a 32-packet transfer losing a telemetry event is a sizing data point, and
the probe above says depth alone would remove it.
