# BUG-001 — miss_fill_macro func cell: 3-check divergence at one lockstep transaction

**Filed:** 2026-10-14
**Observed in:** `make run-all-full-parallel` on the amber unit area
(48 workers), second clean run of the day (post parity-`full` fix).
**Cell:** `test_amber_miss_fill_macro.py::test_amber_miss_fill_macro_s128w4_func`
**Reproducibility:** NOT deterministic — see below.

## Symptom

Full-random lockstep phase (2,500 transactions, 637 idle snoops, 264,883
checks) scored exactly one divergent transaction, `full[2049]`, with three
simultaneous mismatches against the scoreboard:

```
CHECK FAIL: full[2049] MISS_VICTIM entered: got False expected True
CHECK FAIL: full[2049] fill class:        got 2      expected 1
CHECK FAIL: full[2049] fill beat count:   got 0      expected 8
```

The coherent triple (no victim entry, wrong fill class, zero fill beats)
says the FSM took a different legal branch at that transaction — a real
RTL/scoreboard divergence at one corner, not a sampling glitch.

## What has been ruled out

- **Not today's reset-sync work.** The cell's DUT closure
  (`amber_miss_fill_macro_test`) is pending_fill_bypass / victim / control /
  tag / data / repl / axi4_master_rd / l1_fill — it does not include
  `amber_top`, `amber_ace_top`, or `reset_sync`. Unrelated by construction.
- **Not the per-cell seed alone.** The failing run recorded
  `SEED=1425`; two solo reruns at `SEED=1425` PASSED (2/2, ~10 s each).
- **Not a poisoned build dir** (the earlier g++-ICE failure mode): the
  failing run compiled fresh after `make clean-all`.

## Suspected mechanism

~~Load-dependent TB nondeterminism.~~ **DISPROVEN 2026-10-15** — see
"Wall-clock audit" below.

## Wall-clock audit (2026-10-15)

Audited every element of this cell's stimulus path for real-time
coupling. **No wall-clock-coupled stimulus injection exists.** The sim
is fully deterministic per cell seed:

- `amber_miss_fill_macro_tb.py` — zero `time`/`sleep`/`monotonic`
  references; the soak is inherited.
- `_full_random` (`amber_control_tb.py:1951`) — strictly sequential
  `await`s; transactions AND idle snoops both come from the seeded
  global `random`, so the snoop-vs-transaction interleave is a fixed
  function of the seed.
- `SNOOP_CODES` — a dict; `random.choice(list(dict))` is
  insertion-ordered, immune to `PYTHONHASHSEED`.
- `FlexRandomizer` (responder ready/valid delays) — draws from the
  module-level `random`, which TBBase seeds per cell; the soak also runs
  the 'fast' profile (zero jitter) anyway.
- `TBBase` — all `time.time()` use is in the safety monitors
  (observe/abort-only: a violation ABORTS the run, it cannot diverge one
  transaction and continue) and in `mark_progress` bookkeeping. No
  feedback into stimulus.
- CocoTBFramework `components/shared` + `components/axi4` — no
  `urandom`/`secrets`/`uuid`/`numpy`/per-process entropy.
- Verilator model is single-threaded ("cpu ... on 1 threads" in the
  build log) — no multithreaded scheduling nondeterminism.
- Seed plumbing checked end-to-end: the conftest fixture pins
  `SEED=seed_for(nodeid)` per cell and TBBase applies `random.seed()`
  from `SEED` env, so `SEED=1425 pytest <cell>` solo provably applies
  the same RNG state the failing grid worker had.

Forced-load reproduction, same seed as the failing run
(`SEED=1425`, `REG_LEVEL=FUNC`, WAVES off — the failing config):
**6/6 PASS** with 44 concurrent CPU hogs (load avg ~44), 14.9–16.5 s
per iter; solo control 1/1 PASS (8.6 s). The recorded seed under
extreme load reproduces nothing — load is not the trigger.

## Revised understanding / open hypotheses

Ordered by what the evidence now supports:

1. **The failing grid run's compiled binary differed.** Same source +
   same flags should give the same model, but the grid is the only
   configuration that has ever produced this divergence, and a Verilator
   model is the one artifact that is NOT bit-reproducible by
   construction under a build race or a g++ ICE retry. (The filing's
   earlier "not a poisoned build dir" ruled out STALE artifacts, not a
   raced/miscompiled fresh one.)
2. **The RTL corner no longer exists at HEAD.** The failing run
   (2026-10-14) predates the BUG-002 fix (`ab308d108`, PF_GUARD in
   l1_control/l1_fill — both inside this cell's closure). The PF_GUARD
   change alters exactly the pending-fill-vs-snoop grant interaction
   this cell soaks, so "cannot reproduce at HEAD" is confounded: the
   corner may simply be gone.
3. A genuine seed-dependent RTL corner (the original BUG-001
   s016w2_full class — deterministic there) — but then the same seed
   must fail solo, and it does not.

## Next steps (revised)

1. **On any recurrence: archive before rerunning.** Copy
   `local_sim_build/<cell>/` (the exact binary), the cell log, and
   `results_<cell>.xml` to a safe path FIRST — solo reruns overwrite
    the binary and log, which is what made the 2026-10-14 instance
   untriangulable. Then diff the archived binary against a fresh
   compile (`sha256sum` of the sim executable) to test hypothesis 1.
2. Only then rerun solo at the recorded `SEED`; if it passes while the
   archived binary fails, the build-divergence hypothesis is confirmed.
3. Until closed: treat an isolated sub-1% mismatch cluster in this cell
   under heavy parallel load as THIS bug, not as regression signal from
   whatever change was under test.
