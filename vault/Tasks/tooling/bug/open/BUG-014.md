# BUG-014: check_task_ids globs the worktree, so as a pre-commit hook it passes on a tracker state it would reject

**Priority:** P2
**Status:** open
**Owner:** TBD
**Filed:** 2026-09-30 (caught by making the mistake it fails to catch)

`bin/check_task_ids.py` reads tracker state off the filesystem --
`d.glob("*.md")` at lines 149, 181, 335 and `tasks.rglob("*.md")` at 380. In a
pre-commit hook that is the **working tree**, not the temporary index being
committed, so the two can disagree and the hook validates the wrong one.

This is [[TASK-017]]'s defect in a second gate. That task fixed exactly this for
`filelist_registry` -- "reads the toml and baselines from the worktree while the
hook's file set comes from the temporary index" -- and `check_task_ids` was never
given the same treatment.

## Reproduction, and it is not hypothetical

`git commit -- <paths>` builds a temporary index of HEAD plus **only the listed
paths**. Move a task between states with `git mv` and then name only the new path
in the pathspec:

    git mv vault/Tasks/<area>/task/open/TASK-0NN.md \
           vault/Tasks/<area>/task/closed/TASK-0NN.md
    git commit -m msg -- vault/Tasks/<area>/task/closed/TASK-0NN.md

The staged deletion is outside the pathspec, so the commit takes the addition and
leaves it behind. On disk the `open/` copy is already gone, so the hook globs a
consistent tree and prints **PASS**. The commit it just approved has the ID in two
states at once.

Done for real in `0804d45d3` on 2026-09-30, repaired in `9e1cdf6c5`. Running the
checker against that committed tree in a detached worktree:

    git worktree add --detach /tmp/wt 0804d45d3
    cd /tmp/wt && python3 bin/check_task_ids.py

    Task-tracker check FAILED (2 issue(s)):
      - tooling/task: DUPLICATE ID TASK-021 at open/TASK-021.md, closed/TASK-021.md
      - tooling/task: INDEX.md says open: 3 but open/ holds 4

**The checker has full teeth.** It caught the duplicate AND the count, which is
what makes this a targeting defect rather than a coverage gap. It was simply
pointed at a tree where the defect did not exist. A gate that passes because it
was shown the wrong tree is worse than an absent gate: it reports green over the
exact state it was written to reject.

## Why CI does not cover it

`check_task_ids` DOES run in the `Filelist checks` job on a clean checkout, which
is the right tree. But a push event only checks the **head** commit. `0804d45d3`
and its repair were pushed together, so the bad intermediate commit was never
tested -- it survived both the hook (wrong tree) and CI (never visited). Ordering
was what saved it; had the repair not happened first, `main` would have been
pushed with a lying tracker. The safety net is real but it has a hole exactly the
width of one commit.

## The state IS the directory, which is why this matters here

In this convention an item's state is its containing directory, not a field, so a
half-committed `git mv` does not produce a stale label -- it produces an item that
is genuinely open and closed simultaneously, and the counts every INDEX carries go
wrong with it. There is no field to reconcile it against.

## Fix

Follow TASK-017's pattern rather than inventing one. When running under a hook
(`GIT_INDEX_FILE` set, or invoked with file arguments), enumerate tracker files
from the index being committed -- `git ls-files --cached` against that index --
instead of globbing the directories. Outside a hook, keep globbing the worktree:
that is correct for an interactive run and for CI.

Worth considering alongside: a hook cannot see intermediate commits of a push at
all, so the durable guard for the multi-commit case is a CI step that checks every
commit in the push range, not just the head.

## Acceptance

- A test that FAILS before the fix: stage a `git mv` of a task, commit only the
  new path, and assert the hook rejects it. `bin/tests/test_check_task_ids.py`
  already has the planted-defect pattern (5 teeth tests) to extend.
- Interactive and CI behaviour unchanged -- verified by the existing teeth tests
  still passing.
- The duplicate-ID and count checks specifically demonstrated firing from hook
  context, since those are the two that reported PASS on `0804d45d3`.
