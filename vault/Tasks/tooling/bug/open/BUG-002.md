# BUG-002: --blindspots enumerates filelists from the INDEX but resolves them from DISK

**Priority:** P2. Spuriously blocks commits and presents as a gate that
disagrees with itself, which costs far more time than the finding is worth.
Nothing is corrupted.

**Where.** `bin/filelist_registry.py`, two lines apart in the same subtraction:

```python
# line 712 -- the NUMERATOR, read from the INDEX
tracked = subprocess.run(["git", "ls-files", "*.f"], cwd=REPO_ROOT, ...)

# line 349 -- the DENOMINATOR, read from DISK
out.extend(p for p in sorted((REPO_ROOT / d).rglob("*.f")) ...)
```

`unregistered_filelists` is `len(orphans)`, computed by subtracting what the
registered `filelist_dirs` resolve to from what is tracked. One side reads the
git index; the other reads the filesystem. Whenever those two disagree, the
difference is reported as unregistered filelists.

**Symptom, observed 2026-09-26.** A commit was rejected with
`unregistered_filelists 0 -> 3`, while `bin/filelist_registry.py --blindspots`
run standalone in the same tree reported PASS with no unregistered filelists.
Two invocations of the same command, opposite verdicts. It blocked commits
across three sessions for roughly an hour, and the first two explanations
offered for it -- mine ("the hook reads the working tree") and the committer's
("staging") -- were both wrong.

**Mechanism.** `git commit -- <paths>` does not commit the real index. It builds
a TEMPORARY index from HEAD plus only the pathspec'd files, and exports it to
hooks via `GIT_INDEX_FILE`. A rename needs BOTH halves named in the pathspec; if
only the new paths are given, that temporary index still carries HEAD's old
paths. So inside the hook:

- `git ls-files "*.f"` saw 6 filelists (3 old HEAD-side + 3 new)
- the registered `filelist_dirs` resolved 3 on disk
- 6 - 3 = 3 orphans

Committing with all 219 paths (118 new + 101 HEAD-side halves) made both sides
describe the same set, and the gate returned rc=0.

**Why it does not reproduce standalone.** Outside a hook `GIT_INDEX_FILE` is
unset, so `git ls-files` reads the real index, which was self-consistent. The
divergent tree exists only for the duration of the hook and cannot be inspected
afterwards.

**Expected behaviour.** Both halves of one subtraction must read the SAME tree.
Either enumerate and resolve through `git ls-files`, or do both from disk. The
index side is preferable because tracked-only is deliberate -- the comment at
line 710 records that a bare `rglob("*.f")` also matches Fortran sources under
`venv/`.

**Repro:** stage a directory rename containing `.f` files, then
`git commit -- <only the new paths>`. The hook reports
`unregistered_filelists 0 -> N` where N is the number of renamed `.f` files;
running `--blindspots` standalone immediately afterwards reports 0.

**Must not regress:** the tracked-only property (line 710's reason for
`git ls-files` over `rglob`), and the ratchet's existing anti-vacuity behaviour.

**Related.** Same defect class as the broken-link checker's default read: it
scans the working tree while CI reads committed blobs, so untracked directories
made 8 dangling links resolve locally while the gate reported PASS (fixed in
`8562bf0ad`, rule recorded in `vault/Tasks/INDEX.md`). The general hazard is a
check whose two halves are sourced from different trees.
