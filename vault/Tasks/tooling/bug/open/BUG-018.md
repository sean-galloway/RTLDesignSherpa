# BUG-018: concurrent agents on the shared trunk truncate each other's `__pycache__` bytecode — `EOFError: marshal data too short` at import

**Priority:** P2
**Status:** open — workaround documented, structural fix not chosen
**Filed:** 2026-10-09 (mem-ctrl-ip Phase 1 execution; renumbered BUG-018 after collision with closed BUG-017)
**Owner:** TBD

## Symptom

pytest collection dies with `EOFError: marshal data too short` inside
`importlib._bootstrap_external:_compile_bytecode`, importing a TB module
(e.g. `pumice_device` via `pumice_dram_configs.py`). The embedded traceback
paths may point at a *pre-move* location even though the tree has moved —
the stale path comes from the corrupt `.pyc`, not from the live tree.

## Root cause

Multiple agents run Python on the same working tree simultaneously (observed
2026-10-09: one agent in `venv/bin/python -m pytest` while another ran
`venv-cocotb2`; `ps` showed both plus a live verilator build). Python writes
`<mod>.cpython-312.pyc` non-atomically; two writers (or a writer and a
reader) on the same cache file truncate it. Import then reads the half-written
marshal stream and raises. Two pytest-version-tagged siblings
(`...-pytest-9.0.3.pyc` / `...-pytest-9.1.1.pyc`) plus the untagged
`.cpython-312.pyc` share the same `__pycache__` dir, so any pair of runs
races on the untagged file. `git grep` sees the corrupt files because the
pyc trees are untracked but present; `git mv` moves only tracked files, so
cache trees survive moves and keep serving stale bytecode.

## Evidence

- 2026-10-09 mem-ctrl-ip Phase 1: pumice `dv/tests/macro` collection failed
  with the EOFError at the pre-move path (job 1) and at the post-rename path
  (job 2), with caches purged between runs.
- Concurrent writer confirmed live via `ps` (PID 1198336,
  `venv/bin/python -m pytest`, plus g++/cc1plus).
- Clearing every `__pycache__` under the moved trees did NOT fix it — the
  racing writer regenerates corrupt bytecode continuously.
- Running with `PYTHONDONTWRITEBYTECODE=1` did NOT fix it — the reader still
  consumes the other writer's half-written file.

## Workaround (verified 2026-10-09)

Run with a private bytecode prefix so the shared tree's pycs are neither
read nor written:

```bash
export PYTHONPYCACHEPREFIX=/tmp/pycache-<run-name>
```

Plus `-p no:cacheprovider` for pytest's own cache. Green after adoption.

## Candidate structural fixes (choose one; do not silence the gate)

1. `env_python` exports `PYTHONPYCACHEPREFIX=$REPO_ROOT/.pycache-$USER-<pid-ish>`
   — per-shell private cache; costs a cold compile per new shell.
2. Ignore-and-purge policy: `.gitignore` already excludes `__pycache__`;
   add a trunk-etiquette note to the global AGENTS.md telling agents to set
   `PYTHONPYCACHEPREFIX` (cheapest, no code change).
3. Atomic-write cache wrapper (sitecustomize) — most robust, most machinery.

Note: this is the same failure class that masquerades as a DV regression —
do not re-diagnose moved RTL when the traceback path predates the tree.
