# BUG-013: check_port_consumers.py is blind to unpacked-array ports, so it passes the exact break it exists to catch

**Status:** open 2026-09-28  **Priority:** P2 -- the tool's own opening line is
"Adding a port to a module breaks every consumer that does not connect it", and
for one common port shape it does not notice.
**Owner:** TBD
**Found by:** pumice, 2026-09-28, the hard way: it returned CLEAN on the change
that had just failed 16 tests.

## Expected vs actual

`bin/check_port_consumers.py` should report `PINMISSING` when a module gains a
port and a consumer does not connect it. It does -- unless the new port is an
UNPACKED ARRAY, in which case it lints the consumers, sees Verilator's warning,
and filters it out.

Reproduced on `pumice_core.sv` with a dummy port, consumer
(`dv/tb/pumice_core_tb_top.sv`) deliberately not updated. Same file, same
consumer, same invocation -- only the port's shape differs:

| port declaration | result |
|---|---|
| `output logic zz_port_o` | **rc=1**, names the consumer and the missing pin |
| `output logic [31:0] zz_port_o [NUM_BANKS]` | **rc=0**, "9 consumer(s) linted", silent |

## Mechanism

`PORT_RE` (line 67) takes the last identifier before `,` `)` or end of line:

    r"^\s*(?:input|output|inout)\b[^;]*?([A-Za-z_]\w*)\s*(?:,|\)|$)"

An unpacked-array port ends in `] ,` rather than `<identifier> ,`, so the
pattern does not match the line AT ALL and the port name never enters
`port_set()`. Measured on a six-port sample:

    current    -> ['clk', 'last_port_i', 'plain_port_o', 'vec_port_o']
                  missing: ['array_port_o', 'two_dim_o']

Because the tool reports "only for the pins THIS CHANGE TOUCHED" (the symmetric
difference of the old and new port sets), a port it cannot see is a port it
cannot report. Verilator DOES emit the warning; the filter drops it.

## What it cost

pumice BUG-020 added `output logic [31:0] stat_row_hit_o [NUM_BANKS]` to
`pumice_page_policy` / `pumice_mem_cmd_scheduler` / `pumice_core`.
`check_port_consumers.py` was run against all three and returned rc=0. The TB
was not updated, `PINMISSING` is an error under the flags cocotb passes, and
**16 top tests failed to BUILD** -- they never simulated. The consumer was found
by grepping instantiations by hand.

That is precisely the failure in the tool's own docstring
(`math_bf16_fast_reciprocal`, 2026-09-07, five tests that never simulated), and
the third distinct gap in this tool: it previously globbed only `rtl/*` so no
component module was ever checked, and did not follow `-f` includes.

## Candidate fix (tested, not applied)

Allow trailing unpacked dimensions after the identifier:

    r"^\s*(?:input|output|inout)\b[^;]*?([A-Za-z_]\w*)\s*(?:\[[^\]]*\]\s*)*(?:,|\)|$)"

On the same six-port sample that yields all six -- `clk`, `plain_port_o`,
`vec_port_o`, `array_port_o`, `two_dim_o` (2-D unpacked), `last_port_i` -- with
nothing spurious. Not applied from the pumice lane: this is a shared gate and
the fix wants its own test.

## Done when

1. The regex (or a real declaration parse) covers unpacked-array ports.
2. A test in `bin/tests/` pins it: a module gaining an unpacked-array port with
   an unconnected consumer must make the checker FAIL. A checker whose own
   blind spot is untested is how this reached its third instance.
3. Consider asserting that every `PINMISSING` Verilator reports is either
   reported or explicitly explained -- the filter is what turned a detected
   break into a silent pass, and that shape will recur for any port form the
   regex does not model.
