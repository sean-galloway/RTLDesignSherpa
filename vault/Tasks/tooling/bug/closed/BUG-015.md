# BUG-015: the cocotb 2.x flip matrix did not cover the UART-equivalence suites

**Priority:** P3
**Status:** closed 2026-10-09 — re-run matrix executed under cocotb 2.1.0, two
real defects found and fixed, flip matrix extended to a documented two-matrix
pre-release rule. One cell (`test_rs_loop_uart_windows`) dispositioned to
tooling BUG-017, blocked on the amba lane's uncommitted
`monbus_group_core.sv` rework (concurrent-edit contamination, not a cocotb
regression).
**Owner:** TBD

## What happened

The 2026-10-08 cocotb 2.x flip (tooling TASK-025, closed owner-confirmed the
same day) removed `cocotb.external` / `cocotb.function`. Sixteen files still
used them — every silicon/sim-equivalence UART suite (rapids byte/char, stream
mon, RS and BCH loop UART, pumice ddr2 char, cdc demo). All of them failed at
startup (rapids byte sink: 190 ns in, `module 'cocotb' has no attribute
'function'`). The flip matrix that gated TASK-025 exercised val/ suites but
not these; the breakage surfaced the same day only because a utility-ip
TASK-003 board-matrix build runs verify-sim as a gate.

Fixed in 61ea5dc13 (mechanical rename to `cocotb._bridge.bridge`/`resume`;
rapids byte sink re-passed 31 s).

## Defects found and fixed by the re-run

1. **`test_stream_mon.py::cocotb_test_scenario_order` — `TypeError:
   'UARTAxiBridge' object is not callable`** (failing since 61ea5dc13).
   The rename's `from cocotb._bridge import bridge` collided with the
   test's local `runner, bridge = tb.runner, tb.bridge` (the UARTAxiBridge
   driver instance), which shadows the import at the two thread-bridge call
   sites. Fixed by aliasing the import `bridge as cbridge` (three call sites;
   the driver-arg uses of the local `bridge` are unchanged). Verified: the
   test then executed and failed one level deeper (below).
2. **Same test — `TypeError: run_scenario() missing 1 required positional
   argument: 'candidates'`** (pre-existing since 2026-10-04, cocotb-version
   independent). 471692b07's BUG-019 fix added the build-filtered `candidates`
   parameter to `host_mon_matrix.run_scenario` and updated the board
   campaigns, but not this sim mirror — the test had been dead for 5 days
   under every cocotb version. Fixed by giving the test the same contract as
   the board's `run_matrix`: `build_info(bridge)` +
   `filter_legal_by_build(CANDIDATES, binfo)`, filtered set into
   `check_capacity`, `labels`, `run_scenario`, and the per-bin error-class
   lookup. Verified: 1 passed in 13:03 (all four scenarios through the
   board's own program).
3. **`testcase=` selection under cocotb 2.x — unanchored COCOTB_TEST_FILTER**
   (surfaced during this work's verification; the amba lane's record addendum
   item 2). cocotb-test 0.3.0 passes `testcase=` to `COCOTB_TEST_FILTER`
   verbatim; cocotb 2.x matches it with `re.search` over `<module>.<test>`
   fullnames, so `testcase='monitor_soak'` also selected
   `monitor_soak_monlite` — every multi-test module ran ALL its tests in
   EVERY build (observed: the pktgen runner ran the monlite test against the
   pktgen DUT and failed on the lite-only `cmd_valid` pin). Fixed with a
   root-conftest patch in BOTH `RTLDesignSherpa/conftest.py` and
   `RTLDesignSherpa-DV-dev/conftest.py`: anchor each testcase as
   `\b<name>$` before cocotb-test hands it to the simulator, restoring 1.x
   exact-name semantics for all ~80 call sites at once (no cocotb-test fix
   released; 0.3.0 is latest). Verified: soak pktgen runner now runs exactly
   1 test (TEST=1 PASS=1). Upstream issue filed:
   https://github.com/themperek/cocotb-test/issues/285 — delete the conftest
   patches when upstream lands a fix. Upstream PR opened 2026-10-10
   (maintainer invited it in #285):
   https://github.com/themperek/cocotb-test/pull/286 — anchored exact-name
   testcase= selection with regression tests (RED-before/GREEN-after
   verified under cocotb 2.1.0/icarus).
