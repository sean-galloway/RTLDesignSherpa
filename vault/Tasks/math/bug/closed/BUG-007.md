# BUG-007: bf16_divider asserts ow_underflow on exact-zero quotient (0.0 / inf)

**Priority:** P3
**Status:** closed 2026-10-08 — fix-RTL per the BUG-006 precedent
**Owner:** TBD
**Filed:** 2026-10-08
**Refs:** rtl/math/math_bf16_divider.sv:235-243; same flag-semantics family as BUG-006 (bf16_adder)

## Reproduction

Vector: `a = 0x0000` (+0.0), `b = 0x7F80` (+inf) → 0.0 / inf.

- Result bits are CORRECT: `ow_result = 0x0000`.
- `ow_underflow = 1` — WRONG. The quotient is exactly zero; IEEE 754
  underflow requires tiny AND inexact, and this result is exact.

Observed in the 2026-10-08 cocotb-2.1.0 flip matrix (`val/math` full,
SEED=82182, vector random_978: `FAIL random_978: 0.0 / inf`, expected
flags all-false, actual `unf=1`). NOT cocotb-version-related: the logic
is combinational and deterministic; the TB's golden model already expects
`unf=False`. The vector simply had never been drawn by the area's random
sweeps (a latent coverage event, same class as BUG-004/BUG-006).

## Mechanism (rtl/math/math_bf16_divider.sv)

```
w_result_zero = (w_a_eff_zero & ~w_b_eff_zero & ~w_b_is_inf & ~w_b_is_nan)
              | w_finite_div_inf;              // both disjuncts exclude a=0, b=inf
```

For a = +0.0, b = +inf: the first disjunct is killed by `~w_b_is_inf`,
and `w_finite_div_inf` requires `~w_a_eff_zero` — so `w_result_zero = 0`.
The exponent path computes 0 − 255 + 127 < 1, so `w_exp_underflow = 1`,
and the zero-result branch emits `ow_underflow = w_exp_underflow &
~w_result_zero = 1`. The 0.0/inf case falls between the two definitions.

## Suggested fix direction

Include the exact-zero quotient in `w_result_zero` (add the
`w_a_eff_zero & w_b_is_inf` conjunct) so line 267's `~w_result_zero`
suppresses the flag, matching the module's own documented contract
("underflowed to zero" = inexact tiny flushed). Audit the sibling clauses
for the same gap (inf/0 and 0/0 are already covered by earlier branches).

## Notes

- Module is HAND-WRITTEN (not in the bin/rtl_generators/bf16 family) —
  edit the .sv directly.
- The ieee754 fp32 divider (065148c0a) is not affected: its residual-based
  flag logic keys underflow off inexactness, not the exponent compare.

## Resolution

**Fix (rtl/math/math_bf16_divider.sv):** deleted the `~w_b_is_inf` qualifier
from the first disjunct of `w_result_zero` — `w_b_is_inf` already implies
`~w_b_eff_zero`, so the removal adds exactly the zero/inf cell (all four
sign combinations, plus the FTZ subnormal-dividend form, since
`w_a_eff_zero` includes subnormals) to the exact-zero-result class. The
zero-result branch then owns 0/inf and line 267's `~w_result_zero`
suppresses the flag. Result bits unchanged (0x0000|sign, already correct).
Equivalent to the suggested `w_a_eff_zero & w_b_is_inf` conjunct; one term
smaller. Sibling-clause audit: 0/finite, finite/inf, 0/0, inf/inf,
finite/0, inf/finite, NaN all route correctly today; the overflow side is
gated by `~w_result_inf & ~w_div_by_zero` on both inf-producing clauses —
no analogous gap.

**Directed regression (bin/TBClasses/common/bf16_testing.py,
BF16DividerTB.special_values_test):** added 0/inf, 0/-inf, -0/inf,
-0/-inf, subnormal/inf. Mutation-checked per the BUG-006 precedent:
with the fix reverted all five go RED (flag leaked), with it all GREEN.
Divider suite 4/4 at FULL post-fix.

**Escape analysis (why the suite never drew it):** (1) the directed
special-values list is hand-picked — it covers zero/finite and
finite/inf but not their zero/inf corner, so the deterministic layer
never saw the cell. (2) The random layer draws specials sparsely:
a=0x0000 with p = 0.05 x 1/4, b=+/-inf with p = 0.03 x 2/3, so the
joint cell is ~2.5e-4 per draw — ~1% per normal GATE/FUNC run, ~22% per
FULL (1000-draw) run. It surfaced in a seed x cocotb-version flip matrix
(SEED=82182, random_978) — brute-force luck, not designed coverage.
(3) Structurally, the flag was an exponent compare minus an exclusion
list of exact-zero input combos; exclusion lists rot (BUG-004/006
family). The fp32 ieee754 divider is immune because its underflow keys
off inexactness (residual != 0) — nothing to enumerate.

**Prevention filed:** math TASK-006 — a shared special-value Cartesian
product grid for the bf16 TB family so a missing cell cannot recur.
