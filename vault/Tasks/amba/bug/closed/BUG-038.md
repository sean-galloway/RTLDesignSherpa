# BUG-038: axis4_slave/master tuser unpack eats low bits when ID or DEST is zero-width

**Priority:** P1 -- any `axis4_slave`/`axis4_master` instance with
`AXIS_USER_WIDTH > 0` and `AXIS_ID_WIDTH == 0` or `AXIS_DEST_WIDTH == 0`
silently shifted its tuser field right; data/strb/last were unaffected, so
the corruption was invisible to every consumer that does not carry meaning in
tuser.
**Status:** CLOSED 2026-10-02 -- fixed in both modules the day it was found;
reproduced, root-caused, and verified below.
**Owner:** Claude (found via reed-solomon TASK-002)

## Symptom

The RS build-loop harness (n=252, t=8, S=4) with `ERASURE_SUPPORT=1` drives
per-symbol erasure flags spliced above tuser through the `rs_decoder_axis4`
intake (`AXIS_ID_WIDTH=0`, `AXIS_DEST_WIDTH=0`, intake
`AXIS_USER_WIDTH=EUW=5` -- the first-ever zero-ID/DEST instance of the axis4
endpoints with UW>0). Marked runs decoded 7 of 8 blocks uncorrectable with
one miscorrected, while the same stream replayed into `rs_decoder_core`
directly decoded all 8 clean. Probing the core-facing nets inside the wrapper
showed data/keep/last intact on all 504 beats and the erasure field arriving
as `drove >> 2` on all 60 flagged beats -- a static 2-bit right shift, not a
timing skew.

## Root cause

`axis4_slave.sv` (and the mirror in `axis4_master.sv`) packed the skid
payload as `{tdata, tstrb, tlast, tid, tdest, tuser}`, with the zero-width
guards keeping tid/tdest one bit each when their width param is 0 -- i.e. the
guard bits sit BETWEEN tlast and tuser. The unpack generate's
`g_no_id_no_dest` branch sliced `int_t_pkt[TSize-1:2]` as if the two guard
bits were the LSBs; the LSBs are actually `tuser[1:0]`, so
`fub_axis_tuser = {tid, tdest, tuser[UW_WIDTH-1:2]}` = tuser >> 2.
`g_no_dest` and `g_no_id` had the same defect one bit deep.

Every `UW == 0` branch was accidentally correct (the guard bits then sit at
the slice boundary), and every pre-existing instance runs either UW=0 or the
full config (RAPIDS: 8/4/1; pattern pair: 8/4/1), so the bug never fired
until the RS erasure sideband built UW=5 with ID=DEST=0. The val/amba
`(4, 32, 0, 0, 1)` sweep cell IS the buggy config but passed vacuously:
`bin/TBClasses/axis4/axis_slave_tb.py` never drives or checks tuser.

## Fix

Both modules now unpack field-by-field in the axis5 style (which was always
correct): tdata/tstrb/tlast sliced from the top, tid/tdest/tuser sliced from
their constant offsets with per-field generate guards tying zero-width fields
to `'0`. The full-config and UW=0 netlists are logically identical to the old
branches; only the three UW>0-with-a-zero-field configs change (from wrong
to right).

## Verification

- Wrapper-level replay of the failing harness stream (n=252 geometry,
  back-to-back beats): pre-fix reproduced `status=[unc x3, corr-9, unc x4]`
  with 60/504 core-stream beats differing, ALL in the erasure field, every
  one exactly `drove >> 2`; post-fix `504 beats, 0 differ`, all 8 blocks
  corrected with count 8.
- Harness erasure cosim (`test_rs_loop_uart_erasure`): f=t PASS (was
  corr=1/unc=7), f=2t PASS, f=2t+1 refused PASS. (f=16 initially still
  failed on a SECOND, independent bug: the harness's
  `SC_W = $clog2(T+1)` = 4 bits truncated the widened corrected count 16 to
  0 -- every block "corrected with 0 symbols", data perfect. Fixed in
  `rs_loop_harness.sv` by deriving SC_W from ERASURE_SUPPORT to match the
  decoders' STATUS_CNT_WIDTH.)
- reed-solomon dv gate 102/102; func and val/amba gate re-run after the fix
  (results in the commit message).
- DV gap closed: `test_rs_axis4.py` hardcoded `idw, destw = 4, 2`; the grid
  now sweeps `ID_DESTS = [(4, 2), (0, 0)]` on encoder and decoder.

## Sweep

`grep` for the slice pattern (`TSize-1:1]/:2]/:3]`) across rtl/ and
projects/ finds no other instance. `axis5_slave/master` already used
per-field slices. The `_cg` and `_monlite` wrappers instantiate the base
modules, so they inherit the fix.
