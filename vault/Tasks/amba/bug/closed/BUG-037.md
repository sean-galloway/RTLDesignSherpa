# BUG-037: ID filter still loses an owned write's completion at some seeds (TASK-073 symptom back)

**Priority:** P2 -- the write monitors' ID filter is a shipped feature and the
regression that guards it is red at a reproducible seed.
**Status:** CLOSED 2026-09-28 -- root cause found in `axi_monitor_trans_mgr` (early write data dropped) and fixed; the test passes at its seed, val/amba GATE and the trans_mgr/base proofs re-run (results below). Was: open 2026-09-27, reproduced, not diagnosed.
**Owner:** TBD

## Symptom

`val/amba/test_axi4_wr_mon_id_filter.py::test_axi4_wr_mon_id_filter[8-32-32-16]`
(axi4_master_wr_mon, IW=8, MAX_TRANSACTIONS=16) fails its `lost` assertion:

```
enabling the ID filter cost owned-ID write(s) [4] their completion:
completed with the filter off [0, 4, 6], with it on [0, 2, 6].
11 of 16 W transfers occurred with a foreign AWID. TASK-073.
```

The test runs the same stimulus twice, filter off then on, and requires every
owned-ID write that completed with the filter off to also complete with it on.
This is exactly the defect amba TASK-073 described and 657d413c1 ("stop write
monitors ID-filtering W beats against the live AWID", 2026-09-15) fixed -- so
either the fix does not cover every interleaving, or something since has
regressed it. Nothing in the test or its filelist changed: the tooling TASK-005
migration only replaced `filelist_path="rtl/amba/filelists/axi4_master_wr_mon.f"`
with `module='axi4_master_wr_mon'`, which resolves to the same file (verified).

## Reproduction

Deterministic at the seed. The suite's per-run seed base is what makes it
intermittent across regressions (one earlier GATE run the same evening passed
this cell at a different seed):

```
cd val/amba
SEED=94641 REG_LEVEL=GATE python3 -m pytest \
  "test_axi4_wr_mon_id_filter.py::test_axi4_wr_mon_id_filter[8-32-32-16]"
```

Fails at 160,580 ns with the message above (reproduced 2026-09-27 19:32 on a
fresh build directory). Do not dismiss as flaky: the seed replays it every time,
so the interleaving is real -- see [[no-flaky-dismissal]].

## Where to look

`rtl/amba/monitor/axi_monitor_base.sv` around `id_owned()` (line ~361) and the
`w_data_valid_f` attribution (~377-390): the W path was changed to stop filtering
beats against the live `m_axi_awid`. Note that with the filter OFF only three
of the four owned writes complete too (`[0, 4, 6]` of `{0, 2, 4, 6}`), so the
monitor is already dropping one owned completion before the filter is involved;
the filter-on leg then loses a different one. Both legs deserve a look.

## Expected

Owned completions with the filter on are a superset of those with it off, at
every seed. The test is right; the monitor is not.

## Root cause (2026-09-28)

Not the ID filter. A scratch harness that replays the test's stimulus at
SEED=94641 and dumps every AW/W/B handshake and every monbus packet showed
the filter-OFF leg losing two writes too: `0x1080` and `0x11C0` came out as
`Error/PROTOCOL` ("response before data") instead of completions. The
handshake trace has the master BFM presenting W beats BEFORE their AW, which
AXI4 permits, with two such single-beat bursts outstanding at once.

On an AXI write monitor a W beat that finds no entry awaiting data was
simply DROPPED: `data_wants_alloc` is gated with `!IS_AXI`, so no orphan was
allocated either (AXI4 W has no ID to key one on). The AW then arrived to a
table that had never seen its data, waited for beats that had already
passed, and the B closed it as `EVT_PROTOCOL`. With the filter on, the same
mechanism lost owned write 4; TASK-073's fix (do not ID-filter W) was right
but was never the whole story, because the beats it stopped refusing could
still arrive with nowhere to go.

A second, smaller mechanism surfaced once the first was fixed: the
same-cycle AW+W bypass attached a beat to an AW still awaiting its
handshake even when that AW's data phase was ALREADY complete (it had
absorbed an early burst), stealing the beat from the next transaction.

## Fix (`rtl/amba/monitor/axi_monitor_trans_mgr.sv`)

- A small FIFO (`EARLY_BURSTS = 4`) of completed early bursts (beat count
  each) plus the one burst still open. A W beat with no owner goes there; each
  write allocation absorbs the oldest as its data phase (`data_started`,
  `data_beat_count`, `data_completed` when its LAST was seen or the count
  meets `expected_beats`). AXI4 W order is AW order, so the next AW is the
  owner by definition; no ID is needed. More than four completed bursts ahead
  of their addresses keeps the old behaviour (dropped). This is the AXI lite's
  one-burst count, generalised.
- While early data is pending, the same-cycle bypass is OFF (that beat is a
  later transaction's and is queued too), and the bypass never attaches a beat
  to a pending AW whose data phase is already complete.

Verified: the test's own cell at SEED=94641 is the RED-to-GREEN gate
(`filter_on=False: completions=8`, `filter_on=True: owned_completed=[0, 2, 4,
6]`); the pin-level trace of the scratch harness shows every one of the eight
writes in each leg completing. Regression and proofs: see the commit.

Known-issue page: `rtl/amba/KNOWN_ISSUES/axi_monitor_early_write_data_dropped.md`.
