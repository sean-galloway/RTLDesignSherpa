# BUG-039: arming cfg_error_enable makes the axi_monitor_lite shared output queue lossy (~90% of completions dropped, reported as EVENT_DROPPED)

**Priority:** P2
**Status:** FIXED + board-verified 2026-10-09 (this commit): record path pipelined end to end; campaign delivery 54% -> ~92%, residual ~8% is the ingest arbiter's structural 2-cycles-per-transfer rate vs the campaign's burst-offered rate — drops that remain are detected, dropped-and-counted, and reported exactly (the campaign hard-fail on those reports is the stream-side disposition tracked in stream's lane)

## Throughput fix (2026-10-09, this commit) — board-verified

The residual drops after 60c8c230b were the record path's sustained rate,
not the monitor.  Three coordinated changes, each board- or sim-verified:

1. **monbus_group_core write FSM pipelined.**  The WR_AW -> WR_W -> WR_B
   handshake serialization cost ~4 cycles/beat (~12 cycles per raw 3-beat
   record), capping the chain at ~0.08 records/cycle.  Replaced with a
   WR_IDLE/WR_RUN design: AW free-runs up to WR_OS_CAP=4 outstanding writes
   (a B handshake is a pure credit return — bresp/bid are dropped), W
   streams the write FIFO in AW (sub-burst) order, B closes the cycle when
   every committed beat is credited; the close is additionally guarded by
   the W side being empty so an early-B slave model cannot truncate the
   data.  Sub-burst lengths ride in two 4-deep circular queues pushed at
   every AW handshake.  Leaf masters unchanged (axil4_master_wr standalone
   rate test: 0.98 writes/cycle at B latency 2 AND 8 — the leaf was never
   the bottleneck).  Sim: observer suite 25/25 incl. a 0.15 records/cycle
   egress floor (was 0.082); full group wrapper grid green; formal
   prove+cover PASS (harness updated for the pipelined writer).
2. **monbus_tally_axil rec_* B is a pending-count, not a level.**  The
   pipelined producers keep several writes outstanding; the old level B
   dropped responses once >1 write completed per B-accept.  Counter
   (+1 per W handshake, -1 per consumed B, in-order) is exact.
3. **stream_tally_arbiter extracted (new module) + fixed.**  The s4/s6
   harness arbiters were latch-grant-to-B (4 cycles/transfer).  The
   pipelined grant (release at W, B routed in order through a side-queue)
   needed THREE fixes found only by board/sim bring-up: (a) the slave mux
   must be grant-gated — the tally's rec port accepts AW/W unconditionally,
   so an idle cycle phantom-consumed a beat waiting in a leaf skid and the
   tally delivered the SAME beat twice (records with packet.hi==packet.lo,
   then a shifted stream); (b) ONE AW PER GRANT — the leaf AW skid drains
   every ready cycle and the slave's rec_awready is constant 1, so an
   uncapped grant consumed every queued AW while its W trailed, leaving W
   beats with no AW to ever grant them (clean deadlock: write FIFO 96/96,
   zero records); (c) the slave mux defaults to zero when no grant is
   active.  Unit tests (pipelined master 120/120 beats exactly once;
   interleaved bridge 84/84) + a full group->arbiter->tally chain test
   that reproduces the board stall pre-fix.  Structural rate:
   2 cycles/transfer = 0.167 records/cycle.  A both-pending grant (1
   transfer/cycle) was tried and REVERTED — the FSM legitimately runs AWs
   ahead into the leaf skids and the pair-gate deadlocks once the AW skid
   fills; noted here as the known headroom if the campaign rate grows.

**Board A/B (Genesys 2, obs rebuild, WNS +3.0 ns):** per-tally keyed
rd+wr per iteration 2220 -> 3736 of ~4096 offered (54% -> ~92%);
UNEXPECTED = 2 drop reports/iteration carrying the residual (~8%) drops;
accounting closes.  Watermark 0 vs 16: no measurable difference (the
arbiter rate, not the drain-cycle settle, is the ceiling).

## Monitor-side fix (2026-10-08, commit 60c8c230b), board-verified

The robustness package, all three parts validated:

1. **Completion hold** (`r_cmp_pend` in axi_monitor_lite) — a completion the
   pick could not queue (lost to a higher class, or won while the queue was
   full) is held one-deep with its payload and emitted oldest-first at the
   completion rung: the TASK-004 contract the timeout/latency holds already
   had, extended to the only class still exposed to the one-cycle-transit
   loss. Class priority unchanged.
2. **Drain-gated drop reports** — `EVENT_DROPPED` emits only into a fully
   DRAINED queue (the axis_monitor_lite rule), so a report can never take
   the slot a live event needs while the bus is congested.
3. **OUT_DEPTH 4 → 16** on `axi4_master_{rd,wr}_monlite` — rides out the
   ~8-cycle observer-egress stall measured at ~1.1 events/cycle (the depth
   the AXIS taps already run at).

## True root cause (2026-10-08, sim-isolated): the record path sustains ~0.08 records/cycle

The "~938 phantom" was a bad conservation assumption (the DMA issues ~2048
32-byte read bursts per 64KB run, not ~1100, so generated = delivered +
dropped = 2048 per monitor EXACTLY). The drops are REAL, and the monitor
counts them exactly. Sim on the observer with a duty-modeled consumer
(`cocotb_test_observer_consumer_sustained` + `tally_ingest_rate_test`,
both landed 2026-10-08) pinned the bottleneck:

- **Delivery curve with a FREE sink: perfectly linear ~0.082 records/cycle
  (1 record per ~12 cycles), start to finish** — the observer's
  arbiter -> group raw expander -> write FIFO -> AXIL write master chain is
  non-pipelined end to end: every record pays every stage's handshake
  latency serially. Board delivers 0.068/cycle — the same bottleneck minus
  the tally-side decrement.
- The tally core alone sustains 0.500 records/cycle (pinned by
  `tally_ingest_rate_test`; the header's "1 packet / 2 cycles" claim is
  exact). The monitors pick 1 event/cycle each. The arbiter dead-cycles at
  0.5/cycle. Every stage is fast alone; the CHAIN is 6x slower than its
  slowest link because nothing overlaps records.
- The campaign offers ~0.125 records/cycle (32B bursts at ~915 MB/s) — 50%
  above the chain's sustained rate, so ~46% of events are dropped and
  counted no matter how deep the monitor queues are. Arming the error cone
  made the drops VISIBLE (0x0E reports); disarmed they are silent — which
  is the entire "arming ERR_EN poisons the queue" symptom, and why the
  COMPL-only baselines looked clean while being equally starved.
- The accounting identity `offered == delivered + reported` closes to the
  packet in every sim arm (duty 1, 5, and tally-faithful 0), and
  `1110 + 938 = 2048` closes on the board. The monitor RTL is exact; the
  completion-hold fix (60c8c230b) already maximized delivery at this
  consumer rate (228 -> 2220 per tally).

**The remaining fix is the record path's sustained throughput.** Candidate
stages to pipeline, in impact order: (1) `axil4_master_wr` per-record
AW/W/B serialization inside `monbus_axil4_axil4_group` (next measurement:
its standalone sustained rate — ~0.1 would name it); (2) the group raw
expander's 3-cycle-per-record FSM; (3) a harness-side record FIFO between
the group master and the tally `rec_*` port (integration-only change). The
design contract the tally documents is 1 packet / 2 cycles — the chain
should meet it.

Impact until fixed: campaign tallies under-report every class by ~2x at
full DMA rate; the obs campaign hard-fail needs the stream-side disposition
(key 0x0E or match offered rate to the chain) — tracked in stream's lane.
Board repro harnesses: /tmp/bug019/probe_{config_dump,erronly,fifo_stat}.py.

## Where the defect lives

The dropping block is **`rtl/amba/monitor/axi_monitor_lite.sv`** (its sole `Error/EVENT_DROPPED` emitter, protocol AXI), reached on the board through the wrappers **`rtl/amba/axi4/axi4_master_rd_monlite.sv` / `axi4_master_wr_monlite.sv`** (OUT_DEPTH left at the 4-deep default) as instantiated by `projects/components/utility-ip/misc/rtl/axi4_intf_master_observer.sv` (agents 0x00 = rd, 0x10 = wr). The failing tuples on the wire are agent 0x00/0x10, proto 0 (AXI), type 0, evc 0x0E — the AXIS taps (axis_monitor_lite, agent 0x2x, OUT_DEPTH 16) are NOT the source.

## The accounting that constrains the root cause

Campaign per iteration per tally: rd_compl=117 + wr_compl=115 keyed, UNEXPECTED=1964 — and 1964 + 232 ≈ 2196, the COMPL-only event count for the same workload. Three conclusions fall out of the arithmetic:

1. ~89.7% of completions genuinely never reach the tally (they are dropped at the monitor queue, since EVENT_DROPPED is emitted only by that queue's accounting).
2. **Zero error-class packets are ever emitted** while ERROR_EN is armed on clean traffic: UNEXPECTED is exactly the completion deficit, all of it 0x0E. Any detector firing and winning the pick would have been emitted (error has pick priority) and counted on top of the deficit.
3. The consumer keeps up when the error cone is off (0x84/0x86: zero loss on the identical monbus path), so plain consumer backpressure alone cannot explain it either — arming the cone changes the monitor's internal behavior.

## What is correct

Arming a detection cone changes *what is reported*, never *whether an unrelated class is delivered*. Drop-and-count exists as the backpressure contract ("an event it cannot deliver is dropped and counted"), and amba/monitor-lite TASK-004 already conceded that class starvation under a flood is a defect worth fixing — it gave the timeout and latency-threshold events hold registers (r_tmo_pend / r_lat_pend) for exactly this reason. The completion class has no hold: axi_monitor_lite takes **one** event per cycle (error > timeout > completion > threshold), and a completion that loses the pick is dropped-and-counted the same cycle. axis_monitor_lite deliberately takes **two** per cycle with the note "a one-per-cycle pick dropped and counted the loser every time, which made the drop count report ordinary traffic" — the AXI lite kept the single pick. Expected behavior on the board traffic: 0x85 delivers ~2195 completions plus whatever error events genuinely fire (zero here).

## err_en-dependent logic in axi_monitor_lite (the bounded search space)

With no error events firing, `w_err_en` (cfg_error_enable && type mask) touches exactly four things in the core (rtl/amba/monitor/axi_monitor_lite.sv):

1. `w_err_v` gating — error events win the pick (none fire here).
2. `w_err_fired` zeroing — error events enter the offered/lost accounting (none fire here).
3. `w_drop_rpt = (r_dropped != 0) && !w_evt_v && w_wr_ready && w_err_en` — with the cone disarmed, drops are silent (counted, never reported).
4. The addr-checker's cfg_error_enable (compiled out: N_ADDR_RANGES=0 on this build).

A completion can only be dropped when `w_offered > takes`, i.e. an error/timeout/threshold event coincides with it, or the queue is full (`w_wr_ready=0`). Conclusion so far: one of those premises must be false on the board — either an err_en-gated detector fires on this traffic at near-completion rate and its events vanish without emission (only possible through a full-queue path, which needs a sustained backpressure source that the 0x84/0x86 runs argue against), or the queue accounting itself misbehaves when the cone is armed. The unit-level repro below decides it.

## Root-cause candidates and discriminators

| # | hypothesis | discriminator |
|---|---|---|
| H1 | an err_en-gated detector (DATA_ORPHAN / RESP_ORPHAN / WRITE_BEFORE_ADDR / burst-length) fires falsely at ~1/transaction on stream master traffic | unit sim below, log which `r_e_*` fires; board: `dropped_count`/`refused_count` CSRs (obs_rd_dropped / obs_wr_dropped readback) after an 0x85 run — refused>0 points at table overflow → orphan flood |
| H2 | consumer backpressure (observer arbiter dead-cycle / egress err-FIFO stalls, measured 8-cycle stall noted in the AXIS tap's OUT_DEPTH=16 rationale) fills the depth-4 queue; drop reports then re-enter and self-sustain the loss once seeded | unit sim with a stalled consumer and err_en on/off; board ILA on monbus_ready + queue pointers during 0x85 |
| H3 | queue-accounting defect: `w_offered`/`w_lost`/`w_drop_rpt` corrupt when the cone is armed (e.g. drop reports consuming slots / w_lost incrementing without a loss) | unit sim: assert delivered + drops-reported + drops-pending == generated, per the existing soak test's accounting identity (val/amba test_axi_monitor_soak), under 0x85-equivalent config and a clean-traffic profile |

**First discriminator (cheapest, no board):** unit-level repro in val/amba — axi_monitor_lite (or the axi4_master_wr_monlite wrapper) fed a recorded/representative stream master pattern (AW/W/B and AR/R at stream's issue rates, 64-deep table), err_en toggled, consumer keeping up: assert `dropped_count == 0`. Either it reproduces (bisectable in sim, H1/H3 decidable from waveforms) or it exonerates the core and the observer/arbiter/group path is the sink (board ILA becomes the tool).

## Fix options (choose after the discriminator; in likely order)

1. **Give completions the TASK-004 hold treatment** — a completion that loses the pick is held one-deep (or the pick takes two per cycle, the axis_monitor_lite precedent) instead of being dropped. Directly restores "arming a cone doesn't starve a class", at the cost the AXIS core already paid (a second write port / one more hold register).
2. **Raise the wrapper OUT_DEPTH** for the AXI monlite wrappers the way the AXIS tap went to 16 — only if H2 (the measured 8-cycle egress stall) is the driver.
3. **Fix the specific detector** if H1 — with a regression vector in the existing monitor unit suite.
4. **Accounting fix** if H3 — with the soak-test identity extended to the 0x85 configuration.

Regression for whichever lands: the board A/B table above must read "0x85 → keyed ~2195, UNEXPECTED 0", plus the unit suites stay green (val/amba monitor suites; the drop-accounting identity in test_axi_monitor_soak).
