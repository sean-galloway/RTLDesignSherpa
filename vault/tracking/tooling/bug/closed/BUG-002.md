# BUG-002: --blindspots enumerates filelists from the INDEX but resolves them from disk

**Priority:** P2.
**Status:** CLOSED 2026-09-27. Fixed in this commit; see Fix below. **The
original filing's symptom was WRONG and is retracted in Correction below.**

**Where.** `bin/filelist_registry.py`, two reads of different trees inside one
subtraction:

```python
# the orphan set -- enumerated from the INDEX
tracked = subprocess.run(["git", "ls-files", "*.f"], cwd=REPO_ROOT, ...)

# area_filelists() -- resolved from DISK
out.extend(p for p in sorted((REPO_ROOT / d).rglob("*.f")) if not _git_ignored(p))
```

`unregistered_filelists` is `len(tracked - registered)`. One side is the git
index, the other the filesystem.

**The real defect: a false positive on a filelist that is tracked AND registered
but missing from the worktree.** `area_filelists()` cannot see a file that is not
on disk, so the file falls out of `registered` while remaining in `tracked`, and
is reported as an orphan. Measured, on an otherwise clean tree:

```
$ rm projects/asic-trials/timing_characterization/rtl/filelists/char_top.f   # deletion NOT staged
$ python3 bin/filelist_registry.py --blindspots
UNREGISTERED FILELISTS (1) -- invisible to --check/--find:
    projects/asic-trials/timing_characterization/rtl/filelists/char_top.f
    fix: add the containing dir to an area's filelist_dirs in filelists.toml
$ python3 bin/filelist_registry.py --blindspots --ratchet
REGRESSED -- unregistered_filelists   0 -> 1   (+1)        # rc=1
```

That directory **is** in an area's `filelist_dirs`. The advice is impossible to
act on, which is the worst property a gate can have. Note `area_filelists()`'s
own comment already claims "Tracked files only" -- the code implemented
"not git-ignored" instead, which is a weaker and different thing.

**Correction -- what this bug was originally filed as, and why that was wrong.**
It was filed claiming the gate spuriously blocked a commit with a phantom
`unregistered_filelists 0 -> 3` during a directory rename (`rapids_characterization`
-> `rapids_beats`, 2026-09-26). Reproduced in an isolated worktree with
`GIT_INDEX_FILE` pointed at a constructed index, that claim does not survive:

| Filed claim | Measured truth |
|---|---|
| The 0 -> 3 was a phantom; the gate was wrong to block | **The gate was RIGHT.** `git commit -- <paths>` commits HEAD plus only the pathspec'd files. With just the new halves named, the resulting commit really would contain the three OLD `.f` files alongside the three new ones, with only the new directory registered. Three unregistered filelists was a true statement about that commit. |
| Split sourcing produced the wrong number there | It produced the same number either way. Prefix-classifying from the index still reports rc=1 for that temp index, because the old paths genuinely are in it. |
| The fix is to stop the gate blocking renames | The fix for that case is to name BOTH halves of a rename in the pathspec, which is what made it pass (118 paths rc=1, 219 paths rc=0). |

So the rename episode was a correct block on an incomplete pathspec, and the
diagnosability complaint -- a hook failure that cannot be reproduced standalone,
because `GIT_INDEX_FILE` names a temporary index that exists nowhere afterwards
-- is real but is a consequence, not the defect. The defect is the false positive
above, which needs no rename and no hook to trigger.

**Fix.** Classify tracked filelists by registered-directory PREFIX, so both
sides read the index and neither touches the filesystem. Prefix matching is
equivalent to the old `rglob`, which recursed: `d in p.parents` accepts a
filelist nested at any depth under a registered dir.

**Verified, four scenarios:**

| Scenario | Before | After |
|---|---|---|
| clean tree | 0 orphans, rc=0 | 0 orphans, rc=0 |
| tracked+registered, absent from disk | **1 orphan, rc=1** | **0 orphans, rc=0** |
| genuinely unregistered `.f` planted | 1 orphan, rc=1 | 1 orphan, rc=1 |
| temp index holding both halves of a rename | rc=1 | rc=1 (correct -- see Correction) |

`--check`, `--audit`, `--list`, `check_doc_examples.py`,
`check_test_dut_family.py`, `check_broken_links.py --ratchet` and
`check_task_ids.py` all unchanged and passing.

**Must not regress:** tracked-only enumeration (a bare `rglob("*.f")` matches
Fortran under `venv/`, and `rtl/make/area.mk` writes an untracked FLATTENED
filelist into `lint_reports/verilator/` that would otherwise be picked up and
make `--audit` report cross-area sources no commit could fix); recursion into
subdirectories of a registered `filelist_dirs`; and the ratchet still failing on
a genuinely new unregistered filelist.

**Related.** Same defect class as the broken-link checker reading the working
tree while CI reads committed blobs, where untracked directories made 8 dangling
links resolve locally while the gate said PASS (`8562bf0ad`). The general hazard:
a check whose two halves are sourced from different trees yields verdicts that
cannot be reproduced outside the context that produced them.
