## Root cause (waveform-proven)

The two caches miss the **same line** (~one cycle apart). The fabric
grants cache0's transaction (`grant=0`), drives the snoop AC(X) to cache1,
and parks in `F_RESP` waiting for cache1's CRRESP. The fabric only accepts
a cache AR in `F_PASS_AR`/`F_REPLAY_AR`, so cache1's own same-line AR
cannot be accepted while the fabric waits.

Cache1, in the meantime, advanced its own FSM on X:
`LOOKUP→MISS_VICTIM→MISS_FILL`, arming the pending-fill bypass
(`pf_active`), then accepted the snoop (`sn_fill_ok` grants during
MISS_FILL *because* `pf_active`) and entered `OH_SNOOP`.

The snoop answer path then waits on data that can never arrive:

- `l1_control.sv:529` `sn_pf_gnt_match = pf_match && (state_q==OH_MISS_FILL)`
- `sn_pf_q <= sn_pf_gnt_match` (:782); `sn_ref_grant` resolves to
  `pf_state` (:574) → the CRRESP promises **DataTransfer**
- `sn_complete` (:649-652) gates CD beats on `pf_data_valid[beat]`
- `pf_data_valid` is set by arriving fill beats — which need the fill AR
  accepted — which the fabric refuses while in `F_RESP` waiting for this
  very snoop's response.

**Circular wait: fabric(F_RESP) → cache1(CRRESP/CD) → pf_data_valid →
fill R-beats → fill AR acceptance → fabric.** The one-line-apart
same-line miss is the trigger; both earlier same-line races in the same
run (t≈5050000, 5870000) resolved only because both coh_reqs landed
before either fabric grant, so the kill rule serialized them.

The model's own comment (`amber_pair_rig_tb.py:905-908`) encodes the
design intent: *"rig-level serialization makes this path unreachable in a
correct fabric — the kill rule fires instead."* The kill rule
(`peer_pending_true_miss_match`, fabric :471) only inspects pendings
**at grant time**; cache1's coh_req latched *during* F_RESP — too late.

## Fix candidates (analyzed, not landed — owner decision)

RESOLVED 2026-10-15: owner chose **A**, refined during landing into the
**PF_GUARD** form (commit `ab308d108`):

- `l1_fill` exposes `fill_inflight` (AR accepted, response phase begun).
- `l1_control` qualifies `sn_pf_gnt_match` with it under the new
  `PF_GUARD` parameter (default 0 = classic behavior).
- `amber_top` sets `PF_GUARD=1` — it always sits behind a coherence
  fabric (pair rig, Genesys2 harness).
- Standalone benches (direct `l1_control`/`l1_core` instantiation,
  formal included) keep the classic always-answer-from-armed-fill
  behavior their directed snoop scenarios encode; `amber_ace_top` stays
  0 until a real ACE fabric integration exists.
- Pair-rig TB mirrors the guard in `_on_snoop_grant` (answer-as-I for
  pre-AR fills; transient obs and kill state untouched) and the
  scenario-e fairness audit now checks the true invariant (grant-stream
  alternation) instead of the pre-fix hit/kill parity.

**Why the qualifier is "AR accepted" and not "first beat arrived":**
intermediate versions using `|pf_data_valid` (first beat) or a bare
`fill_inflight` without the parameter both broke the directed
snoop-during-fill scenarios in the standalone benches — those
environments intentionally snoop fills before any beat and expect the
bypass answer. No local signal distinguishes "fabric-blocked AR" from
"memory stalled a cycle," so the environment declares itself via
PF_GUARD.

**Original candidate notes (kept for the record):**

**A. Cache side (one-line, implemented + characterized, reverted).**
Qualify `sn_pf_gnt_match` with `|pf_data_valid` — a pre-first-beat fill
answers the snoop from the installed tag (I → no data transfer); the
fabric then passes the requester to memory and serializes the two fills.
Verified: eliminates the hang at SEED=45207 (sim progresses). Side
effect: the pair-rig TB model books every pf-armed snoop as answered-from-
fill (`_on_snoop_grant`, oracle_step on the 'IS'/'IM' transient), so the
new no-data answer diverges the model into a `KeyError` at
`amber_pair_rig_tb.py:771` — the model needs a matching booking rule
(answer-as-I when the DUT fill has no beats). Protocol-legitimate:
neither cache has the line yet; memory is authoritative; read-read
ordering to the same line is safe.

**B. Fabric side (matches the model's stated intent, larger).**
When the peer's pend latches the grant line *during* F_RESP, abandon the
snoop wait and go `F_PASS_AR` (the late kill fires at the peer's own
grant). Requires a snoop-abort path in `l1_control`/`l1_snoop_resp` (the
peer's SNOOP service is mid-flight; its FSM must unwind without the
fabric accepting beats), plus matching model work. More invasive but
preserves "snoop is always answered from the fill" semantics.
