# BUG-008: the Genesys2 harness tally_latch_bank_test assumes the merged MonBus stream's timestamps never decrease

**Priority:** P3 (test defect; seed-dependent false failure).
**Status:** CLOSED 2026-11-26 -- the test checks slot i against the i-th
watched packet the tally accepted.
**Owner:** TBD
**Where:** `projects/fpga-systems/Genesys2/cache-ip/amber/dv/tests/test_amber_pair_harness_axil.py`,
`tally_latch_bank_test` (the same test as amber BUG-006, a second defect).

## What was wrong

The slot walk asserted that latched timestamps are non-decreasing in
capture order. The timestamp is the packet's own (beat 0, `in_ts`), and each
cache stamps its packets as it emits them (`mon0_timestamp`,
`mon1_timestamp`) before `monbus_arbiter` merges the two streams. Each
stream is in order; the merge is not ordered by timestamp, so a packet
stamped 561 by one cache can be accepted behind one stamped 562 by the
other. Seed base 3568510502 (cells SEED=57327 gate, 93446 full) failed
"slot 5 ts 561 < previous 562" and "slot 8 ts 600 < previous 602".

A per-source check is not possible from the packet: both caches are
identical amber_top instances and emit agent 0x00A0.

## Expected

The bank promises capture in ARRIVAL order: slot i holds the i-th watched
packet `monbus_pkt_tally` accepted.

## The fix

A coroutine records `in_ts` of every packet with `w_accept && w_watch_match`
(sampled on the falling edge) from the arm onward; each slot's timestamp
must equal the corresponding recorded one, and at least 16 must have been
accepted.

## Verification

Amber Genesys2 harness suite 6/6 from clean at a fresh seed base, and 6/6
replaying seed base 3568510502 (the same SEED=57327 / 93446 cells that
failed).
