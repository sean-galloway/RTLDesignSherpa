## Reproduction

Jet cell `test_jet_core_s128w4_m16v4_lru_full`, `SEED=1`
(`cd projects/components/cache-ip/jet-mesi-l1/dv/tests && SEED=1
REG_LEVEL=FULL python3 -m pytest test_jet_core.py -q -k "s128w4_m16v4_lru"`):

```
CHECK FAIL: pend effect line=0x5fc: got 0 (I) expected 1 (S)
```

1. Write-miss fill in flight (RU, will install M).
2. Snoop READ_SHARED granted mid-fill (PF_GUARD: no data transfer, beats
   incomplete) → arms pending effect DOWNGRADE_S.
3. Snoop READ_ONCE granted on the same line → the RTL computes next-state
   against the ORIGINAL post-fill reference (M), so RO resolves M→I and
   OVERWRITES the armed downgrade with INVALIDATE.
4. At commit the store has already been merged onto the fill beats, then
   the line installs I. The RS never got the data (PF_GUARD), no peer has
   it — **the store is silently dropped after its response released.**

The gem5-derived oracle (`amber_fsm_oracle._im_step`) chains the
next-state against the armed effect (armed-S then RO → S, fixed point) —
the documented, pinned semantics (gem5_mapping_notes.md divergence 3).
The RTL only consults the armed effect for the I-sticks write gate.

## Expected behavior

For MSHR-source snoops with an armed pending effect, resolve the effect's
next-state against the ARMED state (`effective = armed ? armed_state :
post_fill`), keeping the grant-cycle CRRESP at the original post-fill
state. I-sticks falls out (armed I ⇒ effective I ⇒ all next-states I).
