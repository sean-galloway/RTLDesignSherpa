# BUG-005: amber_pair_fabric's write-port arbiter is not round-robin -- the last winner keeps top priority

**Priority:** P2 (fairness; no corruption or starvation observed).
**Status:** CLOSED 2026-11-26 -- fixed as jet BUG-006 (rtl/common
`arbiter_round_robin` in request/grant/ACK mode, the absorption kick folded
into the write-back's request); amber full 121/121.
**Owner:** TBD
**Where:** `rtl/top/amber_pair_fabric.sv`, the `w_sel` always_comb and the
`w_rr_q` update in W_IDLE.

## What is wrong

The same code as jet BUG-006 (jet's pair fabric inherited it from amber):
the scan from `w_rr_q = w_sel + 1` keeps the LAST candidate it sees, and
the last index scanned is the previous winner, so the previous winner has
top priority at every idle and the requester after it comes last. The
comment above the arbiter says "fair round-robin". The full analysis is in
[jet BUG-006](../../../jet-mesi-l1/bug/closed/BUG-006.md).

## Expected

A first-match scan from `w_rr_q`: the previous winner lowest, every
candidate served within four grants.

## The fix (2026-11-26)

The same change as [jet BUG-006](../../../jet-mesi-l1/bug/closed/BUG-006.md):
`u_w_arb` over the same candidates, the held grant as the burst's owner,
the ACK on the cycle the write FSM leaves W_B, a write-back's request
dropped in the cycle an absorption of its line is kicked
(`abs_kick_match`), `block_arb` tied off (a test hook);
`amber_pair_fabric.f` pulls `arbiter_round_robin.f`.
amber has no order hold (the write-back ordering rule is jet's), so only
`abs_match` can block a candidate.

## Verification

amber full 121/121 from clean, 0 reruns. amber's pair rig has no grant
check or directed kick-cycle scenario of its own; `abs_kick_match` is
exercised on jet's copy (scenario (k), mutation M5).
