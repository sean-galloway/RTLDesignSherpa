# BUG-005: amber_pair_fabric's write-port arbiter is not round-robin -- the last winner keeps top priority

**Priority:** P2 (fairness; no corruption or starvation observed).
**Status:** CLOSED 2026-11-26 -- fixed as jet BUG-006 (rtl/common
`arbiter_round_robin` in request/grant/ACK mode, the absorption kick folded
into the write-back's request); amber full 121/121.
**Owner:** TBD
**Where:** `rtl/top/amber_pair_fabric.sv`, the `w_sel` always_comb and the
`w_rr_q` update in W_IDLE.

## What is wrong

The same code as jet BUG-006 (jet's pair fabric inherited it from amber):
the scan from `w_rr_q = w_sel + 1` keeps the LAST candidate it sees, and
the last index scanned is the previous winner, so the previous winner has
top priority at every idle and the requester after it comes last. The
comment above the arbiter says "fair round-robin". The full analysis is in
[jet BUG-006](../../../jet-mesi-l1/bug/closed/BUG-006.md).

## Expected

A first-match scan from `w_rr_q`: the previous winner lowest, every
candidate served within four grants.

## The fix (2026-11-26)

The same change as [jet BUG-006](../../../jet-mesi-l1/bug/closed/BUG-006.md):
`u_w_arb` over the same candidates, the held grant as the burst's owner,
the ACK on the cycle the write FSM leaves W_B, a write-back's request
dropped in the cycle an absorption of its line is kicked
(`abs_kick_match`), `block_arb` tied off (a test hook);
`amber_pair_fabric.f` pulls `arbiter_round_robin.f`.
amber has no order hold (the write-back ordering rule is jet's), so only
`abs_match` can block a candidate.

## Verification

amber full 121/121 from clean, 0 reruns (2026-11-26, the fix).

**amber's own coverage (2026-11-26).** The case `abs_kick_match` guards
-- an absorption of line X kicked while a write-back of X waits at a cache
port -- cannot occur on amber:

1. a write-back of X waits only while its cache is in MISS_DRAIN (the
   victim drains there and nowhere else, and the FSM leaves MISS_DRAIN
   only on drain_done);
2. the fabric admits a data snoop into a MISS_DRAIN peer only with a
   request pending from that peer (`peer_safe_data`), and amber's request
   is the fill start, which follows the drain (the drain's WRITE_BACK is
   not queued; a clean-all drain queues nothing either);
3. the one exception, a MakeInvalid kill, carries no data and kicks no
   absorption.

A directed attempt (jet's scenario (k) built for amber: cache o held in
MISS_DRAIN with X's AW waiting behind an absorption held in W_B) stalls at
step 2 with cache o's request count at 0, which is what the chain predicts.
So amber's pair rig carries two rig-wide checks instead of (k):

- `_check_w_grant` (as jet's): no write-back's burst starts with an
  absorption of its line already pending. 50 / 268 grants checked in the
  s016w2 gate / s128w4 func cells.
- `_check_kick_vs_wb`: an absorption kick while a write-back of that line
  waits at a cache port fails the run, naming the chain above as broken.
  16 / 18 kicks checked in the same cells, 0 hits.

Mutations: M5 cannot be caught on amber by any stimulus (the case is
unreachable). M6 (`abs_match` itself removed from `wb_blocked`) also
survives -- amber never has a write-back waiting while an absorption of
its line is pending, by the same chain. M7 (the fabric admits data snoops
into MISS_DRAIN without a pending request, breaking step 2) survives
random traffic; with M7 and the directed sequence above (its pending
check dropped), `_check_kick_vs_wb` fires ("absorption kick on line 0x12d
while cache0's write-back of it waits"), which shows the check is live.
The directed sequence's own order checks passed in that run, i.e.
`abs_kick_match` handled the case once it was reachable.

amber full 121/121 from clean, 0 reruns, with both checks.
