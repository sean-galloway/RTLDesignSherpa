# BUG-003: tally bins all zero on some seeds ("MonBus observation path is silent") — seed-flaky, both levels

**Date:** 2026-10-25
**Priority:** P3
**Status:** CLOSED 2026-10-27
**Owner:** amber
**Where:** `projects/fpga-systems/Genesys2/cache-ip/amber/dv/tests/test_amber_pair_harness_axil.py` (`smoke_test` tally CAM programming)
**Found by:** the monbus_axil4_group_1wr harness sweep, 2026-10-25

## What

`test_amber_pair_harness_axil[gate|func]` failed on some seeds with

```
AssertionError: tally bins all zero: MonBus observation path is silent
```

at EITHER level: gate (SEED=24983, SEED=12478, SEED=74560), func
(SEED=83362). The same seeds failed identically at 8854596d7 (before the
2026-10-25 stream/rapids 1wr commits) and on both monitor groups, so this
was never the group swap. Sibling seeds passed, so roughly every other seed
was red.

## Root cause

(2026-10-27, probed with hierarchical counters + the tally's first-event
latch on SEED=74560)

The MonBus path was never silent. Two stacked test-side bugs emptied the
tally's legal-set CAM on EVERY run, and a readback race turned the
deterministic failure into a coin flip:

1. **CAM_LOAD VALID at the wrong bit.** The test wrote
   `CAM_LOAD = (1 << 16) | idx`; the regblock (`tally_regs.rdl`) declares
   `VALID[31]`, `INDEX[7:0]`. Bit 16 belongs to no field, so every entry
   loaded with VALID=0. (Every other consumer — stream's DV, the fub test,
   `bin/tally.py`, and `amber_board.py` via the generated regmap — uses
   bit 31 or field names.)
2. **`write64` clobbered every CAM register.** The helper splits a 64-bit
   write into lo/hi 32-bit writes at +0/+4. The tally's cfgw port is 64-bit
   and its regblock wrapper ignores WSTRB and always writes `wdata[31:0]`
   with full bit-enables, so the hi-word write at +4 aliased onto the same
   register: CAM_KEY was zeroed before every load, and CAM_LOAD re-fired
   with INDEX=0/VALID=0, invalidating entry 0. Probe after programming:
   `r_valid = 0x7fe`, all keys 0.

With the CAM empty, every packet missed the legal set and landed in the
UNEXPECTED bin (index 32, which the test never reads): probe showed
UNEXPECTED = 867 ≈ the total merged record count on every seed, with
profile bins genuinely zero.

3. **The seed flake was a readback race on top.** The smoke sweep reads
   bins with no freeze while records are still draining past injector-done;
   `monbus_pkt_tally`'s registered readback serves the RMW traffic's SRAM
   read register during activity, leaking the live UNEXPECTED mid-count
   into whichever bin the host asked for. A leaked nonzero value made
   `sum(bins) > 0` pass spuriously; whether the sweep overlapped RMW
   traffic depended on host BFM timing, i.e. the cocotb SEED (the injector
   seeds are fixed — the SEED only moves host transfer timing and the two
   injectors' start phase).

## Fix

Program the CAM with single 32-bit writes and VALID at bit 31
(`smoke_test` and `aperture_probe_test`); the CAM registers are 32-bit and
never needed a 64-bit decomposition. `docs/address_map.md` now states
`{VALID[31], INDEX[7:0]}`.

Verified: instrumented run shows `hit=1, bin=1` on the first packet,
UNEXPECTED=0, bins counting real events (hit/miss/evict/...); the axil
test goes 2/2 on all four known-bad seeds (gate 74560/24983/12478, func
83362) plus three unpinned runs; uart 2/2.

## Follow-ups filed

- **misc BUG-003** — the WSTRB-blind 64-bit cfgw write wrapper in
  `monbus_tally_axil`: a 4-byte-strided write to a register's high half
  clobbers the register and re-fires its swmod actions. Latent for every
  host that decomposes 64-bit accesses; amber works around it test-side.
