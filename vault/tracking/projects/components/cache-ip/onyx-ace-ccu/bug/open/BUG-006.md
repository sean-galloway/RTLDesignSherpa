# BUG-006: a replay can starve behind a requester's streaming memory beats

**Priority:** P2 -- unbounded wait of an upgrade's (or a supplied line's)
completion; PRD criterion 3.
**Status:** open (filed 2026-11-27).
**Owner:** TBD
**Where:** `rtl/top/onyx_ccu.sv`, the requester's R select (memory beat
first, else replay) and `r_rpl_hold`.

## What is wrong

A memory beat for a requester always wins its R channel over the replay
engine, and `r_rpl_hold` arms only after a replay beat was presented and
refused. A replay that never gets presented is never protected, so a
requester with fills streaming back to back never sees it.

## Reproduction

Liveness harness `formal/onyx/onyx_ccu_live` (L2.rpl, a loaded replay
completes within (2 SLOTS - 1) FILL_BEATS + 2): FAIL at step 44 at N = 2,
3 and 4. N = 2 trace: all four slots are cache 1's; slot 2 is a
CleanUnique (one no-data replay beat) loaded into the engine at step 8;
slots 0 / 1 / 3 are fills re-granted continuously with memory returning
their beats back to back -- the upgrade's beat never goes out (to step
44). Needs a cache with >= 3 fills streaming plus a pending upgrade
(jet-prime at MSHR_COUNT >= 3; the rigs run 8).

## Fix direction

Give a loaded replay priority at the next burst boundary of the memory
stream (or alternate per burst), so its wait is bounded by one fill burst.
Re-run L2.rpl.
