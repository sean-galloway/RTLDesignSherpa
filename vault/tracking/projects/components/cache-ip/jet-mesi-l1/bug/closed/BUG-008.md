# BUG-008: jet_pair_fabric's safe-peer wait starves a miss behind the peer's pipelined hit stream

**Priority:** P1 (liveness: a cache's miss waits for as long as its peer
keeps hitting back to back -- unbounded for a core that never pauses; no
data corruption).
**Status:** CLOSED 2026-11-27 (filed and fixed the same day).
**Owner:** cache-ip session
**Where:** `rtl/top/jet_pair_fabric.sv`, `peer_unsafe()` and
`peer_safe_data` (the safe-peer wait in front of `s{0,1}_acvalid`).

## What is wrong

A granted coherence request presents its AC only when `peer_safe`. With no
kill and no request of the snooped cache's own held here, that is
`!peer_unsafe(peer_state) && !peer_lkup_live` -- and `peer_unsafe` counts
LOOKUP, HIT_RD and HIT_WR as unsafe. A jet fed a pipelined hit stream
reports HIT_RD (and `lkup_live`) on every cycle, so the fabric sits in
F_AC with the grant held until the peer's stream stops. On the bench the
stall ends because the injector's count runs out; a real core does not run
out.

The file disagrees with itself about this wait: the header calls it
"belt-and-suspenders ... a presentation-time optimization, not a
correctness mechanism" on jet (the responder's `sn_safe_o` holds an AC
presented in its own unsafe windows), while the block above `peer_unsafe`
keeps amber's skid-deadlock argument for treating LOOKUP / HIT as unsafe.
BUG-004 removed the same kind of term from the PENDING bypass; the
no-pending path still has it.

## Reproduction

- **Board** (common-ip BUG-001's GO rebuild, jet bitstream sha256
  f51ec558e557e5cb, `jet/results/perf_sweep_bin20_go_20261127T091929Z.json`):
  `r4k_we0` (all reads, one 4 KB set, both injectors, launched by one GO)
  -- depth 1 overlaps (80,401 / 80,259 cycles), every depth >= 2 runs one
  injector at full rate and the other after it: depth 4 20,293 / 40,320,
  depth 16 20,005 / 40,337. Same shape in `r1k_we64`, `r64b_we64`,
  `smoke4k_we64` at depth >= 8.
- **Sim from reset** (`jet/dv/tests`, smoke_test, `JET_SMOKE_MASK=0xFFF
  JET_SMOKE_WE_MIX=0 JET_SMOKE_COUNT=20000 JET_SMOKE_OUTSTANDING=4`,
  GO-launched): run_cycles 22,705 / 42,525 (depth 16: 22,901 / 42,623;
  depth 2: 42,761 / 42,635, overlapped). The wave: from ~305 accepts each,
  the fabric holds `state_q == F_AC`, `grant_q == 1`, `peer_safe == 0`,
  `peer0_state == ST_HIT_RD` and `peer0_lkup_live == 1` for ~20,000
  cycles while cache 0 completes ~1 access per cycle and cache 1 completes
  none; the AC issues the cycle cache 0's stream ends.
- **Not seen on** jet-prime's pair (`ref` SEL 3), onyx (SEL 4/5) or amber:
  `r4k_we0` overlaps at every depth (ratio 0.50) on the same GO pass.

## What correct looks like

A granted miss is snooped in bounded time whatever the peer's hit rate:
`r4k_we0` overlaps at every depth (both injectors ~20,000 cycles at depth
>= 4), as it does on jet-prime and onyx.

## Notes

- Every board "dual" sweep before the GO was sequential (common-ip
  BUG-001), which is why no board run showed this; the sim rigs' random
  traffic leaves gaps in the hit stream.
- A pin for the fix: the smoke_test cell above with an assertion that the
  slower injector's run_cycles stays within a bound of the faster's.

## Fix (2026-11-27)

`jet_pair_fabric.sv`: `peer_unsafe()` no longer counts LOOKUP / HIT_RD /
HIT_WR, and the no-pending path no longer demands an idle peer lookup
(`peer_safe_data = !peer_unsafe(state) || (pend && !drain_same_line)`).
The wait now holds the AC only in INIT and the miss states, as the file
header already specified. The `peer{0,1}_lkup_live` ports are gone (the
pair rig TB and the Genesys2 jet harness no longer wire them).

Why it is sound on jet (the comment block above `peer_unsafe` carries the
argument): the LOOKUP / HIT terms were amber's -- a skidded AC against
amber's pending-fill bypass. jet has no such bypass, and jet_control
orders a snoop against its own pipeline: the AC is granted only while
`sn_safe_o` (no init walk, service, commit window, victim capture, CU
grant cycle or unlanded pended write), a captured request classifies
against the post-snoop state, and a waiting AC (`sn_want`) throttles new
CPU accepts so the window opens within the pipe drain (Task 11's
liveness). A miss the peer takes after the AC is presented is held at
this fabric, so it is pre-AR and answers at the Invalid row (BUG-004's
argument). jet-prime's pair fabric, same responder lineage, presents its
AC with no peer-state wait at all.
