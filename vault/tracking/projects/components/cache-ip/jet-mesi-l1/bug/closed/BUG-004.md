# BUG-004: jet_pair_fabric safe-peer wait demands an idle peer lookup that a pipelined request stream never grants -- both caches park with an AR held, the fabric in F_AC forever (rig deadlock)

**Date:** 2026-11-11
**Priority:** P1
**Status:** closed 2026-11-11 -- fix in the fabric, pair-rig scenario (i) pins it; clean jet FULL 149/149, jet-g2 gate 2/2 (depths 1/8/16), Genesys2 jet bin 17 WNS +0.212, smoke PASS, depth sweep err 0 (common-ip TASK-002 closed on it).
**Owner:** jet

## Symptom

The pipelined cycle injector (cache-ip common-ip TASK-002) at depth 8 on the
jet Genesys2 pair harness (`injector_pipeline_test`, both injectors on the
same 4 KB region, 256 transactions each): after six accepts on one injector
and five on the other, neither cache ever responds again. The injector's
24-bit response timeout is longer than the test's poll budget, so the gate
reports "cycle injectors did not finish" (jet-g2 gate 1 failed, 3 reruns).
Depth 1 (the original blocking behaviour) passes; the amber rig passes at
every depth (amber is blocking at its CPU port).

Reproduced in jet's own pair rig by the new scenario (i)
`_s_deep_pipelined_misses` (eight back-to-back true misses per CPU before
any response is awaited): `test_jet_pair_rig_s016w2l64b64_mon_gate` hangs at
cycle 33,105 with the hang trace

    fstate 1 (F_AC) pend 01 grant_q 1 peer_safe 0 pend_cnt0 1
    c0ar 10 c1ar 10 s0ac 01 s1ac 01
    core0: lk_valid 1 fill_pend 1 fill_start 1 fill_accept 0 eng_busy 1
    core1: lk_valid 1 fill_pend 1 fill_start 1 fill_accept 0 eng_busy 1

The pre-TASK-002 rigs could not show it: a blocking injector keeps at most
one request per cache in flight, and the random lockstep of scenario (g)
pipelines bursts of at most three with 30 % probability.

## Cause

`jet_pair_fabric.sv`, the safe-peer wait. The AC to the peer is presented
only while `peer_safe`; its data-snoop term was

    (!peer_unsafe(peer_state_now) && !peer_lkup_now)
    || (peer_pend_now && !peer_drain_grant && !peer_lkup_now
        && (peer_state_now == ST_MISS_FILL || peer_state_now == ST_MISS_DRAIN))

Both terms require the peer's lookup to be idle (`peer_lkup_now`, the
`lkup_live` export of `jet_top`, ISSUE-001 v2 step 3), and the pending
bypass additionally requires an amber miss pseudo-state that jet reports
only as one-cycle events (the fill accept, the drain start). So on a jet the
bypass never applied in steady state, and the wait reduced to "the peer's
lookup must be empty".

With a pipelined request stream the peer's lookup is never empty while its
own fill waits: the fill-launch register (`r_fill_pend`) is busy behind the
AR this fabric holds, so the next true miss at the classify stage holds
("fill-launch register busy"), `w_pipe_room` drops, the skid keeps its
request and `lkup_live` stays high. The same holds for an MSHR-full stall
and for the cross-class wait behind a pending fill: each resolves only
through this fabric's grant. The fabric therefore waited on a lookup that
was waiting on the fabric. Once both caches had a fill queued and a second
miss parked, the grantee's peer could never be snooped and the grant never
completed.

The header's liveness argument ("the pending term releases the wait")
described the intended behaviour, but the term as written could not fire on
a jet.

## Fix

Drop the two amber-era qualifiers from the pending bypass:

    wire peer_safe_data = (!peer_unsafe(peer_state_now) && !peer_lkup_now)
        || (peer_pend_now && !peer_drain_grant);

Sound on jet: while the peer's request is held here, every fill the peer
can launch is pre-AR (the single-outstanding engine's AR for that direction
is accepted only at that direction's grant), and `jet_control`'s pre-AR rule
answers any snoop to a pre-AR entry at the Invalid row with no data,
whatever the ACSNOOP encoding -- a launch the kill rule did not see is
answer-neutral. The commit, capture and snoop-service windows are the
responder's own (`sn_safe_o` holds a presented AC); the drain-on-this-line
window stays excluded by `peer_drain_grant`. `jet_control` is untouched, so
the formal flats are unaffected; the fabric has no formal harness.

Regression: pair-rig scenario (i) `DeepPipelinedMisses` runs at every level
(gate included): a shared-line round (c0 writes beat 0, c1 reads beat 1 of
the same eight lines) and a disjoint-line round, each checked for liveness,
a legal MESI pair per line and the writer's store in every valid copy.
Lines are (tag, set) pairs fresh to the run (tags 1..8 at sets 7..16),
one per set per cache per round, drawing no fresh tag (the directed tag
budget is exhausted at WAYS=4).
