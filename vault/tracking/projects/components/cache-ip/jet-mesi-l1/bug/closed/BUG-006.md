# BUG-006: jet_pair_fabric's write-port arbiter is not round-robin -- the last winner keeps top priority

**Priority:** P2 (fairness and determinism of the write port; no data
corruption, no starvation observed).
**Status:** CLOSED 2026-11-26 -- the hand-written scan replaced by rtl/common
`arbiter_round_robin` in grant/ACK mode with `block_arb` (the owner's
choice); jet full 149/149.
**Owner:** TBD
**Where:** `rtl/top/jet_pair_fabric.sv`, the `w_sel` always_comb and the
`w_rr_q` update in the write FSM's W_IDLE. The same code is amber's
(amber BUG-005); jet-prime's and onyx's write paths are different code.

## What is wrong

The comment above the arbiter says "fair round-robin" over
`w_cand = {absorb1, absorb0, cache1 wb, cache0 wb}`. The code:

```systemverilog
w_sel = w_rr_q;
for (int k = 0; k < 4; k++)
    if (w_cand[(w_rr_q + k) % 4]) w_sel = (w_rr_q + k) % 4;   // LAST match wins
...
w_rr_q <= (w_sel + 1) % 4;                                   // at the grant
```

The scan starts one past the last winner, but the loop keeps the LAST
candidate it sees, not the first. The last index scanned is
`(w_sel + 1 + 3) % 4 == w_sel`, so the previous winner always has top
priority, then `w_sel - 1`, `w_sel - 2`, and the requester just after the
winner comes last. That is a sticky, reverse-order priority, not a
round-robin.

## Expected

A first-match scan from `w_rr_q` (the first candidate at or after the
pointer wins), so the previous winner has the LOWEST priority at the next
idle and every candidate is served within four grants.

## Consequences

- A requester that presents again at the next idle wins again. Absorptions
  are single per direction and a cache's next drain AW has a gap after its
  BRESP, so in practice the port still alternates, and no run has starved.
  Nothing bounds it, though: the property holds by accident of timing.
- Arbitration outcomes depend on who won last rather than on rotation,
  which made the BUG-005 order hazard reachable in a specific way: jet
  pair-rig scenario (j) `WbSameLineOrder` relies on it (after abs0, index
  2, wins, cache1, index 1, outranks cache0, index 0). With a first-match
  scan, cache0 would win that idle on its own, the scenario would pass
  without the order hold, and M1 would go uncaught again. A fix here must
  rebuild (j) so the newer write-back outranks the older one under the new
  rotation (for example, the third burst from the cache1 direction).

## The fix (2026-11-26)

`u_w_arb`: `arbiter_round_robin #(.CLIENTS(4), .WAIT_GNT_ACK(1))` over the
same `w_cand`. Its grant is registered and HELD until acked, so the held
grant is the burst's owner (`w_wr_is_abs` / `w_wr_owner` decode
`grant_id`); the registers `w_owner_q`, `w_is_abs_q` and `w_rr_q` are gone.
The write FSM leaves W_IDLE on `w_gnt_valid` and acks on `w_burst_done`
(W_B and BVALID, the cycle it leaves W_B); the arbiter rotates on that ACK
and forms the next grant on the ACK edge when another candidate waits, so
back-to-back bursts keep the one-idle-cycle spacing. A fresh request
after an idle spell now takes one more cycle to reach W_AW (the grant is
registered).

`block_arb = w_abs_kick` (the snoop's CR accept with DT and PassDirty):
the grant registers a request sampled a cycle earlier, and the one way a
candidate stops being eligible in between is a write-back whose line gets
an absorption kicked in that cycle. No grant forms in a kick cycle.
Absorption requests and AWVALIDs are otherwise stable until served, and
`aw_younger` can only turn on for the later-presented write-back.

The filelist `jet_pair_fabric.f` pulls `arbiter_round_robin.f`; the jet
Genesys2 pair harness lint (which reaches the fabric through it) passes.
The bitstream was not rebuilt.

## Verification (2026-11-26)

- jet full 149/149 from clean, 0 reruns.
- New rig-wide check `_check_w_grant`: in W_IDLE with a valid grant, the
  granted candidate is still set in `w_cand`. Each full pair-rig cell
  checks 3317-4217 grants.
- Scenario (j) `WbSameLineOrder` reworked (it relied on the old order;
  roles swapped, see jet BUG-005) and passes in 26/26 pair-rig cells.
  M1 (the BUG-005 order hold removed) fails both gate cells four ways.
- New scenario (k) `WbGrantVsAbsorbKick`: a B-channel valve on the rig top
  (`tb_b_hold`) holds cache1's burst in W_B and releases it in exactly
  the cycle cache1's write miss kicks the absorption of X, whose write-back
  from cache0 waits; passes in 26/26 cells. M4 (`block_arb` tied low)
  passed every random cell and (j) before (k) existed; with (k) it fails
  both gate cells: the eligibility check (candidate 0 granted, no longer
  eligible), (k)'s order check (cache0's write-back of X lands before the
  absorption) and the passed-entry check.

## Reproduction

Read the loop; or in jet pair-rig scenario (j), log `w_sel` at each W_IDLE
grant: after `abs0` (2) wins, the next idle with candidates {0, 1} grants 1
(a round-robin from `w_rr_q = 3` would grant 0).
