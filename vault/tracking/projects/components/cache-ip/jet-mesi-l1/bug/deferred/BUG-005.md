# BUG-005: a write-back victim passed on by a snoop still drains (jet carries jet-prime BUG-002)

> Source: jet-prime BUG-002 (2026-11-24). jet-prime is jet forked at
> 2be919254, and the defect is jet's: the rule is in jet's MAS ch02/03 and in
> `jet_wb_buffer`, `jet_control` and `jet_pair_fabric` unchanged.

**Priority:** P1 in principle (silent memory corruption between two caches);
not reproduced on jet.
**Status:** DEFERRED 2026-11-24 -- jet is frozen as the measured baseline
(the area rollup: "nothing in it moves"). Fix by porting jet-prime BUG-002 if
jet is ever unfrozen or shipped.
**Owner:** TBD
**Where:** `rtl/fub/jet_wb_buffer.sv` (the effect `r_eff` is written and never
read; "an invalidated snarfed victim still drains"), `rtl/fub/jet_control.sv`,
`rtl/top/jet_pair_fabric.sv` (a write-back is held only while an absorption to
its line is pending, then round-robin).

## What is wrong

As jet-prime BUG-002: a WB entry answers a snoop at Modified, every such snoop
passes the line on (DT + PassDirty, or MakeInvalid), and the entry still
drains. If the new owner's write-back of the line lands first, the old drain
overwrites it. The entry also stays a snoop source until its BRESP, so a
second snoop is answered from the stale bytes.

## Reach on jet

jet's pair fabric is serial: one coherence transaction at a time, the memory
read after the snoop. A hot-set soak phase (both CPUs, 70 % writes, `WAYS + 3`
tags in two sets) run once on jet's pair rig on 2026-11-24 passed 26 of 26
cells, with 7-29 WB snarfs per cache per full cell, against jet-prime's 21-102
and two failing cells. The window is narrower on jet; it is not shown closed.
The phase was not kept in jet's testbench (jet is frozen).

## Why jet's suites miss it

The same five reasons as jet-prime BUG-002 (jet-prime inherited them): the
rule is the MAS's, `jet_wb_buffer_tb.py` asserts it, the core rig has no
second writer, the pair rig's model restates it, and the uniform soak reaches
a WB snarf a handful of times per cell.
