# BUG-006: jet_pair_fabric's write-port arbiter is not round-robin -- the last winner keeps top priority

**Priority:** P2 (fairness and determinism of the write port; no data
corruption, no starvation observed).
**Status:** OPEN 2026-11-26 -- filed; not fixed.
**Owner:** TBD
**Where:** `rtl/top/jet_pair_fabric.sv`, the `w_sel` always_comb and the
`w_rr_q` update in the write FSM's W_IDLE. The same code is amber's
(amber BUG-005); jet-prime's and onyx's write paths are different code.

## What is wrong

The comment above the arbiter says "fair round-robin" over
`w_cand = {absorb1, absorb0, cache1 wb, cache0 wb}`. The code:

```systemverilog
w_sel = w_rr_q;
for (int k = 0; k < 4; k++)
    if (w_cand[(w_rr_q + k) % 4]) w_sel = (w_rr_q + k) % 4;   // LAST match wins
...
w_rr_q <= (w_sel + 1) % 4;                                   // at the grant
```

The scan starts one past the last winner, but the loop keeps the LAST
candidate it sees, not the first. The last index scanned is
`(w_sel + 1 + 3) % 4 == w_sel`, so the previous winner always has top
priority, then `w_sel - 1`, `w_sel - 2`, and the requester just after the
winner comes last. That is a sticky, reverse-order priority, not a
round-robin.

## Expected

A first-match scan from `w_rr_q` (the first candidate at or after the
pointer wins), so the previous winner has the LOWEST priority at the next
idle and every candidate is served within four grants.

## Consequences

- A requester that presents again at the next idle wins again. Absorptions
  are single per direction and a cache's next drain AW has a gap after its
  BRESP, so in practice the port still alternates, and no run has starved.
  Nothing bounds it, though: the property holds by accident of timing.
- Arbitration outcomes depend on who won last rather than on rotation,
  which made the BUG-005 order hazard reachable in a specific way: jet
  pair-rig scenario (j) `WbSameLineOrder` relies on it (after abs0, index
  2, wins, cache1, index 1, outranks cache0, index 0). With a first-match
  scan, cache0 would win that idle on its own, the scenario would pass
  without the order hold, and M1 would go uncaught again. A fix here must
  rebuild (j) so the newer write-back outranks the older one under the new
  rotation (for example, the third burst from the cache1 direction).

## Reproduction

Read the loop; or in jet pair-rig scenario (j), log `w_sel` at each W_IDLE
grant: after `abs0` (2) wins, the next idle with candidates {0, 1} grants 1
(a round-robin from `w_rr_q = 3` would grant 0).
