# BUG-004: jet_prime_pair_fabric carries onyx BUG-001 and BUG-002 -- CleanUnique snooped as MakeInvalid, and no hold of a memory read against an in-flight write

**Priority:** P2 (the pair fabric is onyx's predecessor; the defects are
real here, but onyx is the active manager).
**Status:** open (filed 2026-11-26; not reproduced on this fabric).
**Owner:** TBD
**Where:** `rtl/top/jet_prime_pair_fabric.sv`: `map_snoop` (CLEAN_UNIQUE ->
`ACSNOOP_MAKE_INVALID`) and the memory AR candidate (`w_marc_*`, about
line 705).

## What is wrong

The same code shape as onyx before its fixes (onyx `onyx_ccu` is this
fabric generalized):

1. **onyx BUG-001.** A killed upgrade (its Shared line invalidated by a
   snoop before its CleanUnique was granted) is still granted, and its
   `MakeInvalid` snoop drops the stores of a peer that took the line
   Modified in between. This rig's golden model encodes that loss as "the
   fabric-contract M-kill corner" (`dv/tbclasses/jet_prime_pair_rig_tb.py`,
   the snoop-effect and CU-install paths), so the rig scores the loss as
   correct rather than flagging it.
2. **onyx BUG-002.** A slot's memory read can issue while the write port
   has a burst to the same line in flight; the read may return the bytes
   from before the write.

Both were found in onyx by its core-alone rig (BFM caches); neither has
been reproduced here, where the caches are jet-prime RTL.

onyx BUG-003 (a stale drain held behind a NEWER owner's absorption) needs
a third requester; this fabric has two caches and no IO port, and a
cache's own-lookup stall keeps it from re-requesting a line its drain
holds, so it is not expected here -- not proven either.

## Expected

As onyx after its fixes: CleanUnique -> CleanInvalid (IHI 0022), and the
memory AR candidate held while the write port's selected burst targets the
slot's line. The golden model's M-kill corner then has to go: a Modified
peer passes the line dirty and the store survives.
