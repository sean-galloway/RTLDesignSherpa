# ISSUE-001: jet-prime's fill-to-snoop-to-data-array path swings across the 0.2 ns budget from build to build (+0.252 to -0.204 ns routed on the Genesys2 ref rig)

**Status:** open (filed 2026-11-27; first structural cut in 2026-11-27, owner to decide whether it is enough -- see Progress).
**Owner:** TBD
**Where:** the jet-prime cache (`jet_prime_top` / `jet_prime_coh_core`):
the fill stage's read pointer -> the snoop front end's request
(`u_fab/u_snoop/u_transport/ac_channel/core_snoop_req`, fan-out 153) ->
the snoop probe (`r_sn_ref` / `r_sn_src`, `w_sn_thit`) -> the data array's
port-B address (`u_data/g_way[*].mem_reg_*/ADDRBWRADDR`).

## What was seen

Genesys2 reference rig, `REF_CACHE_SEL=3` (two jet-primes through
`jet_prime_pair_fabric`), 100 MHz with the 0.2 ns clock-uncertainty
budget:

| build | change | routed WNS | after post-route phys_opt |
|---|---|---|---|
| GO pass (common-ip BUG-001), 2026-11-27 | the harness GO | +0.252 ns | -- |
| jet-prime BUG-004, 2026-11-27 | two small terms in the pair fabric | -0.204 ns (10 endpoints) | +0.005 ns (shipped) |

All 10 failing routed paths start at
`u_ref{0,1}/u_coh/u_fill/u_stage/read_pointer_inst/counter_bin_curr_reg[0]_replica`
and end at a data-array `ADDRBWRADDR`: 19 logic levels, 85 % route
(9.533 ns, 1.451 ns logic). None is in the pair fabric the change
touched; the cache's own path moved with the placement of the design
around it.

## Open question

The owner's rule (timing must be predictable): WNS near zero is
placement noise, and a path that swings 0.46 ns between two builds of the
same cache is not closed. Whether to fix it structurally -- register the
snoop request before the probe (`core_snoop_req`'s 153 fan-out), or cut
the probe-to-address cone -- and what that costs the snoop-service
latency. Resolves to a task (the fix) or a recorded decision.
