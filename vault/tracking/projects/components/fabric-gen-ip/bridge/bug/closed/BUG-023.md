# BUG-023: a path's W destination FIFO overflows when a width converter issues several AWs per master burst

**Date:** 2026-10-21
**Priority:** P1
**Severity:** HIGH
**Status:** CLOSED 2026-10-22 (fixed; verified in sim and on the board)
**Owner:** unassigned
**Found by:** the Genesys 2 bridge stress model on the board (`build-axi4`, `bursts` seed 1, 2026-10-21, `reports/board/bridge_bs_axi4_20261021_151417.csv`), the first run after bridge BUG-018's converter fix; reproduced cycle-for-cycle in simulation
**Affects:** every generated crossbar: the per-(master, width path) W destination FIFO (`<m>_<w>b_wdest`) on any path that has a width converter

## Summary

Each write-capable master width path keeps a FIFO of which slave each
accepted AW targets; its head steers that path's W beats. The generator
sized it to the master's `max_outstanding` and gave it **no full check**, on
the argument that the master adapter never has more than `max_outstanding`
bursts in flight. That counts the MASTER's bursts. A width converter on the
path can issue several AWs for one of them: a > 256-beat downsize split, and
since bridge BUG-018 one AW per beat for a FIXED / WRAP burst wider than the
narrow path. The 17th live entry then overwrites the oldest, that path's W
beats go to the wrong slave, and the fabric hangs.

## Measured (board and sim agree exactly)

`bursts` seed 1, 4000 bursts per master direction: every write master stops
at ~680 (cpu.wr issued 682 completed 676; dma 541/534; acc 705/691; io
662/656), reads complete; mem0 `S_WDATA` / `S_WLAST` x226 and mem3 x597, first
at id 0x18 (dma) addr 0x044ae160. The same counts and first error come out of
`BS_PROFILES=bursts BS_TXNS=800 SEED=1` in simulation. A reference probe on
dma's 128 -> 64 write converter found its output correct, which put the fault
after it: dma's 64-bit path feeds mem0 and mem3, and its `wdest` FIFO was
16 deep with `dma_64b_awready` not gated on it.

## Why nothing caught it

The stress profiles ran at the 40-burst gate length in simulation; the
FIFO only overflows once enough expanded FIXED / WRAP bursts are in flight.
The converter's own tests are serial (one burst, then its B).

## Fix

`crossbar_generator.py`: the FIFO is full-checked, and `_aw_gate` -- the term
every AW path takes (request slot input, AWREADY, grant-on-entry request,
single-master grant, CDC lane) -- carries `!<path>_wdest_full`. A full FIFO
can only drain while an AW waits (it pushes on the handshake), so the gate
never drops a VALID it raised. Depth is clamped to >= 2. Regression:
`bin/tests/test_generator_pkg.py::test_w_dest_fifo_full_holds_the_aw` (fails
on the old generator). Every bridge regenerated (component batch and the
eight board-area regen scripts).

## Closes when

- `bursts` seed 1 x 800 replays clean in sim, and `bursts,narrow,chaos` x 1000
  on all five stress DUTs.
- The bridge component suite is green on the regenerated RTL.
- Board: `build-axi4` (and the other stress builds) every profile x 3 seeds.

## Resolution

All three "Closes when" items are met:
- Sim: `bursts` seed 1 x 800 passes, `bursts,narrow,chaos` x 1000 on all five
  DUTs passes, and every profile x 400 at SEED=3 passes.
- The bridge suite passes 511/512 on the regenerated RTL. The one failure is
  BUG-025, which fails on HEAD with DV 1.2.8 and with 1.2.9.
- Board, 2026-10-22, every stress build on bitstreams with the BUG-018/019/023/024 RTL (timing met on all five), every profile x seeds 1-3, 4000 bursts per master direction, no path limits (`bstress.path_caps` returns `{}`): axi4 30/30, axi3 30/30, axi5 30/30, xil 30/30, xmix 30/30 = 150/150 (`projects/fpga-systems/Genesys2/bridge-stress/reports/board/bridge_bs_*_20261022_*.csv`).
