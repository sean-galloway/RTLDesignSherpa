# BUG-025: bridge_2x2_lite_req concurrent AXI4-Lite write times out at SEED=65563

**Date:** 2026-10-21
**Priority:** P2
**Severity:** MEDIUM
**Status:** CLOSED 2026-10-22 (fixed in `axil_to_axi4_wide_align_wr`; verified in sim)
**Owner:** unassigned
**Found by:** the bridge component func regression (2026-10-21), on the BUG-018/023/024 tree
**Affects:** every bridge master port that goes through `axil_to_axi4_wide_align_wr`: an AXI4-Lite, AXI5-Lite or WB4 master writing to a wider slave. Found on `bridge_2x2_lite_req`

## Summary

`test_bridge_2x2_lite_req_concurrent[gate]` fails deterministically at
`SEED=65563`: `write m1 0x0000901C: AXIL4 write timeout after 1001 cycles`.
Other seeds pass (two random reruns did). It is not a regression of the
2026-10-21 work: the same seed fails on a `git archive HEAD` tree (before
the converter, BUG-023 and BUG-024 changes) with both RDS-DV 1.2.8 and
1.2.9.

Not yet known: whether the write is lost (a hang) or only slower than the
TB's 1001-cycle limit. Correct is either the write completing, or a limit
derived from the fixture's worst-case latency with the reason written down.

## Reproduction

```
cd projects/components/fabric-gen-ip/bridge/dv/tests
SEED=65563 python3 -m pytest -q -p no:rerunfailures \
  "test_bridge_2x2_lite_req_sideband.py::test_bridge_2x2_lite_req_concurrent[gate]"
```

## Root cause

A lost B, not a slow one. Traced in the SEED=65563 waveform on the AXI5-Lite
master's path (pins, `axi4_slave_wr` timing wrapper, `axil_to_axi4_wide_align_wr`,
crossbar, 64-bit memory):

| Point on the lite5 path | B handshakes |
|---|---|
| memory slave, BID=2 (lite5) | 8 |
| converter `m_axi_b*` (from the crossbar) | 8 |
| converter `s_axi_b*` (to the timing wrapper) | **7** |
| lite5 master pins | 7 |

The converter took Bs at 1060 ns and 1180 ns and passed on one B at 1200 ns.

`axil_to_axi4_wide_align_wr` registers each B in a one-entry register
(`r_s_bvalid`) and goes back to idle without waiting for the master to take
it, so the next write can reach `S_B` while that B is still held. Its
`m_axi_bready` was `(r_state == S_B)`, which ignores the register. So when
the master held BREADY low for longer than one write takes, the next B
overwrote the held one. The seed only decides the master BFM's BREADY
delays, which is why other seeds passed. The read twin is safe: its FSM
waits in `S_S` until the master has taken R.

## Fix

`m_axi_bready = (r_state == S_B) && (!r_s_bvalid || s_axi_bready)`: a new B
is taken only when the register is empty or drains in that cycle.

Regression: `converters/dv/tests/test_axil_to_axi4_wide_align_wr.py` is new;
the module had no unit test before.
- `b_backpressure`: six writes in flight, BREADY held 30 cycles after each
  BVALID.
- `lane_alignment`: every 4-byte slot of four wide rows.

Both run at 32 -> 64 and 32 -> 128. All 4 cells fail on the old RTL (Bs lost:
the BFM's default BREADY delays are enough) and pass with the fix. The
original reproduction passes at SEED=65563.
`verilator --lint-only -Wall` is clean.

The converters MAS ch2.7 now states the module's flow control (2.7.3), and
the handbook `design/valid-ready-contracts.md` records the rule.
