# BUG-016: a descriptor held in CH_FETCH_DESC emits a DESC_START MonBus packet every cycle

**Priority:** P2
**Status:** closed -- 2026-10-22; found 2026-10-21 while extracting scheduler_core (rapids TASK-034)
**Owner:** sean galloway

## Reproduction

`dv/tests/fub/test_scheduler.py::test_scheduler_pkt_backpressure[gate-0-8-512-default]`, with the
DESC_START count added to `SchedulerByteTB.test_pkt_backpressure`. The test holds
`sched_wr_pkt_ready` low for 60 cycles, so one descriptor waits in CH_FETCH_DESC. Result:
62 DESC_START packets for one descriptor (2026-10-21).

## Expected

One DESC_START per descriptor, however long it waits in CH_FETCH_DESC.

## Cause

`rtl/fub/scheduler.sv`, MonBus block: `r_mon_valid <= 1` on every cycle in CH_FETCH_DESC. Before
rapids TASK-019, CH_FETCH_DESC always lasted one cycle. The byte tree holds it while the data
paths' record queue is full (`!w_pkt_ok`), and TILE_CREDITS holds it until the advertisement
window closes (`w_tile_wait`, which can be thousands of cycles). Neither hold is rare.
The beats tree (`scheduler_beats.sv`) and STREAM's scheduler never hold FETCH, so they are not
affected.

## Fix

Emit DESC_START on entry to CH_FETCH_DESC. This lands with the scheduler_core extraction
(rapids TASK-034), which moves every per-state MonBus action to an entry pulse.

## Closed 2026-10-22

`rtl/fub/scheduler_core.sv` raises DESC_START on entry to CH_FETCH_DESC (`w_enter_fetch`) and
DESC_COMPLETE / IRQ on entry to CH_COMPLETE, for both `scheduler` and `scheduler_g`. Gate:
`SchedulerByteTB.test_pkt_backpressure` now asserts exactly one DESC_START per descriptor (it counted
62 before the fix). Product gate from clean, 0 failures: rapids fub 1,740, fub_beats 1,302, macro 843,
macro_beats 774, top 183, top_beats 54; STREAM fub 510, macro 684 (5 skipped), top 69.
