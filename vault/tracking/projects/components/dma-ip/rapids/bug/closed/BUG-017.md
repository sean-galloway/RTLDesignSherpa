# BUG-017: after a channel reset, the next EXT descriptor walks the reset descriptor's run bases

**Priority:** P2
**Status:** closed -- 2026-10-22; found 2026-10-21 by the rapids-g equivalence bench (rapids TASK-034)
**Owner:** sean galloway

## Reproduction

`dv/tests/fub_g/test_rapids_g_equiv.py::test_rapids_g_equiv[gate-4-256-reset_ext]`: on every channel an
EXT descriptor A (24 beats, inner_count 2, so 11 run bases) is held in CH_FETCH_DESC with its record
queue full, the channel is reset, then EXT descriptor B (different strides) runs. Checked against an
independent golden model (`RapidsGEquivTB.golden_cmds`), 2026-10-21:

- FSM scheduler (`rtl/fub/scheduler.sv`), channel 0, B's second read command: got `(0x1001000, 3)`,
  A's second run base; golden `(0x3FFFFF00, 3)`. B's read sequence is 7 commands, golden 8.
- `scheduler_g` (firmware bases, FIFOs flushed outside FETCH/XFER): matches the golden.

## Cause

`stream_run_addr_gen` (`projects/components/utility-ip/misc/rtl/`) is started once, on entry to
CH_FETCH_DESC with an EXT descriptor, and then generates every base of that descriptor into its
4-deep FIFO. Nothing stops it or empties the FIFO on a channel reset (only `rst_n` does). The
scheduler's counters are cleared by the reset, but the generator keeps its position and queue, and
the next EXT descriptor's `start` resets the position, not the FIFO: B's first base(s) are A's.

## Scope

Same generator, same hookup, no flush: `rtl/fub_beats/scheduler_beats.sv` (RAPIDS Beats) and STREAM's
`rtl/fub/scheduler.sv`. There CH_FETCH_DESC lasts one cycle, so the exposure is a reset during
CH_XFER_DATA of an EXT descriptor; not yet reproduced in those trees.

## Fix (proposed)

A `flush` input on `stream_run_addr_gen` that empties the FIFO and stops generation; each scheduler
drives it with its channel reset. Tie-off 0 keeps today's behaviour for any other user.

## Closed 2026-10-22

The proposed fix landed: `stream_run_addr_gen` has a `flush` input (stop and empty the FIFO; a
`start` during or right after a flush loses nothing of the new descriptor; tie 0 for no flush). The
channel reset drives it in all three schedulers that use the generator: `rapids/rtl/fub/scheduler.sv`,
`rapids/rtl/fub_beats/scheduler_beats.sv` and `stream/rtl/fub/scheduler.sv`. Gate:
`test_rapids_g_equiv[*-reset_ext]`, where RAPIDS's scheduler now matches the golden model at 4 and 8
channels; the product gate from clean (rapids byte, beats and STREAM, 0 failures, counts in
rapids BUG-016) shows no change elsewhere.
