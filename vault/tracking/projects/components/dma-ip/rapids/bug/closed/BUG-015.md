# BUG-015: snk_data_path_axis stress stall -- the TB descriptor-take wait raced an idle FSM

**Priority:** P3
**Status:** closed -- 2026-10-18
**Owner:** sean galloway

## Reproduction

`dv/tests/macro/test_snk_data_path_axis_test.py::test_stress[func-8-64-256-8-4096-default]`,
`REG_LEVEL=FUNC SEED=13275`. The test passes, but the log shows the AXIS
master's `TIMEOUT waiting for ready after 1000 cycles` 114 times on the HEAD
scheduler (2026-10-18, before rapids TASK-028) and 76 times with the
descriptor skid; with `send_descriptor(wait_taken=True)` a channel's
scheduler also fails to take a paced descriptor within 20000 cycles (32 and
20 times). Seen at gate, func and full across configurations.

## Expected

With each descriptor taken by its scheduler before its data is sent, the
head AXIS beat always belongs to a channel holding its packet record, so
the ingress should accept it within the transfer time; no ready timeout and
no dropped beat.

## Root cause (2026-10-18, measured from waves at SEED=13275)

The stall is not a short BFM timeout. All 71 `tvalid && !tready` runs at the
ingress last exactly 1000 cycles, and in every one the head beat's channel is
in `CH_ERROR`, which is sticky. Only 6 AW and 34 W handshakes complete in
406k cycles; every BRESP is OKAY.

The chain:

1. The test helper `_wait_desc_taken` sampled `sched_state` AFTER
   `master.send` returned and waited for the FSM to pass through `CH_IDLE`
   and leave it. An idle FSM pops the descriptor skid within a clock, so at
   cycle 110 ch7 had already gone IDLE -> FETCH -> XFER before sampling
   began. The helper then waited for an IDLE that only comes after the
   data, which it had not yet sent: a deadlock broken only by the helper's
   20000-cycle timeout.
2. `snk_data_path_axis_test.sv` ties `cfg_sched_timeout_cycles=1000`,
   `cfg_sched_timeout_limit=1`, so ch7 escalated to sticky `CH_ERROR` at
   cycle 1113.
3. Every later ch7 beat then holds the shared ingress (`s_axis_tready` low),
   the AXIS BFM drops it after 1000 cycles, and the stall spreads: by cycle
   223748 all 8 channels are in `CH_ERROR`.

The earlier "predates the skid" A/B ran the HEAD scheduler under the same
helper, so it measured the helper on both sides. This is a test defect, not
an RTL defect.

## Fix

`_wait_desc_taken` now counts `CH_IDLE` exits per channel in a background
sampler started before the send, and waits for the count to pass the value
taken before `master.send`. SEED=13275 then shows 0 ready timeouts and 0
missed takes, and runs in 44 s instead of 150 s.

## Still open

- The stress test checks no memory, so a dropped beat cannot fail it.
- The wrapper's 1000-cycle, escalate-after-one timeout turns any pacing
  slip into a whole-ingress cascade.

## Notes

- The stress test picks random channels and random addresses up to 4 MB
  into each channel's window, waits 10-30 cycles between operations, and
  scores only whether a send raised; it checks no memory, so the BFM's
  dropped beats never fail it.
- (As filed; superseded by the root cause above.) "Not caused by the skid" and the
  first-step guess were both wrong: the A/B ran the same faulty helper on both sides.

## Closure (2026-10-18)

Test defect, fixed in the TB (`_wait_desc_taken` counts CH_IDLE exits). snk_data_path_axis_test from clean builds: func 116/116 and full 174/174 pass with 0 missed takes and 0 AXIS ready timeouts. Full still shows 4 descriptor-port ready timeouts per multi_channel_operation cell: it queues 4 descriptors per channel and sends no data, and the wrapper's port holds 3 (FSM + 2-deep skid). That is correct backpressure the test ignores, not a stall; with the two items under Still open it is test hardening, not part of this bug.
