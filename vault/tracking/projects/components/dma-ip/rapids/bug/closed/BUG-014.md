# BUG-014: snk_data_path_axis channel-reset block clobbers a HEALTHY channel's same-cycle output-register load and flush registration

**Priority:** High -- silent data loss in the product byte tree: an accepted
stream packet's memory beat (and its spill flush) can vanish, with the
packet-record queue left holding a record whose data never reaches the fill
interface.
**Status:** CLOSED 2026-10-02 (fix + verification below; commit lands with
TASK-022 DIR 1)
**Owner:** Claude (TASK-022 formal proofs)

## Mechanism

Found by the new TASK-022 port-level formal harness
(`formal/rapids/snk_data_path_axis/`), property `ap_tready_needs_record`,
BMC counterexample at step 4 -- 24 hours after the harness's first run, on
the FIRST property batch. The macro-level proof approach is vindicated.

`snk_data_path_axis.sv:355-371`: the per-channel reset loop runs last in the
always block "so it wins over every update above", and clears the shared
output register / flush flag by comparing the RESETTING channel against the
**stale** `r_out_id` / `r_flush_ch`:

```systemverilog
if (r_out_id == ch[CIW-1:0])   r_out_valid   <= 1'b0;   // :366
if (r_flush_ch == ch[CIW-1:0]) r_flush_valid <= 1'b0;   // :369
```

But `r_out_valid` / `r_flush_valid` may have been loaded **this same edge**
with a *different, healthy* channel's beat (`:325-353`, the flush-load and
`w_in_accept` branches). The reset block then kills the freshly-loaded beat
because the OLD id happened to equal the resetting channel.

## Counterexample (from the BMC trace)

`r_out_id`/`r_flush_ch` reset to 0, so at boot the window is wide open:

1. `cfg_channel_reset[0]` pulses (ch0 in its 2-cycle `w_rst` window).
2. Same window: ch1 accepts a tlast beat with offset 5 + 4 bytes = spill
   (`w_in_accept`, `w_pkt_done_now=0`, spill into hold). The accept branch
   loads `r_out_valid<=1` (ch1's memory beat) and `r_flush_valid<=1`
   (ch1's pending flush), `r_out_id/r_flush_ch<=1`.
3. The reset block for ch0 sees stale `r_out_id==0` / `r_flush_ch==0` and
   clears both valid flags.
4. Result: ch1's memory beat never enters the out register, the flush is
   never registered, `w_pkt_done_flush` never fires, ch1's packet record
   never pops. The stream beat WAS consumed (`tready` was high) -- the
   bytes are gone.

The same-edge accept/flush-load for the healthy channel is clobbered through
two paths (`:366` out-reg load, `:369` flush registration); the flush path
additionally loses the PQ pop, so the record wedges.

## Fix

Gate both clears on "no same-edge load for another channel":

```systemverilog
wire w_load_flush = r_flush_valid && w_out_free;
wire w_load_any   = w_load_flush || w_in_accept;
wire [CIW-1:0] w_load_id = w_load_flush ? r_flush_ch : w_in_ch;
```

- `r_out_valid` clear fires only when `!(w_load_any && w_load_id != ch)`.
  (`:368`, the flush-load-of-resetting-channel clear, is subsumed by this
  and removed.)
- `r_flush_valid` clear fires only when no same-edge flush set
  (`w_in_accept && s_axis_tlast && spill`) -- a set always targets
  `w_in_ch`, which cannot be in reset (tready gates it).

## Scope check

`macro_beats/snk_data_path_axis_beats.sv` has no `cfg_channel_reset` and no
per-channel reset block at all (per-channel reset is a byte-tree feature),
so the pattern cannot exist there. Nothing to port.
