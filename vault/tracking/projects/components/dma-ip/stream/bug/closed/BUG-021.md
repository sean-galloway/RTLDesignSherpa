# BUG-021: after a channel reset, the next EXT descriptor walks the interrupted one's run bases

**Status:** CLOSED 2026-10-21 -- the same defect as rapids BUG-017 (shared `stream_run_addr_gen`), fixed in all three schedulers together
**Priority:** P2
**Filed from:** rapids TASK-034 (the rapids-g equivalence bench found it in the byte-granular RAPIDS)

## Reproduction

`dv/tests/fub/test_scheduler.py::test_scheduler_extended[cocotb_test_scheduler_ext_channel_reset]`:
EXT descriptor A (16 beats, inner_count 2) is reset after its second read; EXT descriptor B then runs.
Before the fix B's reads were `0x60000, 0x40400, 0x40600, 0x40800` -- from the second on, A's run bases --
against `0x60000, 0x60400, 0x60800, 0x60c00`.

## Cause

`stream_run_addr_gen` is started on entry to CH_FETCH_DESC and generates all of its descriptor's bases into a
4-deep FIFO; only `rst_n` emptied it. A channel reset cleared the scheduler's counters but not the generator.

## Fix

`stream_run_addr_gen` has a `flush` input: generation stops, results in flight in `dma_address_gen` are
discarded, and the FIFO (now `gaxi_drop_fifo_sync`) is dropped whole. STREAM's scheduler drives it with
`r_channel_reset_active`, as do the RAPIDS and RAPIDS Beats schedulers. STREAM full regression from clean
passed with the fix and the new cell (2026-10-21).
