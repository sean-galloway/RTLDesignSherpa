# BUG-031: granite on the Nexys A7 completes every write and no read; the same host, harness and PHY read fine under the pumice bitstream

**Priority:** P1
**Status:** closed (2026-10-24, root cause a double continuous driver in `mc_rd_intake`; fixed, flow gate added, verified on the Nexys A7 by leveled init + write_read + 128 MB memtest)
**Owner:** TBD
**Filed:** 2026-10-24 (pumice TASK-058 item 3, the first silicon run of granite since the 2026-10-12 bring-up)
**Repro:** program `targets/granite/fpga/bitstream/ddr2_char.bit` (any of today's builds), then `run_smoke.py --board nexys_a7_100t --controller granite --no-leveling --sequences init write_read`: init PASS in 0.7 s, `write_read` FAIL after one 15 s engine wait with `mismatched=0 crc exp=0 act=0`. With leveling on, the sequence is silent for hours: every one of the 256 (bitslip, tap) points times out twice.

## Symptom

On the board, `STATUS.init_done` = 1, `init_error` = 0 within a second of
`soft_reset`. Writes complete and stream at the expected rate (64 x bl8 in
2 139 cycles, 512 beats produced). A read of any length (bl1 x1, bl8 x1,
after a write of the same address or not) never asserts `rd_done`: the
read meter shows 0 beats produced and the read bus starved for the whole
wait; the harness timer shows the read window opened (`r_first` set) and
never closed.

## What is NOT the cause (measured)

- Host, harness, UART, PHY, board: the pumice bitstream from 2026-10-23
  (`build-perf/fpga/bitstream/ddr2_char.bit`), driven by the same host in
  `--controller pumice` mode, passes every cell of the same probe (reads of
  both lengths, writes of 1 / 2 / 4 / 64 transactions, write-then-read).
- Read-FIFO depth 4 (TASK-055): a build with `GRANITE_DFI_RD_FIFO_DEPTH=16`
  fails identically (WNS +0.250).
- The same-clock DFI crossing (TASK-053): a build with `GRANITE_DFI_CDC_EN=1`
  (the async form back) fails identically (WNS +0.187).
- Timing closure: every build above met timing with 0 failing endpoints; the
  board XDC has no false path or clock group that touches the DFI or read
  return path (the only ones are reset, UART, LEDs and the `bank_lsb` CSR).
- Simulation cannot show it: the granite UART smoke test and the granite
  proxy pass with the PHY model in STRICT read timing (rddata_en-anchored
  return) at both the sim tuple and the board tuple (wrlat 1, rddata_en 6,
  rddata_delay 7, read latency 8), at read FIFO 4 and 16. The sims that
  gated TASK-050 through TASK-057 all ran the model's default, non-strict
  mode, where read data returns command-anchored and rddata_en is ignored.

## Root cause

`mc_rd_intake.sv` (TASK-054) drove `map_req_o` twice: a common
`assign map_req_o = map_req_o_int;` and, inside the `HAS_ADDR_MAP` generate
branch, `assign map_req_o = 1'b0;`. Two continuous assigns on one net are
legal Verilog (wired resolution). Verilator lints the file clean (5.045,
`-Wall`) and keeps one driver; the net is dead in the board configuration
(the plane only reads it under `SHARED_ADDR_MAP`), so every simulation was
right. Vivado reports it:

```
CRITICAL WARNING: [Synth 8-6859] multi-driven net on pin map_req_o with 1st driver pin 'u_axi_plane/u_rd_intake/u_slave_rd/i_ar_channel/g_skid.rd_valid_reg/Q'
CRITICAL WARNING: [Synth 8-6859] multi-driven net on pin map_req_o with 2nd driver pin 'GND'
```

With `map_req_stage_ok` constant 1 the first driver is the AR skid's valid
itself, so synthesis had merged `map_req_o` with `fub_arvalid`, then
resolved the conflict to GND: the read intake never saw an AR, no READ was
ever admitted, and `rd_done` never rose. The write intake drives the same
output only inside its generate branches, which is why writes streamed at
full rate throughout. The warning is in every build log since TASK-054
(four reports per build) and in none before; the flow printed it and did
not fail.

## Fix

- `mc_rd_intake.sv`: one driver per branch -- the `HAS_ADDR_MAP` branch
  keeps `map_req_o = 1'b0`, the shared-map branch takes
  `map_req_o = map_req_o_int`, the common assign is gone.
- `make/fpga_flow.mk`: `_multidriven_scan` beside the peer's undriven scan;
  `make bitstream` and `make synth` now FAIL on `Synth 8-6859` (0 reports in
  every build before TASK-054, 4 in every build after, in the same logs).
- Handbook `design/generated-rtl-discipline.md`: the rule, beside today's
  undriven-net lesson.

Sim after the fix: granite UART smoke 1 / 1, granite suite 6 / 1 xfail,
granite proxy std_n1 cycle-identical to the grid (the net was dead in sim,
so no sim can move). Board after the fix: the fixed text built (WNS +0.134, 0 multi-driven
reports in its synthesis log), programmed and probed: single reads of both
lengths and every write complete; then the real smoke -- leveled init PASS
(the 256-point sweep in 301 s), `write_read` PASS with mismatched 0, 128 MB
memtest PASS 32 / 32 chunks clean. Fixed-text core: 5 631 LUT / 3 532 FF
against 3 939 / 2 567 for the broken build -- the difference is the read side
of the store, the return ring and the intake that synthesis had folded away
behind the grounded valid, which is why every board figure quoted in
TASK-054..057 is corrected to this trend (TASK-053 text 6 090 / 4 417).

The break is inside TASK-054 (linked-list bank queues, circular fill FIFO,
lean intakes). Its knob-selectable parts are cleared on today's text:
`HAS_SNARF=1`, `INTAKE_FIFO_DEPTH=16 AXI_SKID_DEPTH=4`, `STORE_BACKEND=0`
(the entry store under the TASK-054 AXI plane) all fail identically. Next:
TASK-054 split in two worktrees, one with TASK-053's AXI plane / intakes /
core wiring on the TASK-054 store, one with TASK-054's text and the
TASK-053 store.
