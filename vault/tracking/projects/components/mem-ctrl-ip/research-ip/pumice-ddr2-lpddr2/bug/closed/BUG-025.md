# BUG-025: OBS_ROW_HIT counters read zero — BUG-020 regression net was dark (vacuous pass)

> Source: mc_init_plane work, 2026-10-15. Surfaced when the vacuous-pass
> window in test_pumice_top.py was fixed (the repo conftest's BUG-015 anchor
> re-escaped the file's own `$` testcase suffix, so every cell in the file ran
> ZERO cocotb tests and reported pass).
> Related: BUG-020 (the fix this test regresses), tooling BUG-015.

**Priority:** P2
**Status:** closed
**Owner:** TBD

## Symptom

`test_pumice_top.py::test_pumice_top_row_hit_counters` fails:

```
AssertionError: OBS_ROW_HIT[8] counted ZERO row hits across 64 column ops
with only 64 activations, under static_open with refresh parked. The
counters are not driven -- this is pumice BUG-020 returning.
```

## Why it went unseen (the important part)

The failure is **pre-existing**, proven at 6d0e797 (pre-init-plane) in an
isolated worktree with the testcase-anchor fix applied: identical failure.
`test_pumice_top.py` cells were vacuously passing — `_run` passed
`testcase=f"{name}$"`, the conftest anchor wrapped it with `re.escape`, the
`$` became a literal-dollar regex, COCOTB_TEST_FILTER matched nothing, cocotb
ran zero tests, cocotb-test reported PASS. Every ~183 cell in the file was
affected for as long as the anchor has existed. This cell's last REAL
execution predates that window.

## What is known

- Chain: `mc_page_policy.stat_row_hit_o` → `mc_scheduler_plane` (g_page_policy,
  HAS_PAGE_POLICY default) → `pumice_core.stat_row_hit_o` →
  `pumice_top` `hwif_in.OBS_ROW_HIT[b].ROW_HIT.VAL.next` → generated CSR.
- pumice_core.sv:306 connects the plane output; pumice_top.sv:149 drives the
  hwif. Wiring is present at both hops (inspected 2026-10-15).
- The mc_init_plane extraction (Tasks 1-3 of the init work) did NOT touch this
  chain, and the CSR regen for LP_MR1/2/3_OP added only the three new
  registers (readback array 66→69 entries) — verified by git diff of
  pumice_csr.sv.
- The stimulus produces 64 activations / 64 column ops (per the assertion),
  so the pattern does open rows; the counters still read zero.

## Suspects (unverified)

1. `mc_page_policy` row-hit counting never fires for this command stream
   (count condition vs. the common-plane command timing).
2. The generated CSR block's `hwif_in` row-hit fields are not readback-connected
   (compare the RDL's OBS_ROW_HIT regfile `hw=w` field against the generated
   `pumice_csr.sv` readback mux — the field may need `hw=r`/`hw=rw` semantics
   or an explicit next→value path the map doesn't emit).
3. `program_defaults` or `_bringup` programs a paging mode that precharges
   before reuse despite the test's static_open intent (the test docstring
   records two earlier instances of this exact self-defeat).

## Reproduce

```
source env_python && export PYTHONPATH="$(pwd)/bin"
python -m pytest \
  projects/components/mem-ctrl-ip/research-ip/pumice-ddr2-lpddr2/dv/tests/top/test_pumice_top.py::test_pumice_top_row_hit_counters -q
```

Closes when the counters move and agree with the global arithmetic, and the
suite is green with the anchor fix in place.

## Resolution (2026-10-20) — CLOSED (collateral of BUG-027)

The counters were never broken. With CLOSE_ON_DRAIN active (BUG-027),
every row was auto-precharged after ~8 columns, so the test's 64 column
ops were all misses — 64 activations, zero row hits, OBS_ROW_HIT reads
zero. With `CLOSE_ON_DRAIN=0` (the BUG-027 fix) the same stimulus
produces row hits and the counters move as the arithmetic expects. The
suspects listed above (count condition, CSR readback wiring, paging-mode
self-defeat) are exonerated by the pass.
