# BUG-033: pumice reads return wrong data with FAST_RD_RELEASE on -- windows random_bl8, ~1 run in 3 at 50 MHz

**Priority:** P1 -- silent data corruption on the board's shipping point.
**Status:** closed 2026-11-07 -- root cause fixed in `e91fb524e` (the scheduler
plane's fast-release token accounting lost a token when a slow token matured
in the same cycle as a fast push; one command then sat in the output FIFO
with no token and every command left only on the next push, so a REF waited
for the ACT behind it). Confirmed on the board: 16 of 16 interleaved runs
clean on the fixed sys50 bitstream (8 with the bit on, 8 off), where every
earlier build failed a bit-on run by run 4 or 5. See "Closed" below.
**Owner:** TBD
**Filed:** 2026-11-04 (found under pumice TASK-047's board run, 2026-11-03)
**Repro:** Nexys A7, `build-perf`, `PUMICE_SYS_50=1`, HEAD text (`FAST_RD_RELEASE = 1`,
on since `bfc3cbf7a` 2026-10-31), host `PUMICE_MC_CLK_HZ=50000000`,
`make run SEQUENCES="init char" RUN_ARGS="--profile windows --txn-scale 4000"`.
About one run in three: `open_page/random_bl8` NOT OK ~5,900-6,200 beats and
`close_page/random_bl8` NOT OK ~4,700 beats (occasionally `close_page/mixed_bl8`
8,258 or `close_page/row_thrash_bl8` 10,661). Bandwidth is unchanged; only data
is wrong. Expected: 0 mismatched, as on the 2026-10-27 bitstream.

## What the option does

`mc_scheduler_plane` delays every command CMD_DELAY cycles so a WRITE's data
reaches the DFI first. With FAST_RD_RELEASE, `r_fast` is set after the command
line has been empty for CMD_DELAY + the largest programmed timing; while set,
commands bypass the delay; a WR push clears it and takes the full delay.
Granite has run it at 75 / 100 MHz on every profile with 0 mismatches
(`ff8c64d18`), so the failure needs pumice's path (FR-FCFS arbiter + CAMs) or its
50 MHz board point.

## Root cause and fix (2026-11-07)

Found by reading the capture against the arbiter rather than the release. Two
things in the decode settle where the compression happened: the token-shift
probe (`g_cmd_delay.r_tok_shift`) is 0 at every sample, so the whole window ran
in fast mode and the wire spacing IS the arbiter's fire spacing; and the same
REF-then-ACT-at-+2 shape appears a second time in the same capture (REF at
-418, ACT b3 at -416, that bank's reads returning all-ones at -407..-405). So
the arbiter fired the ACT two cycles after the REF, and nothing downstream
moved either command.

The hole, in `mc_cmd_arbiter` (pumice's `SCHED_CORE=0`; scoria and andesite
wrap the same core, granite's `mc_bank_pick` is pick==fire and does not have
it):

- `r_rfc_cnt` loads on `w_fire_out && r_grant`, i.e. the cycle AFTER the REF
  leaves the output register. In the REF's own fire cycle `w_rfc_busy` is 0
  and `w_act_gate_live` is open.
- That cycle was shielded only by the pick chain's refresh branch
  (`else if (refresh_req_i || refresh_drain_i)`), which picks nothing while
  `r_grant` is set. The 2026-09-09 fix for this exact two-cycle signature
  ("an ACT selected in the one cycle between tRFC expiring and the next REF
  firing") re-checked `w_rfc_busy` live at the pick -- a counter that has not
  loaded yet in that cycle.
- `mc_xddr2_refresh_ctrl` requests a PULL-IN refresh as a function of idle
  (`w_req = ... w_idle && pullin < limit`), and `w_idle` resets the cycle
  `demand_i` returns. A read landing in the cycle the REF is picked drops
  `refresh_req_o` in the cycle the REF fires. The demand branch runs, the
  ACT is picked at counter 0 and leaves one cycle behind the REF (two DFI
  cycles on the wire with the phase placement). tRFC 7, the DRAM drops the
  ACT, and bank 7 reads an undriven bus until its next ACT.

Why it tracked the fast-release bit: the release does not touch the arbiter,
it moves when read DATA returns, so it moves when the generators' next
requests (demand) return relative to the idle-confirmed pull-in REF. The
`windows` pattern at 50 MHz with the bit on lands on the one-cycle coincidence
about once in three runs; with the bit off the same traffic does not, in the
samples taken (0/8, 0/8). The option exposed the hole; it did not create it.

The fix (`mc_cmd_arbiter.sv`): the granted REF / REFpb sitting in the output
register counts as the first cycle of the tRFC window --
`w_ref_inflight = r_pick_valid && r_grant`, ANDed into `w_act_gate_live`
(stage-1b pre-pick, the final pick and the TASK-047 row lane all read it).
The tZQCS branch of the pick chain gets the same term for a granted ZQCS
(`r_zqcs_cnt` loads the same way). Zero cost: in the normal case that cycle
was already a bubble (the refresh branch with `r_grant` set picks nothing).

Evidence:

- `formal/mc_common/mc_cmd_arbiter` gained `a_trfc_spacing` (parameter
  `BUG033`, armed for every task like `ISSUE019`): the wrapper times REF to
  ACT itself, `t_rfc_i` a bounded constant, `refresh_req_i` free. Pre-fix
  RTL: FAIL at step 6 -- the trace is the board's (step 4: `r_grant=1`,
  `cmd_ready_i=1`, `refresh_grant_o=1`, `refresh_req_i=0`, `r_rfc_cnt=0`,
  `w_valid=1 w_do_act=1`; step 5: `evt_act_o=1`, `r_rfc_cnt=6`). Fixed RTL:
  `prove` PASS to depth 30 with ISSUE019 still armed; `cover` reaches a REF
  followed by an ACT at tRFC+3 (the earliest the pre-pick register allows);
  `dual` / `dual_cover` (row lane built) pass.
- Char-harness sim, board geometry (`families_x16`, `windows` profile, txn
  scale 1, 21 min each) with the DFI-wire scoreboard armed

## Root cause, second and final: the DFI command CDC FIFO stalls the stream (2026-11-07 midday)

The capture that settled it (`assets/bug033_ila/ila_arb_r2.*`, the ILA bitstream
with the fix of `f2f7b15ff` and the arbiter's registers probed by EXACT net
name -- `r_rfc_cnt[7:0]`, `r_grant`, `r_pick_valid`, `r_do_act/pre`,
`r_rd_issue`, `r_op[3:0]`, the refresh controller's `r_pending`/`r_pullin`;
see [[build-flows]] for why the first probe set was wrong). Failing run,
trigger on the reader's first mismatched beat, arbiter time vs wire time:

```
arbiter fire                      wire (DFI boundary)
 -45  PRE  b1                      -35  PRE b1          latency 10
 -41  REF  (grant=1, op=REF)       -24  REF             latency 17
 -40..-33  r_rfc_cnt 7,6,...,0
 -30  ACT  b1 (counter 0: legal,   -22  ACT b1          latency  8
       11 cycles after the REF)
 -28..-24  RD x5                   -21..-17 RD x5       latency  7
```

Every refresh in every capture is followed on the wire by an ACT two cycles
later, in passing stretches as well as failing ones (`ila_fix_r4`,
`ila_fr1_r3`): the DRAM tolerates the violation most of the time, which is the
"one run in three". The arbiter is right every time; the stream is compressed
downstream of its fire. The idle refresh capture (`ila_arb_refidle_decoded.txt`)
gives the undisturbed fire-to-wire latency: 7 cycles (grant at -7, counter
7..1 while the REF travels, REF on the wire at 0).

Where the stall is: pairing fires with wire commands over the whole capture,
every 8-read burst (random_bl8 = eight columns per row) shows the first seven
reads at latency 7 and the EIGHTH at 12; the PRE and REF queued behind it are
delayed 3 and 10 and then everything drains back to back. The scheduler's
own output FIFO (16 deep, `mc_scheduler_plane` u_cmd_fifo) absorbs the stall,
so the arbiter never sees `cmd_ready` drop and keeps its spacing exact -- in
its own time. The stall itself: `mc_dfi_cdc` carries the command stream to the
DFI side through `gaxi_fifo_async` at the plane default `CMD_DEPTH = 8`. The
read pointer reaches the writer through a registered Gray pointer, two
synchroniser flops and a registered full flag (~4 ctl cycles), and a write
reaches the reader the same way; on a burst at one command per cycle the
writer's view of the FIFO holds every command written minus the pops it has
seen, which is ~8 before the first pop is visible. Depth 8 is exactly the
number that fills, so the 8th command waits until the first pop arrives
(~5 cycles), and the burst behind it bunches. The ddr2 char harness ties
`dfi_clk` to `mc_clk` with `DFI_CDC_EN = 1`, so this is a same-clock design
paying async pointer latency.

Why the fast-release bit selected it: with the uniform CMD_DELAY the reads'
data returns 6 cycles later relative to the arbiter, the injectors (whose
request rate is latency-bound: read latency measured 6.0 cycles lower with
the bit on, bandwidth identical) issue less densely, and a row's eight reads
do not arrive at the CDC back to back. The bit does not touch the FIFO; it
makes the bursts dense enough to fill it. The 10-27 bitstream predates the
release entirely.

Why the sim did not show it: both char sims of the `windows` profile with the
DFI-wire scoreboard armed found nothing. The loopback's read latency and the
UART-driven generators do not produce the board's eight-deep bursts at one
per cycle; the compression needs the burst. `mc_dfi_cdc` now counts its
command-side stalls (`r_cmd_stall_cnt/_max`, `final $display` like the
write-staged hold in `mc_dfi_cmd_path`), so a sim that does produce the burst
reports it even when no JEDEC window happens to be behind the stall.

Candidate fix, REFUTED as the cause (same day): `pumice_core` parameter
`DFI_CMD_FIFO_DEPTH = 32` passed as the plane's `CMD_FIFO_DEPTH` (kept as
margin; the netlist of the fixed build carries 6-bit pointers, i.e. the depth
did change). The pointer-latency arithmetic behind it was wrong: the CDC
formal's new LINERATE task proves depth 8 streams a 24-command burst with no
write-side stall. Soak #2 on that
bitstream: bit on failed run 4 of 4 so far with the same signature (open_page
/ close_page random_bl8 5,955 / 4,711, close_page mixed 15k, close_page
row_thrash 10,666), bit off 0 of 3. So the ~5-cycle stall on the eighth read
is elsewhere between the scheduler's fire and the DFI boundary: the
scheduler plane's token release, the plane's own output FIFO, the DFI command
path's read gate (`rd_op_ready_i`, aligner `MAX_OUTSTANDING` = 64 on this
build) or the formatter. The TASK-007 note in `mc_dfi_cmd_path` ("the CDC
command FIFO preserves ORDER but not SPACING -- any stall here silently
rewrites the interval between every command queued behind it") names the
class; the stage is what ILA build #3 measures.

Follow-up, not done here (owner's call): the pumice char harness
(`ddr2_char_macro`) ties `dfi_clk` to `mc_clk` and leaves pumice_top's
`DFI_CDC_EN = 1`, so the board pays the async crossing's latency (7 cycles
scheduler to DFI pins) on one clock. Granite's harness sets `DFI_CDC_EN = 0`
(synchronous FIFOs, where its command depth of 4 is sound) -- which is why
granite never saw this. `granite_core` now guards its command depth to 32
for any crossing build the same way it already guards the write-data and
read-return depths. Switching the pumice harness to `DFI_CDC_EN = 0` would
remove the stall class entirely and shorten the command path; it changes the
board point, so it is a separate item.

## Root cause, third and real: a lost release token in the scheduler plane (2026-11-07, 14:45)

ILA build #3 probed the queues between the arbiter and the pins
(`ila_queues_fail_r1`, failing run): the scheduler plane's output FIFO
write pointer advances with every arbiter fire; the CDC command FIFO's
write-side view advances 3 cycles after each fire and its read-side view 4
cycles after that, for every entry including the REF; the read aligner's
outstanding count never exceeds 9 of 64; `r_fast` = 1 throughout; and
`r_tok_cnt` = 0 at EVERY sample, through bursts of eight back-to-back reads.
ILA build #4 added the formatter output, pumice's registered DFI outputs and
the harness delay stage, and a trigger on the arbiter's refresh grant with
reads outstanding (`capture_ila.tcl` mode `refarb`) caught a refresh amid
traffic in a PASSING run (`ila_stages_pass_refarb`): grant at 0, counter
7..0, REF at the formatter at 6, on the pins at 7, the ACT fired at 11 and
on the pins at 18 -- the eleven-cycle spacing intact -- and `r_tok_cnt`
reading 1 during bursts.

That difference is the mechanism. The plane's fixed-delay release
(`mc_scheduler_plane` `g_cmd_delay`) counts tokens, not entries: a push in
fast mode matures a token immediately, a push in slow mode drops a token
into a CMD_DELAY-deep shift, and the FIFO head is released when the token
count is non-zero or a token matures this cycle. Tokens equal entries, and
the release is immediate. If the FIFO ever holds one entry MORE than there
are tokens, that entry is released only by the next push's token, the pushed
command inherits the orphan role, and every command thereafter leaves at the
next command's arrival: one cycle behind in a burst, and -- for the last
command before a gap -- exactly when the next command comes. The last PRE of
a drain waits for the REF; the REF waits for the ACT the arbiter spaced
tRFC later; the two leave one cycle apart (two on the wire with the phase
placement). `r_tok_cnt` stays 0 because every push's token is consumed by
the head in the same cycle. The failing captures' "eighth read of every
burst at latency 12" was this: the burst's last read leaving at the next
burst's first push.

How the orphan is made: `w_tok_mature = r_tok_shift[CMD_DELAY-1] ||
(w_cmd_push && w_fast_now)` -- the slow shift's output and a fast push ORed
into one token, and `r_tok_cnt` incremented by one. Two tokens maturing in
one cycle lose one. The design argued the collision cannot happen because
"in fast mode the shift register is empty": `r_fast` sets only after the
line has been idle `r_smax` cycles. But `r_fast <= 1` is evaluated on
`r_idle >= r_smax` registered, so a push landing in the very cycle `r_idle`
reaches `r_smax` is a SLOW push (`r_fast` still 0) whose token enters the
shift -- and `r_fast` is 1 the next cycle with that token in flight. Six
cycles later it matures; a fast push in that cycle (a burst is one per
cycle) collides. The alignment needs an idle gap of exactly `r_smax` + 1
cycles ending in a command, which the `windows` profile's latency-bound
injectors produce every few hundred gaps: one run in three gets an orphan
early and corrupts from then on, the rest never do. With the bit off there
is no fast mode, no shift-plus-fast collision, nothing to lose.

Fix (`mc_scheduler_plane.sv`): `w_tok_matured` counts both maturities (0, 1
or 2) into `r_tok_cnt`, so a collision banks the second token instead of
dropping it; and `r_fast` sets only on an idle cycle (`&& w_line_empty`), so
the state "a slow token in flight in fast mode" no longer exists -- the
invariant the comment claimed is now enforced by the condition that sets the
mode. Either alone closes the hole; both together make the accounting
independent of the mode logic.

Why the sims never saw it: the loopback's generators do not produce the
`r_smax`+1 idle gap followed by a burst; the hazard is one cycle wide in
idle length and needs the burst to reach the shift's output cycle. A sim
check that does not need the alignment: the plane's FIFO occupancy minus
pending tokens (`r_tok_cnt` plus the shift's population) must be zero
whenever the line is quiet; an orphan makes it one for the rest of the run.

Why the board still produces REF then ACT inside tRFC with the arbiter hole
closed. The two-cycle wire gap in capture 3 is one cycle wider than the hole
explains (REF fires at F, the counter loads at F+1, the hole's ACT fires at
F+1), so the ACT that reaches the wire two cycles after the REF was picked at
F+1 with `w_rfc_busy` reading 0 -- which means either the counter did not load
(the REF on the wire was not a granted REF, or `t_rfc_i` at the arbiter was
not 7), or the ACT reached the wire by another path. Candidates to settle from
the arbiter-probed capture: `r_rfc_cnt` across the REF (did it load, with
what), `r_grant` on the REF's fire, `refresh_req_o` / drain / pull-in credit
around it, and whether the ACT is the main lane's `r_do_act`. The host prints
tRFC=7 per config and writes it through the shadowed `TIMINGS_RFC_REFI`
word; a readback of that CSR on the board after a failing run is the cheap
cross-check.

## Workaround

pumice_core / pumice_top / pumice_top_geared default `FAST_RD_RELEASE = 0`
(2026-11-04, `2ad7f65d8`). Granite keeps it (`GRANITE_FAST_RD_RELEASE`).

2026-11-04, later: the option is now a runtime bit, `SCHED_POLICY.fast_rd_release`
(bit 13, resets 0). `FAST_RD_RELEASE` goes back to 1 in the pumice tops and only
builds the path; `mc_scheduler_plane.fast_rd_en_i` gates the entry and clears
fast mode when low, so with the bit at its reset the stream is the
uniform-delay stream. Granite ties the enable high; scoria and andesite tie it
low (they do not build the path). One bitstream now A/Bs the bug: host
`TEST_FAST_RD=1` sets the bit; sim `PUMICE_FAST_RD=1` drives it in the core
suite. The off case on a bit-gated bitstream still needs a board soak to
confirm it matches the 0/8 of the parameter-off build.

## Board soak on the bit-gated bitstream (2026-11-04)

`ef4e36f1e` at 50 MHz (WNS +0.020, 0 failing), `windows` x `--txn-scale 4000`,
reprogrammed before every run so each starts at the reset value, bit off and bit
on interleaved, 8 each:

| bit | runs with NOT OK | read latency mean / min (cyc), row_thrash |
|-----|------------------|-------------------------------------------|
| 0   | 0 / 8            | 62.56 / 41 (= the parameter-off build)     |
| 1   | 0 / 8            | 56.56 / 35 (= the always-on build)         |

The bit works: on, the latency matches the always-on build to the cycle. Yet
bit on did not reproduce the corruption, where the always-on builds failed 5 of
14 runs (P(0/8) at 1/3 per run is ~4 %).

The difference between the two: the init sequence (soft reset, controller cfg,
read-path leveling) never writes SCHED_POLICY, so here leveling ran with the
release OFF and the host turned it on afterwards. On the always-on builds
leveling ran with the release ON. Working hypothesis: the release is fine in
steady state, and what goes wrong is read-path leveling (bitslip/tap) taken
under the release -- a marginal eye that fails some runs later. Test: set the
bit before `init` (leveling under the release) and soak; expect the ~1/3 rate
back. Refuted the same day -- see below.

## Leveling hypothesis refuted (2026-11-04)

Same bitstream, same profile, reprogram per run, 8 cycles alternating. Host knob
`TEST_FAST_RD_EARLY=1` sets the bit in `SimpleTest.init` right after
`program_geometry`, before the leveling verify; `TEST_FAST_RD=1` alone sets it
later in `ControllerConfig.apply`.

| bit set               | runs with NOT OK | failing runs                                    |
|-----------------------|------------------|-------------------------------------------------|
| early (before level)  | 1 / 8            | c6: open random_bl8, close row_thrash + random   |
| late (after level)    | 2 / 8            | c1: same three; c5: open + close random_bl8      |

Both orders fail, so leveling under the release is not the trigger. Leveling
was never re-taken anyway: every run restored and verified the same
`level_cache.json` (bitslip 0, rd_tap 8, window [0,16], unchanged since 11-01,
checked byte-identical after the soak).

Totals for the bit on `ef4e36f1e`: 3 of 24 runs (0/8 + 1/8 + 2/8); bit off
0 of 8. The always-on builds ran ~1 in 3 (13/55). The lower rate here is not
significant on these counts. The bit is the variable and the earlier clean 0/8
was chance (P ~ 1/3 at 1/8 per run).

Signature unchanged: only random_bl8 (both page modes) and close-page
row_thrash_bl8, ~4,700-6,200 beats lost on random, 10-21k on row_thrash.
Mechanism still open. Next step stays the char-harness sim of random_bl8 with
`PUMICE_FAST_RD=1`, board config matched exactly.

### Trace of the free-running model at the PHY ports (2026-11-06, later)

`CHAR_DFI_TRACE=N` (new, `test_ddr2_char_char.py`) logs the PHY-side DFI
column commands, rddata_en, rddata_valid and rddata per cycle. Two traced
points, one injector, bit off, scale 1:

- `smoke/close_page/incremental`, L=8 V=11 (1 of 64 beats bad): RDs every 4
  cycles, rddata_en the cycle after each RD (the harness delays both by
  `cmd_delay`), rddata_valid at RD+12, the bus changing to the read's word on
  the same cycle. V=9 and V=10 were 64 of 64 bad, so the capture window is one
  cycle wide, not the hold-tolerant window the model's docstring describes.
- `windows/close_page/random`, L=8 V=10 (23 of 64 bad): the same RD-to-en
  spacing, valids at RD+11, and RD pairs one cycle apart across two banks
  (149916 bank 1, 149917 bank 0) each getting its own valid and word. The
  aligned V here is one less than for the incremental stream, and neither
  value is clean for both.

So the model-plus-harness has a scenario-dependent one-cycle offset between
the data landing and the valid, and the controller's capture tolerates none.
Candidates: the DRAM model's cycle base (the data is scheduled off
`dram.cycle` at command decode, the valid off the enable sample), the
harness `dfi_rddata_delay` (data delayed 2, valid not), or a half-cycle
drive/sample phase in the slave. The on-board a7ddrphy does not have this

### Capture 3: the mechanism (2026-11-06 evening, written up 2026-11-07)

The 30-run armed soak on build 3 (scratchpad `ila/cap7`, bit ON, `windows` at
scale 4000) triggered on run 3, which failed 3 of 9 scenarios (open_page/random_bl8
5,952 beats, close_page/mixed_bl8 15,328, close_page/random_bl8 4,716). The
capture, its decode and the run log are kept in
`vault/tracking/projects/components/mem-ctrl-ip/assets/bug033_ila/`
(`ila_fr1_r3.csv`, `ila_fr1_r3_decoded.txt`, `fr1_r3.log`). The decoded DFI
boundary around the trigger (samples are controller cycles at 50 MHz, two DFI
phases each; the trigger is the reader's `rd_dbg_valid & rd_dbg_mismatch`):

```
 -24  REF
 -22  ACT  b7 row 0          <- two cycles after the REFRESH, tRFC = 7
 -21  RD   b7 col 050   -20  RD col 054   -19  RD col 058
 -13  RD   b7 col 05c        rddata = ffff_ffff_ffff_ffff
 -11  PRE  b7
  -9  ACT  b7 row 2
  -8  RD   b7 col 180 ... -4  RD col 190   rddata = 0000_0000_0000_0000
  -3  ACT  b3 row 5
   0  trigger
```

Every read in the 1,000 samples before the REFRESH returns its expected word
(the `DBG act == exp` pairs in the decode). The first command after it is an
ACTIVATE inside tRFC, and from there bank 7 reads all-ones then all-zeros until
the debug stream flags the mismatch. That is a DRAM-side timing violation, not a
marginal capture: the data pattern is the DRAM's, not a bit-flip's, and it
explains why the earlier eye-margin A/B showed nothing. The "build-dependent"
reading of the afternoon is withdrawn; the 15 / 15 clean runs were a small
sample of a one-in-several fault.

Working hypothesis: with the fast release a read's slot is freed early, and the
next command for that bank re-enters arbitration while the refresh is in flight,
missing the refresh hold the normal path honours. The DFI command path's own
comment says a hold at its head "compresses spacing exactly", so the fix belongs
upstream: in the scheduler plane's refresh gate against fast-released commands,
not in the DFI plane.

Lost with the host reboot at 20:02 and to be re-run: (a) the bit-OFF board
capture triggered on REF with reads in flight (`cap_ref.sh`), to show the normal
path holds the ACT for tRFC on the same build; (b) the two char-harness sim
DFI-trace histograms of REF-to-next-ACT gaps, `PUMICE_FAST_RD=0` vs `1`
(`CHAR_DFI_TRACE` now logs every command type for this). Then find the gate,
fix it, and re-soak interleaved (bit on vs off, same bitstream).

## Closed (2026-11-07)

Root cause: `mc_scheduler_plane` `g_cmd_delay` ORed the two release-token
sources (`r_tok_shift[CMD_DELAY-1]` and the fast push) into one, and `r_fast`
could set one cycle after a slow push that landed on the cycle `r_idle`
crossed `r_smax`, so a slow token was in flight under fast mode and matured
beside a fast push; the lost token left one orphan entry in the output FIFO
for the rest of the run. Fix `e91fb524e`: `w_tok_matured` counts both
sources, `r_fast` sets only on an idle cycle, and a sim-visible balance
counter (`r_tok_orphan_cycles`) reports entries != pending tokens.
