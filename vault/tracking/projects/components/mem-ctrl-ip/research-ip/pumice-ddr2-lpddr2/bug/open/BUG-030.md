# BUG-030: the page policy's idle-timeout close precharges rows that queued bursts still need (45% of streaming bandwidth from three threads up)

**Priority:** P1 -- every multi-thread streaming number on either core and
either backend was wrong by it; the reset default triggers it
**Status:** open (fix in review 2026-10-22: `mc_page_policy` open-row-demand veto)
**Owner:** TBD
**Found:** 2026-10-22, the three-way controller table (report
`reports/regr/mem-ctrl-recovery-phase3-2026-10-22.md` §5.1): FR-FCFS fell to a
pattern-independent 307 / 354 MB/s on every family from four threads per
direction up, while two threads ran at 556 / 558.

## Expected vs observed

Four writer generators one bank apart, each streaming its own row (row_major,
txn 256, 75 MHz board geometry), FR-FCFS core. Expected: page hits throughout,
~560 MB/s, a few dozen ACTs (refresh reopenings). Observed: 306.5 / 353.7
MB/s, 2 099 ACTs for 16 384 columns -- ONE ACT PER 8-COLUMN BURST, ACT cadence
15 cycles (the single-bank row-walk floor). Page stats: col_ops 8 192, miss
1 049, empty 3, acts 1 052, pres 1 056. Same shape at 8 threads, on every
address family, on granite (entry store) and pumice (CAMs) alike.

## Root cause, established

`mc_page_policy` (common-ip) runs the fixed_open idle timer with no view of
the scheduling window: a bank whose row has seen no COMMAND for `tr_init`
cycles is expired, and the arbiter serves the resulting PRE as its
lowest-priority pick, in any free slot. The CSR reset is policy_mode 3 /
tr_init 2 (set 2026-09-26 as "the measured optimum", on single-thread row
walks). With four threads interleaving, every bank is idle for three bursts
between visits, every bank is expired almost always, and the first free slot
closes a row whose next burst is already queued; the ACT round trips create
more free slots and the thrash sustains itself. The DFI trace shows every
bank on row 0 throughout, each PRE in the slot between two bursts 16 cycles
after that bank's last column, and the next ACT reopening the same row.

Proof: the same run with the timeout disabled through its own register
(`PAGE_TIMEOUT_CFG.tr_init = 0`): 554.2 / 553.3 MB/s, 128 ACTs.

Why it hid: BANK_PICK leaves no free slot while streaming (the PRE never
issues; yesterday's four-generator loss on BANK_PICK was this policy taking
the stale-pick slot); two FR-FCFS threads happen to fill every slot; the
telemetry classified these closes as CONFLICT misses (`w_pre_was_timeout`
read `r_expired` after the row image had already cleared it), which pointed
at the row-hit logic; and the perf proxy's `TEST_PAGE_POLICY` knob wrote the
legacy `REFRESH_TUNING.page_policy_or`, not `PAGE_POLICY_CFG.policy_mode`, so
two "static_open was identical" experiments never turned the timeout off.

## Fix

- `mc_scheduler_plane`: per-bank `w_open_row_demand` -- a queued column
  wants the bank's OPEN row -- from the records' head hit (BANK_PICK) or a
  compare of the flat vectors against the registered row image (FR-FCFS).
- `mc_page_policy`: `open_row_demand_i` re-warms the idle timer (a row with a
  burst waiting for it is not idle) and vetoes the close request live.
  Telemetry: a close counts as timeout if the bank was expired within the
  last two cycles.
- Proxy: `TEST_PAGE_MODE` / `TEST_TR_INIT` reach the engine; `PERF_HOST_DIAG`
  records stall and page stats on every phase; `DFI_CMD_TRACE` forwarded.

The reset default stays tr_init 2: at one thread it is worth 308 / 350 vs
238 / 260 on col_ilv (bank-interleaved row walks, where the next access to a
bank is a different row and the veto does not apply) and nothing on
col_major. Whether that default is right is the owner's call; the veto makes
it safe under streaming either way.

## What the veto does and does not do (measured)

The matrix re-run with the veto in place is bit-for-bit the pre-veto one on
both cores: FR-FCFS still 306 / 353 at four threads. The veto is blind here:
with four or more generators sharing a 16-entry window, a bank's next burst
is usually NOT admitted yet when its last column fires, so there is no
queued demand for the policy to see and the 2-cycle timer wins. The veto
stays (correct, free, and it covers the case where demand IS visible); the
lever that works is the timer value. FR-FCFS sweep, txn 256:

| tr_init | 4 thr row_major | 4 thr col_ilv | 1 thr col_ilv | 1 thr col_major |
|---|---|---|---|---|
| 2 (reset) | 307 / 353 | 307 / 353 | 308 / 350 | 195 / 194 |
| 0 (off) | 554 / 553 | - | 238 / 260 | 195 / 194 |
| 32 | 554 / 557 | 460 / 488 | 306 / 349 | 195 / 194 |
| 128 | 554 / 557 | 459 / 488 | 247 / 261 | 195 / 194 |

The early close earns its keep only on single-thread bank-interleaved row
walks (col_ilv), where a bank is revisited with a NEW row every ~120 cycles;
it costs 45% on any stream whose bank revisit interval (threads x burst)
exceeds tr_init. Eight threads close the door on a fixed value: tr_init 32
and 64 both still read 307 / 352 at eight threads (ACTs 8 396 and 6 767;
the eight-bank revisit interval is ~70 cycles), while 128 keeps streaming
and loses col_ilv (247 / 261). No single tr_init serves every thread count.

## The fix that holds at every thread count: a per-bank mistake predictor

`mc_page_policy` keeps one bit per bank: a TIMEOUT close whose row the very
next ACT to that bank reopens was a mistake (the row was not idle, the
stream had not reached the bank again yet); the bank is marked keep-open and
the idle timer stops naming it until a CONFLICT precharge (a real row
change) clears the mark. A stream pays one reopen per bank and then runs
open; a row walk never trips it, because its reopens are different rows.
Needs no window visibility and no tr_init tuning; tr_init keeps its
single-thread meaning. The open-row-demand veto stays beside it.

It did nothing at first, and the reason is the third defect in this bug:
the policy consumed the plane's command-FIFO READ side (`cmd_valid_o &&
cmd_ready_i`) while the bank image it compares against updates when a core
FIRES into that FIFO. Each command reached the policy an arbitrary number of
cycles later, after the row image had dropped and the expired flag was
cleared -- so every timeout close classified as a conflict (the telemetry
defect above, which a two-cycle shadow could not reach), the idle timer
re-warmed late, and the predictor's "that PRE was a timeout close" never
armed. The policy now consumes the fire side (`a_cmd_valid && a_cmd_ready`,
`a_cmd_op / bank / row`). With that, FR-FCFS at four threads: row_major
540.3 / 550.7 (was 306.5 / 353.0; timer-off ceiling 554 / 553), col_ilv
419.5 / 441.4 (was 307 / 353); ACTs 821 for 65 536 columns; page stats
read empty 71 / miss 21 on the write phase (were miss 1 049 / empty 3).
One thread: col_ilv 306 / 350 (benefit intact), col_major 212.6 / 211.5
(was 195 / 194: the timer now closes row-walk rows at fire time).

A fourth defect showed in the full-family run: one-thread col_ilv read
254 / 298 when it followed the streaming families (306 / 350 when run
first). After a stream every bank is expired AND marked keep-open; col_ilv's
first precharge on each bank is a demand conflict, but the policy inferred
"timeout close" from its own expired flag, which is true for both, so the
mark was never cleared and the early close was lost for the whole family.
The inference is gone: both cores export the branch they fired on
(`cmd_timeout_pre_o`, fire-side: the arbiter registers `w_do_to_pre` beside
`r_do_pre`, BANK_PICK's is `w_to_fire`), the plane carries it as
`a_cmd_to_pre`, and the policy classifies on `pre_is_timeout_i`. The two
other instantiators of the arbiter (scoria, andesite wrappers) and the
contract TB connect the new output explicitly. The reset value is a declared shipping value in
`dv/csr_reset_parity.py` (tr_init 2 = TASK-013's single-thread board
optimum), so moving it is the owner's decision; the same `pumice_csr`
regblock feeds granite's policy engine.

## Timing

The first board build of the fix missed the 75 MHz floor: `w_sys_i` -0.277
ns, 15 of 86 116 endpoints, all in the FR-FCFS arbiter's pick-to-output
cone (2.7 ns logic, 10.9 ns route). The policy's close request had grown
two live terms -- the open-row-demand vector (on FR-FCFS, 2 x NUM_ENTRIES
row compares OR-reduced per bank) and the keep-open mark -- and that request
feeds the arbiter's pick comb through its timeout branch. The demand vector
is now REGISTERED in the plane before it reaches the policy (a one-cycle-old
veto is fine for an idle timer); the keep-open mark was already a register.
The build on that text is the gate below.
