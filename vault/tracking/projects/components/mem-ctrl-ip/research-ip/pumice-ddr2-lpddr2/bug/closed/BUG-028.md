# BUG-028: FRFCFS refresh drain deadlocks behind a demand-PRE pre-pick to the same bank (col_major writer wedges at board timings)

**Priority:** P1
**Status:** closed (2026-10-21, fix verified: perf proxy col_major clean at txn 64/256/1024, pumice run-all-func 216/1 at both geometries)
**Owner:** TBD
**Filed:** 2026-10-21 (mem-ctrl recovery plan Phase 0, first run of the new pumice-CAM perf proxy)
**Repro:** `cd projects/fpga-systems/NexysA7/mem-ctrl-ip-ddr2/ddr2_char_framework/dv/tests && TEST_FAMILIES=col_major TEST_TREFI=585 TEST_TXN=64 python -m pytest test_ddr2_char_perf.py -v -s` (after `source env_python`). Writer never completes; 16 ACT / 15 PRE / 126 WR fired, then nothing.

## Symptom

pumice with its CAM storage plane, board geometry (rate-2 / 32b beat / x16 /
BL4) and board-derived JEDEC timings at 75 MHz, tREFI=585: the col_major
write phase (same-bank row walk, 8 columns per row) deadlocks at the first
refresh request that lands while a row is open with a row-miss entry behind
it. incremental, row_major and col_ilv complete clean in the same run.

Stall snapshot (perf proxy `rtl_snapshot`, txn 64 and 256 identical):

| signal | value | meaning |
|---|---|---|
| `sched.refresh_req` / `refresh_drain` | 1 / 1 | REFab requested, drain wanted |
| `arb.r_bank_row_active` / `r_bank_pre_ready` | 0x1 / 0x1 | bank 0 open and precharge-ready |
| `arb.w_any_active` | 1 | so the refresh branch wants a drain PRE |
| `arb.w_rfsh_pre_found` | 0 | none found |
| `arb.w_guarded` | 0x1 | bank 0 guarded |
| `arb.r_guard0` / `r_guard1` / `w_inflight_preact` / `r_pick_valid` | 0 / 0 / 0 / 0 | nothing fired, nothing in flight |
| `arb.w_ref_col_block` | 0xff | demand columns blocked for the episode (correct) |
| `store.wr_sch_valid` | 0xff | CAM full of schedulable writes |

## Mechanism

`w_guarded` (`mc_cmd_arbiter.sv`, the full-signal guard the refresh/timeout
cone uses) includes `w_prepick_guard`, the pre-pick-register shadow of ACT
and PRE candidates. With `CLOSE_ON_DRAIN=0` (pumice default since
a8331c9d6, 2026-10-20) a row-miss write behind an open row is a demand PRE
candidate every cycle, so `wr_pre_f`/`wr_pre_bank=0` is reloaded into the
pre-pick register each cycle and `w_guarded[0]` is held at 1. When a refresh
is requested:

1. The refresh branch is above every demand class in the pick chain. It
   wants a drain PRE on bank 0 but `w_rfsh_pre_found` requires
   `!w_guarded[0]`, so it finds nothing and produces `w_valid=0`.
2. Because the branch is taken (`refresh_req_i || refresh_drain_i`), the
   chain never reaches the demand PRE class that would have closed the row.
3. Nothing is ever loaded into the output register. Deadlock.

`CLOSE_ON_DRAIN=1` (granite, and pumice before 2026-10-20) hid it: the last
column was an RDA/WRA, so no demand-PRE candidate existed when the refresh
arrived and `w_any_active` fell on its own. The pumice func suite was green at
a8331c9d6 because no cell drives a refresh into a same-bank row walk at
board timings; the 2026-10-03 board A/B predates the CLOSE_ON_DRAIN flip.

## Fix

`mc_cmd_arbiter.sv`: a drain-specific guard `w_guarded_drain` = `w_guarded`
minus the demand-PRE shadow terms (keeps `r_guard0/1`, the ACT shadows, the
column in-flight guards and the output-register terms). The refresh/ZQ drain
picker uses it. A drain PRE and a pending demand PRE to the same bank are the
same command: once the drain PRE fires, `r_guard0` masks the bank and the row
image drops, so the demand candidate dies in the mask before any demand class
can run again. Shared module: granite builds inherit the change (its drain
path is unchanged in behaviour because its demand-PRE candidates are rare).
