# BUG-033: pumice reads return wrong data with FAST_RD_RELEASE on -- windows random_bl8, ~1 run in 3 at 50 MHz

**Priority:** P1 -- silent data corruption on the board's shipping point.
**Status:** active 2026-11-07 -- MECHANISM CAUGHT on the board ILA 2026-11-06: an
ACTIVATE two controller cycles after a REFRESH (tRFC programmed 7) with the
fast-release bit on, and the reads behind it return 0 / all-ones. Fix not yet
made; the runtime bit's reset-off default stays the workaround.
**Owner:** TBD
**Filed:** 2026-11-04 (found under pumice TASK-047's board run, 2026-11-03)
**Repro:** Nexys A7, `build-perf`, `PUMICE_SYS_50=1`, HEAD text (`FAST_RD_RELEASE = 1`,
on since `bfc3cbf7a` 2026-10-31), host `PUMICE_MC_CLK_HZ=50000000`,
`make run SEQUENCES="init char" RUN_ARGS="--profile windows --txn-scale 4000"`.
About one run in three: `open_page/random_bl8` NOT OK ~5,900-6,200 beats and
`close_page/random_bl8` NOT OK ~4,700 beats (occasionally `close_page/mixed_bl8`
8,258 or `close_page/row_thrash_bl8` 10,661). Bandwidth is unchanged; only data
is wrong. Expected: 0 mismatched, as on the 2026-10-27 bitstream.

## Measured (interleaved programs, windows only, 2026-11-03/04)

| bitstream | FAST_RD_RELEASE | runs | failed |
|---|---|---|---|
| 2026-10-27 shipped (pre-`bfc3cbf7a`) | 0 | 8 | 0 |
| HEAD text, scratch tree with the default set to 0 in pumice_core / pumice_top / pumice_top_geared | 0 | 8 | 0 |
| HEAD text as committed, lane-off build | 1 | 8 | 3 |
| all HEAD builds over the day (lane build lane off / on, lane-off build) | 1 | 55 | 13 |

Same profile, same host, same board, alternated program by program. The
TASK-047 row lane is not involved (its lane-off build fails at the same rate).
The `FAST_RD_RELEASE=0` HEAD build closes 50 MHz at +0.020 ns.

## What the option does

`mc_scheduler_plane` delays every command CMD_DELAY cycles so a WRITE's data
reaches the DFI first. With FAST_RD_RELEASE, `r_fast` is set after the command
line has been empty for CMD_DELAY + the largest programmed timing; while set,
commands bypass the delay; a WR push clears it and takes the full delay.
Granite has run it at 75 / 100 MHz on every profile with 0 mismatches
(`ff8c64d18`), so the failure needs pumice's path (FR-FCFS arbiter + CAMs) or its
50 MHz board point.

## Not yet known

The mechanism. On paper the release keeps the pick's spacing (it engages only on
an idle line, and the first WR leaves it). The proxy that validated it uses an
MC-anchored DRAM model with zero violations; it never ran `random_bl8` with the
data checker on the board harness. Next: the char-harness sim of `windows`
`random_bl8` with the option on and off at board geometry, and a DFI-level
trace of the first fast command after idle against the DRAM model.

## Workaround

pumice_core / pumice_top / pumice_top_geared default `FAST_RD_RELEASE = 0`
(2026-11-04, `2ad7f65d8`). Granite keeps it (`GRANITE_FAST_RD_RELEASE`).

2026-11-04, later: the option is now a runtime bit, `SCHED_POLICY.fast_rd_release`
(bit 13, resets 0). `FAST_RD_RELEASE` goes back to 1 in the pumice tops and only
builds the path; `mc_scheduler_plane.fast_rd_en_i` gates the entry and clears
fast mode when low, so with the bit at its reset the stream is the
uniform-delay stream. Granite ties the enable high; scoria and andesite tie it
low (they do not build the path). One bitstream now A/Bs the bug: host
`TEST_FAST_RD=1` sets the bit; sim `PUMICE_FAST_RD=1` drives it in the core
suite. The off case on a bit-gated bitstream still needs a board soak to
confirm it matches the 0/8 of the parameter-off build.

## Board soak on the bit-gated bitstream (2026-11-04)

`ef4e36f1e` at 50 MHz (WNS +0.020, 0 failing), `windows` x `--txn-scale 4000`,
reprogrammed before every run so each starts at the reset value, bit off and bit
on interleaved, 8 each:

| bit | runs with NOT OK | read latency mean / min (cyc), row_thrash |
|-----|------------------|-------------------------------------------|
| 0   | 0 / 8            | 62.56 / 41 (= the parameter-off build)     |
| 1   | 0 / 8            | 56.56 / 35 (= the always-on build)         |

The bit works: on, the latency matches the always-on build to the cycle. Yet
bit on did not reproduce the corruption, where the always-on builds failed 5 of
14 runs (P(0/8) at 1/3 per run is ~4 %).

The difference between the two: the init sequence (soft reset, controller cfg,
read-path leveling) never writes SCHED_POLICY, so here leveling ran with the
release OFF and the host turned it on afterwards. On the always-on builds
leveling ran with the release ON. Working hypothesis: the release is fine in
steady state, and what goes wrong is read-path leveling (bitslip/tap) taken
under the release -- a marginal eye that fails some runs later. Test: set the
bit before `init` (leveling under the release) and soak; expect the ~1/3 rate
back. Refuted the same day -- see below.

## Leveling hypothesis refuted (2026-11-04)

Same bitstream, same profile, reprogram per run, 8 cycles alternating. Host knob
`TEST_FAST_RD_EARLY=1` sets the bit in `SimpleTest.init` right after
`program_geometry`, before the leveling verify; `TEST_FAST_RD=1` alone sets it
later in `ControllerConfig.apply`.

| bit set               | runs with NOT OK | failing runs                                    |
|-----------------------|------------------|-------------------------------------------------|
| early (before level)  | 1 / 8            | c6: open random_bl8, close row_thrash + random   |
| late (after level)    | 2 / 8            | c1: same three; c5: open + close random_bl8      |

Both orders fail, so leveling under the release is not the trigger. Leveling
was never re-taken anyway: every run restored and verified the same
`level_cache.json` (bitslip 0, rd_tap 8, window [0,16], unchanged since 11-01,
checked byte-identical after the soak).

Totals for the bit on `ef4e36f1e`: 3 of 24 runs (0/8 + 1/8 + 2/8); bit off
0 of 8. The always-on builds ran ~1 in 3 (13/55). The lower rate here is not
significant on these counts. The bit is the variable and the earlier clean 0/8
was chance (P ~ 1/3 at 1/8 per run).

Signature unchanged: only random_bl8 (both page modes) and close-page
row_thrash_bl8, ~4,700-6,200 beats lost on random, 10-21k on row_thrash.
Mechanism still open. Next step stays the char-harness sim of random_bl8 with
`PUMICE_FAST_RD=1`, board config matched exactly.

## Sim repro, step 2: the a7ddrphy free-running model at the board tuple (2026-11-06)

The gated-loopback sim did not fail at scale 1, 64 or 4000 with the bit on, so
the board-specific read path is being modelled instead: `CHAR_A7_FREE=L,V,W`
in `test_ddr2_char_char.py` swaps in `DFITimingProfile.a7ddrphy_free_running`
(data anchored to the RD command at L, valid = rddata_en + V, write latency W)
under the board tuple (`TEST_T_RDDATA_EN=1 TEST_RDDATA_DELAY=2
TEST_T_PHY_WRLAT=1 TEST_CMD_DELAY=1`, 50 MHz). Two traps cost a day:

- The char runner levels before measuring (`run_matrix(do_leveling=True)` ->
  `ensure_leveled(hard=True)`), and in sim the IDELAY/bitslip strobes are
  no-ops, so the 256-point eye sweep re-tests ONE alignment 256 times and
  raises "no (bitslip, tap) eye" whenever that alignment is wrong. Every
  (L, V) failed that way twice over (W=0 then W=1). `CHAR_NO_LEVEL=1` now skips
  the sweep (`run_profile(do_leveling=...)` threaded through); the families'
  mismatch counts are the calibration measurement.
- Only V - L matters for one read; the first sweep (L = V+1..V+4) was in the
  wrong band.

Bit OFF, scale 1, `close_page/random_bl8`, L = 8, W = 1 (W = 0 identical):

| V | 4..8 | 9 | 10 | 11 | 12 | 13 | 14 | 16 |
|---|---|---|---|---|---|---|---|---|
| beats mismatched (of 64) | 64 | 55 | **12** | 48 | 48 | 49 | 53 | 59 |

No point reads clean. The minimum at V - L = 2 still leaves 12 of 64 beats
wrong, which is the "consecutive-read one-slot shift" the model was written to
reproduce (its docstring), i.e. at the board tuple pumice's rddata_en cadence
on back-to-back BL4 reads does not match this model's command-anchored data,
while the board itself reads clean with the bit off. So the model as
parameterised is not the board's PHY at this tuple, and a bit-on/bit-off
comparison on it would not be meaningful yet.

Next: one scale-1 run at L=8/V=10 with waves, and compare the first
mismatched read's RD command, rddata_en, model data and valid against the
board ILA capture of the same tuple (bring-up notes), to see which of the
model's assumptions (data hold, valid reference, the harness
`dfi_rddata_delay` placement) is off. Scripts and logs: session scratchpad
`b033/cal3.sh`, `b033/cal4/`, `b033/cal5/`.

### Trace of the free-running model at the PHY ports (2026-11-06, later)

`CHAR_DFI_TRACE=N` (new, `test_ddr2_char_char.py`) logs the PHY-side DFI
column commands, rddata_en, rddata_valid and rddata per cycle. Two traced
points, one injector, bit off, scale 1:

- `smoke/close_page/incremental`, L=8 V=11 (1 of 64 beats bad): RDs every 4
  cycles, rddata_en the cycle after each RD (the harness delays both by
  `cmd_delay`), rddata_valid at RD+12, the bus changing to the read's word on
  the same cycle. V=9 and V=10 were 64 of 64 bad, so the capture window is one
  cycle wide, not the hold-tolerant window the model's docstring describes.
- `windows/close_page/random`, L=8 V=10 (23 of 64 bad): the same RD-to-en
  spacing, valids at RD+11, and RD pairs one cycle apart across two banks
  (149916 bank 1, 149917 bank 0) each getting its own valid and word. The
  aligned V here is one less than for the incremental stream, and neither
  value is clean for both.

So the model-plus-harness has a scenario-dependent one-cycle offset between
the data landing and the valid, and the controller's capture tolerates none.
Candidates: the DRAM model's cycle base (the data is scheduled off
`dram.cycle` at command decode, the valid off the enable sample), the
harness `dfi_rddata_delay` (data delayed 2, valid not), or a half-cycle
drive/sample phase in the slave. The on-board a7ddrphy does not have this
property (bit off reads clean at the same tuple), so until the model
reproduces a clean bit-off read at one (L, V) for every family, a bit-on vs
bit-off comparison on it cannot be read.

Knobs added for this work (all default-off): `CHAR_NO_LEVEL=1`,
`CHAR_DFI_TRACE=N`, `CHAR_A7_FREE=L,V,W`, `CHAR_BUILD_TAG`, `CHAR_TXN_SCALE`,
`TEST_FAST_RD`, and `run_profile(do_leveling=...)` in `pumice_char.py`.

## Board ILA (2026-11-06, owner's call: board route over finishing the model)

Plan: `PUMICE_SYS_50=1 PUMICE_RD_DBG_FIFO=32 make bitstream-ila`, program once,
level over UART, arm the ILA on the reader's own `rd_dbg_valid &
rd_dbg_mismatch` (trigger mid-buffer, so the preceding commands are in the
window) with the fast-release bit ON, run `windows` at `--txn-scale 4000` until
the corruption fires, decode the DFI boundary around it. `capture_ila.tcl`
gained `CAP_NO_PROGRAM=1` (arm without reprogramming the levelled board) and
`CAP_TIMEOUT`; `build_ila.tcl` gained `ILA_EXTRA_NETS` (probe nets by name on
the synthesised netlist, used for the scheduler's token shift) and `ILA_DEPTH`.
Scripts: session scratchpad `ila/cap_loop.sh`, `ila/host_runs.sh`,
`ila/decode_ila.py`.

- The `mism` trigger alone fires on an idle bus: `rd_dbg_mismatch` is
  `actual != expected`, a level; it must be ANDed with `rd_dbg_valid`
  (fixed in the tcl).
- ILA build 1 (37 probes incl. 372 stray scheduler nets from a loose
  `*r_idle*` glob, depth 4096, WNS +0.004 ns) does not level: the first init
  found an eye but failed the centred verify, every later sweep found no
  (bitslip, tap) at all. The board is healthy: the soak bitstream
  (`frrcsr_ef4e36f1e.bit`) reprogrammed right after levels clean (bitslip 0,
  tap 8, eye 0..16). Build 2 (DFI boundary + debug stream + `r_tok_shift`
  only, depth 2048, WNS +0.203) levelled the same way: eye found, centred
  verify failed.
- Root cause of both, found from capture 1: the harness ORs the debug stream's
  mismatch FIELD into the sticky `rd_error` unqualified
  (`ddr2_char_harness.sv`: `w_rd_error = w_gen_any_error | w_rd_dbg_mismatch`).
  The field is a FIFO payload, a level that reads 1 on an idle bus, so on every
  `PUMICE_RD_DBG_FIFO` build `rd_error` latches by itself, the leveling
  `_test`'s write-wait bails on `any_error`, and the sweep reports "no eye"
  with a perfectly good read path. Fixed: qualified with `w_rd_dbg_valid`.
  Build 3 with the fix is building; the ILA bitstreams were never the problem.

### Board ILA results, build 3 (2026-11-06 afternoon)

Build 3 (harness fix, 19 probes, depth 2048, WNS +0.495 ns) levels clean and the
mismatch trigger works: it fired once, on a levelling-verify read, with ONE bit
wrong (bit 60 = DQ12 of the upper lane) on `w_dfi_rddata` itself, i.e. a
marginal DQ capture at the cached tap with the bit OFF. That is also why every
host run spends ~5 min in init: the restore verify at the cached tap fails and
the sweep re-runs.

With the ILA armed only after each run's levelling (`ila/cap_loop2.sh`):
**15 of 15 fast-release runs clean, no capture** (4 at scale 4000, 11 at scale
16000; the `windows` char step is cycle-bounded and runs 45 s whatever the
scale). The soak on the plain HEAD builds failed 3/24 and 13/55 under the same
host program, and the 10-27 shipped build 0/8. So the failure is
BUILD-DEPENDENT: it follows the placement, not the RTL feature alone.

Eye margin A/B (`host_eye_margin_ab.py --points 1:2 6:7`, bit off vs
`TEST_FAST_RD_EARLY=1`): identical, 31 taps wide at both tuples, both states.
At 50 MHz the whole IDELAY range sits inside the eye, so the tap sweep cannot
resolve margin here; the earlier cached window (0..16) was a different day.

Reading: a logic bug in the fast release would not be build-dependent; a path
whose margin depends on placement would. Candidates are the a7ddrphy read
capture (DQ12 already shows single-bit errors at the levelled tap) or an
unconstrained/blank domain path (the `w_sys2x*`/`w_idelay` intra-clock rows are
EMPTY in every build's timing summary, ILA or not), with the fast-released
first-read-after-idle cadence as the trigger that makes a marginal capture fail
on the builds where it is marginal. Next: (1) a 30-run armed soak on build 3 is
running (`ila/cap7`); (2) explain the blank sys2x/idelay timing rows (the PHY's
capture domain may be untimed); (3) if build 3 never fails, insert the ILA into
a FAILING build's routed checkpoint incrementally (keep its placement) instead
of re-placing with the ILA.
- (2) resolved, benign: in `a7ddrphy_generated.v` the OSERDES/ISERDES take
  `sys2x_clk` / `sys2x_dqs_clk` on their CLK pins and `sys_clk` on CLKDIV; every
  register is on `sys_clk`, so the `w_sys2x*` / `w_idelay` intra-clock rows are
  empty because those domains hold no register-to-register paths. The DQ capture
  margin is the IDELAY/bitslip-levelled analog path, which STA never sees.
- (3) in progress: a plain `PUMICE_SYS_50=1 PUMICE_RD_DBG_FIFO=32` build is
  running to get a routed checkpoint of a non-ILA placement; soak it with the
  bit on, and if it fails, insert the ILA into THAT checkpoint incrementally.

### Capture 3: the mechanism (2026-11-06 evening, written up 2026-11-07)

The 30-run armed soak on build 3 (scratchpad `ila/cap7`, bit ON, `windows` at
scale 4000) triggered on run 3, which failed 3 of 9 scenarios (open_page/random_bl8
5,952 beats, close_page/mixed_bl8 15,328, close_page/random_bl8 4,716). The
capture, its decode and the run log are kept in
`vault/tracking/projects/components/mem-ctrl-ip/assets/bug033_ila/`
(`ila_fr1_r3.csv`, `ila_fr1_r3_decoded.txt`, `fr1_r3.log`). The decoded DFI
boundary around the trigger (samples are controller cycles at 50 MHz, two DFI
phases each; the trigger is the reader's `rd_dbg_valid & rd_dbg_mismatch`):

```
 -24  REF
 -22  ACT  b7 row 0          <- two cycles after the REFRESH, tRFC = 7
 -21  RD   b7 col 050   -20  RD col 054   -19  RD col 058
 -13  RD   b7 col 05c        rddata = ffff_ffff_ffff_ffff
 -11  PRE  b7
  -9  ACT  b7 row 2
  -8  RD   b7 col 180 ... -4  RD col 190   rddata = 0000_0000_0000_0000
  -3  ACT  b3 row 5
   0  trigger
```

Every read in the 1,000 samples before the REFRESH returns its expected word
(the `DBG act == exp` pairs in the decode). The first command after it is an
ACTIVATE inside tRFC, and from there bank 7 reads all-ones then all-zeros until
the debug stream flags the mismatch. That is a DRAM-side timing violation, not a
marginal capture: the data pattern is the DRAM's, not a bit-flip's, and it
explains why the earlier eye-margin A/B showed nothing. The "build-dependent"
reading of the afternoon is withdrawn; the 15 / 15 clean runs were a small
sample of a one-in-several fault.

Working hypothesis: with the fast release a read's slot is freed early, and the
next command for that bank re-enters arbitration while the refresh is in flight,
missing the refresh hold the normal path honours. The DFI command path's own
comment says a hold at its head "compresses spacing exactly", so the fix belongs
upstream: in the scheduler plane's refresh gate against fast-released commands,
not in the DFI plane.

Lost with the host reboot at 20:02 and to be re-run: (a) the bit-OFF board
capture triggered on REF with reads in flight (`cap_ref.sh`), to show the normal
path holds the ACT for tRFC on the same build; (b) the two char-harness sim
DFI-trace histograms of REF-to-next-ACT gaps, `PUMICE_FAST_RD=0` vs `1`
(`CHAR_DFI_TRACE` now logs every command type for this). Then find the gate,
fix it, and re-soak interleaved (bit on vs off, same bitstream).
