# BUG-033: pumice reads return wrong data with FAST_RD_RELEASE on -- windows random_bl8, ~1 run in 3 at 50 MHz

**Priority:** P1 -- silent data corruption on the board's shipping point.
**Status:** active 2026-11-04 -- cause isolated to `FAST_RD_RELEASE` on the board;
mechanism not yet found; pumice default turned off as the workaround.
**Owner:** TBD
**Filed:** 2026-11-04 (found under pumice TASK-047's board run, 2026-11-03)
**Repro:** Nexys A7, `build-perf`, `PUMICE_SYS_50=1`, HEAD text (`FAST_RD_RELEASE = 1`,
on since `bfc3cbf7a` 2026-10-31), host `PUMICE_MC_CLK_HZ=50000000`,
`make run SEQUENCES="init char" RUN_ARGS="--profile windows --txn-scale 4000"`.
About one run in three: `open_page/random_bl8` NOT OK ~5,900-6,200 beats and
`close_page/random_bl8` NOT OK ~4,700 beats (occasionally `close_page/mixed_bl8`
8,258 or `close_page/row_thrash_bl8` 10,661). Bandwidth is unchanged; only data
is wrong. Expected: 0 mismatched, as on the 2026-10-27 bitstream.

## Measured (interleaved programs, windows only, 2026-11-03/04)

| bitstream | FAST_RD_RELEASE | runs | failed |
|---|---|---|---|
| 2026-10-27 shipped (pre-`bfc3cbf7a`) | 0 | 8 | 0 |
| HEAD text, scratch tree with the default set to 0 in pumice_core / pumice_top / pumice_top_geared | 0 | 8 | 0 |
| HEAD text as committed, lane-off build | 1 | 8 | 3 |
| all HEAD builds over the day (lane build lane off / on, lane-off build) | 1 | 55 | 13 |

Same profile, same host, same board, alternated program by program. The
TASK-047 row lane is not involved (its lane-off build fails at the same rate).
The `FAST_RD_RELEASE=0` HEAD build closes 50 MHz at +0.020 ns.

## What the option does

`mc_scheduler_plane` delays every command CMD_DELAY cycles so a WRITE's data
reaches the DFI first. With FAST_RD_RELEASE, `r_fast` is set after the command
line has been empty for CMD_DELAY + the largest programmed timing; while set,
commands bypass the delay; a WR push clears it and takes the full delay.
Granite has run it at 75 / 100 MHz on every profile with 0 mismatches
(`ff8c64d18`), so the failure needs pumice's path (FR-FCFS arbiter + CAMs) or its
50 MHz board point.

## Not yet known

The mechanism. On paper the release keeps the pick's spacing (it engages only on
an idle line, and the first WR leaves it). The proxy that validated it uses an
MC-anchored DRAM model with zero violations; it never ran `random_bl8` with the
data checker on the board harness. Next: the char-harness sim of `windows`
`random_bl8` with the option on and off at board geometry, and a DFI-level
trace of the first fast command after idle against the DRAM model.

## Workaround

pumice_core / pumice_top / pumice_top_geared default `FAST_RD_RELEASE = 0`
(2026-11-04). Granite keeps it (`GRANITE_FAST_RD_RELEASE`).
