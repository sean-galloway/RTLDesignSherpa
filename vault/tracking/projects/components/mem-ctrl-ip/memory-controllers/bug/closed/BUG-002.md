# BUG-002: mc_dfi_cdc crosses the write-staged token and its data on separate synchronizers

> Source: found reading `mc_dfi_cdc` during memory-controllers ISSUE-001, 2026-11-05.
> Verified against the source. Not reachable on either board (both tie `dfi_clk`
> to the controller clock with `DFI_CDC_EN = 0`), so there is no board or sim
> reproduction yet; it needs a true two-clock build.

**Priority:** P2 -- latent until a two-clock DFI build exists; when it does, it
is a write-data timing corruption the comment says cannot happen.
**Status:** closed 2026-11-07 -- fixed 2026-11-06 (staged token launched one cycle after the burst's last word; granite derives `DFI_WD_FIFO_EFF`), regression-clean (see Closed).
**Owner:** TBD
**Where:** `projects/components/mem-ctrl-ip/common-ip/rtl/fub/mc_dfi_cdc.sv:105-188`
(`g_async` branch), consumer `mc_dfi_wr_serializer.sv:85-99`.

## Observed

The port comment (`:105-112`) says the staged token is "pushed ... through the
same N_FLOP_CROSS synchronizer as the data pointer, so never visible on dfi_clk
before the data is". The code has two `gaxi_fifo_async` instances, `u_wd_fifo`
(`:155-171`) and `u_wtok_fifo` (`:174-188`), each with its own Gray write
pointer and its own 2-flop synchronizer. They are written in the same ctl
cycle (`wd_ready_o` requires both to have room, `:150-152`), but two
independent synchronizers resolving the same edge may settle one destination
cycle apart. So `pwr_staged_valid_o` can assert a dfi_clk cycle before
`pwd_valid_o`.

When it does: `mc_dfi_cmd_path` accepts the WR on the token, `wr_fire` arms the
serializer's maturity pipe at `t_phy_wrlat`, and `w_drive = owed && wd_valid_i`
(`mc_dfi_wr_serializer.sv:98`) waits one extra cycle for the data. `dfi_wrdata`
then lands one DFI cycle after the slot `t_phy_wrlat` promised the PHY. At the
board value `t_phy_wrlat = 1` that is a corrupted write.

## Expected

The DFI write data must appear exactly `t_phy_wrlat` cycles after the WR
command. A token that gates command issue must never be observable before the
data it stands for.

## Fix shape

Delete `u_wtok_fifo`. The data word already carries `last` as its MSB
(`mc_dfi_2p1_plane.sv:260`); count complete bursts on the dfi side from the
single data FIFO's popped `last` bits, and present that count as
`pwr_staged_valid_o`. One crossing, one ordering. The synchronous branch
(`:271-367`) already has this property because it is one clock.

Also fix the comment, which is the reason this was not caught: it describes
a single synchronizer that does not exist.

## Related

cdc BUG-004: the synchronizer these FIFOs use (`glitch_free_n_dff_arn`) has no
`ASYNC_REG` attribute, so Vivado's CDC report cannot classify these crossings
either way.

## Fix (2026-11-06)

`mc_dfi_cdc` (async branch) launches the staged token one ctl cycle AFTER the
burst's last data word (`r_wtok_push`), so two independent synchronizers each
with their +-1 cycle of settling can no longer let the token lead. The token
FIFO is 2 x WD_DEPTH so the delayed push always finds room (tokens in flight
never exceed the bursts in the data FIFO plus one) and `wd_ready_o` keeps its
shape. The port comment that claimed one shared synchronizer is corrected.

Cost: the token follows its last word by one more cycle, so the write-data
FIFO needs one more word of headroom in two-clock builds. Measured on
granite_core (DFI_CDC_EN=1, dfi_clk = 2 x aclk, a 24-write stream across all
banks): with the 16-deep write-data FIFO the FIFO settles at its full depth
and a WRITE sat at the DFI head for its data 4 cycles (0 with the token pushed
immediately, 0 on the same-clock path); at depth 32, 0. Raising CMD_DELAY by
one did NOT help (still 4): at the full-depth equilibrium the drain's last word
lands only as the serializer pops, whatever the lead. granite_core therefore
derives `DFI_WD_FIFO_EFF` for CDC builds: at least `CMD_DELAY_EFF + 1 +
BURST_WORDS` words, rounded to a power of two (16 -> 32 at the test geometry).
pumice_core already uses 32. The boards tie `dfi_clk` to the controller clock
and are unaffected.

## Closed (2026-11-07)

The two-clock granite_core cell (DFI_CDC_EN=1, dfi_clk = 2 x aclk) shows 0 held
WRITEs at the derived FIFO depth (4 at the old depth 16). Regression on the full tree (2026-11-06, every suite from `make clean-all`, the
MC-004 / MC-005 array moves included): common-ip fub 47 / 47 and macro 36 / 36
+ 3 declared xfail (the store-arbiter contract cells, chopped bursts included);
granite top 30 / 30 + 1 declared xfail; pumice `run-all-func-both` 224 + 224
(default and board geometry); char harness 226 + 2 xfail; val/amba 1437;
val/cdc 131.
Neither board exercises the async branch (`dfi_clk` tied to the controller
clock), so there is no board gate for this one.
