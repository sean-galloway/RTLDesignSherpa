## What this IS

Granite's scheduler core — the one the owner designed the SKU around:
per-bank in-order request queues (independent per-bank head sequencers) with
a cross-bank arbitration mux, no CAM, no FR-FCFS reordering within a bank.
Behavior reference: LiteDRAM's per-bank in-order machines (its col_major
edge comes from the next row's ACT already being queued per bank).

The shared FR-FCFS 5-stage pick core that granite v1 speaks today is the
RESEARCH core (pumice's). Granite v1 used it as a reuse shortcut — that is
the root of "why isn't granite in order", not a missing feature.

## Required uarch (the difference from the mask)

Per-bank head SEQUENCERS — small independent FSMs, one per (direction,
bank) — each tracking its own head entry (ACT -> columns -> AP on drain),
whose per-cycle "head ready + op" outputs feed a cross-bank priority mux and
the existing fire-stage JEDEC authority (bank/global timers, tFAW/tRRD
holds, refresh/ZQ/init override). No shared 5-stage class pipeline in the
per-bank path, so single-bank throughput is tCCD-bound, not pipe-depth-bound.

## Design points (settle in implementation)

- Per-bank queue depth: 2 (total 16 at 8 banks) as the v1; the A7 granite
  macro already runs NUM_ENTRIES=16.
- Storage seam: the granite entry store (already BRAM-backed, FIFO
  allocation) either gains per-bank allocation or presents a per-bank
  head view; storage-backend co-verification rule applies (AGENTS.md).
- Write drain ordering: commits are per-bank in-order; the wr data drain
  FIFO ordering must follow commit order exactly (the 5d4a9704a
  write-reorder lesson).
- Interaction with `CLOSE_ON_DRAIN`: per-bank queue-empty behind the head
  replaces the youngest-same-row heuristic (strictly simpler and exact).
