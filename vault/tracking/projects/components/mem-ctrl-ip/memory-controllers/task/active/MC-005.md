# MC-005: storage arrays out of ALWAYS_FF_RST into reset-free always_ff (ISSUE-001 row 2b)

> Source: memory-controllers ISSUE-001 (the FPGA microarchitecture review,
> 2026-11-05), resolution table row 2b. Owner 2026-11-06: "start with 2b and 1,
> file the tasks first." Scope: `common-ip` RTL first (both controllers build

**Priority:** P2 -- the one habit that keeps the whole design out of the

reset-free flops outside the FIFO memories.
**Status:** active 2026-11-06 -- phases 1 and 2 done, measured and regression-clean (below); routed same-tree A/B 2026-11-07 pumice -2,198 LUT / -737 FF, granite -2,042 LUT / -579 FF (below); committed dc4eb6b47; phase 3 (bridge generator) open.
**Owner:** TBD

## Why

Vivado will not infer distributed or block RAM from an array written in a
process that has an asynchronous reset branch, whatever that branch does to the
array. The repo macro `ALWAYS_FF_RST` is unconditionally async-assert
(`rtl/amba/includes/reset_defs.svh:55-64`), so every array written inside it
dissolves into flops plus a read mux. The 10-27 synth logs name 35 (pumice) and
30 (granite) arrays blocked with the one message `[Synth 8-4767] ... RAM is
sensitive to asynchronous reset signal`. The handbook already records the rule
and two earlier instances (`vault/handbook/design/sram-and-memories.md`: the
char histogram and the pumice BRAM CAM).

## Method (per array, mechanical)

1. The array gets its own `always_ff @(posedge clk)` with no reset and no clear
   term, gated only by the write condition that already exists.
2. The valid / occupancy / pointer state that says which entries are live stays
   in the `ALWAYS_FF_RST` block, unchanged.
3. Every read of the array must be qualified by that live state before it can
   reach a port or a decision. Verilator is 2-state and will NOT show an
   unwritten entry as X ([[reference_verilator_5020_regblock_struct_bug]] is a
   different trap, same lesson: the simulator hides it), so this is checked by
   reading, not by running.
4. The signal keeps its `r_` prefix (it is still a flop,
   [[signal-prefixes]]).

## Done 2026-11-06: phases 1 and 2

**What moved.** Every array the census found written at ONE site, under a dynamic
slot index, with no reset-loop write -- 31 in `common-ip` plus the ring's skid
and the harness queue -- now has its own `always_ff @(posedge aclk)` carrying
the identical write condition and index. Nothing else changed: the valid /
pointer / count state that makes an entry readable stays in the `ALWAYS_FF_RST`
block, every reader was already qualified by it, and the arrays were never in
a reset branch to begin with. Simulation cannot distinguish the two forms
(Verilator lint warning census identical to HEAD for all four files).
