# MC-012: bring in Ramulator 2 and explore modelling the mem-ctrl-ip controllers with it

> Owner, 2026-11-10: "Add a task for mem-ctrl-ip to download ramulator2, and
> let's explore modeling with it."

**Priority:** P3 -- exploration; nothing on the board depends on it.
**Status:** CLOSED 2026-11-11 -- Ramulator 2 pinned and built from `references/ramulator2/fetch.sh`; DDR2 / DDR2_BL8 device classes checked constraint by constraint against JESD79-2F (14 device-timing tests, 1 smoke); the board's char families replayed through the model and placed beside the measured granite / LiteDRAM cells; the exploration questions have first answers (below); policy work filed as MC-013; the JEDEC table error filed as BUG-003.
**Owner:** TBD

## Why

Every performance number the family has is measured: cocotb characterization
of pumice / granite, LiteDRAM on the same harness, and the board. There is no
cycle-level model to ask "what would an ideal FR-FCFS / open-page controller
do on this trace", to separate the scheduler's share of a gap from the DRAM's,
or to try a policy (read/write turnaround, refresh placement, bank-group
awareness for DDR4 / LPDDR4 in diorite / andesite) before it is RTL. Ramulator
2 (CMU-SAFARI, C++20, YAML-configured, per-device timing classes, plug-in
scheduler / refresh / address-mapper) is the standard academic model for
exactly that.

## What

1. **Download.** Clone `https://github.com/CMU-SAFARI/ramulator2` into
   `vendor/ramulator2` (the `vendor/` tree is gitignored: third-party sources
   are fetched, never committed -- the LiteDRAM reference and the pulp / verilog-axi
   fabrics live the same way). Record the pinned commit and a fetch + build
   recipe in `projects/components/mem-ctrl-ip/references/ramulator2/` (a
   `fetch.sh`, the configs we write, and the notes), beside the paper archive.
2. **Build and run the stock examples** (CMake, g++ 13 is on the machine).
3. **Device coverage.** Ramulator 2 ships DDR3 / DDR4 / DDR5 / LPDDR5 / HBM2 /
   HBM3 / GDDR6 device specs. It has NO DDR2 and NO LPDDR2 -- granite's and
   pumice's parts. The first modelling question is therefore what a DDR2 spec
   costs: a device class with DDR2 timings (tRCD / tRP / tRAS / tRC / tRRD /
   tFAW / tWTR / tRTW / tCCD / tWR / tRFC / tREFI as our CSRs carry them, BL4 /
   BL8, x16, 8 banks, no bank groups) derived from the DDR3 class, or a DDR3
   spec with the DDR2 numbers pasted in (the command set is the same; the
   differences that matter here are timings and the BL4 option).
4. **A granite-shaped configuration.** Nexys A7 part (MT47H64M16: 64M x 16,
   8 banks, 8K rows, 1K columns), CK 150 / 200 MHz (= sys 75 / 100 MHz with
   the 1:2 DFI ratio), one channel, one rank, FR-FCFS, open page, the refresh
   interval the board uses. Drive it with traces that match the char host
   program's patterns (`ddr2_char.py`: row-major / column-major sweeps, the
   mixed read / write ratios, the threaded half-pairs) so the model's
   throughput can sit beside the measured granite SKU and LiteDRAM columns of
   `ddr2-characterization/char_results/compare_granite_sku100_vs_litedram_hx100_2026-11-09.md`.
5. **Exploration questions** (pick by what the first numbers say):
   - how far granite's measured bandwidth sits from the model's ideal on the
     same traces, per pattern -- the scheduler's share vs the DRAM's;
   - whether the model reproduces LiteDRAM's lead on the cells LiteDRAM wins;
   - the policies worth RTL: write-drain thresholds, read/write turnaround
     batching, refresh placement, per-bank vs pooled queues (the granite /
     pumice difference) as Ramulator scheduler plug-ins.
6. **Trace format.** Ramulator 2's trace frontends take `<addr> <R|W>` (and a
   timestamped variant); write a small exporter from the char host program's
   request stream, or from a cocotb monitor, so the SAME requests feed both.

## Results log

### 2026-11-10: first pass (clone, build, run, survey; nothing committed)

Full write-up with every command and file path: the session scratch note
`ramulator2/FINDINGS.md` (320 lines); the durable facts are here.

- **Upstream is Ramulator 2.1, not the 2.0 the task text assumed.** HEAD of
  `main` (pinned **7bead6cb7c4b03e095c6d4769ae3181a8e0bf6da**, 2026-11-04) is
  a restructure: device specs are Python DSL classes
  (`python/ramulator/dram/*.py`) that generate the C++ into
  `src/ramulator/dram/impl/` at build; configurations are Python scripts (YAML
  only as an export for C++ embedding); plug-in wrappers are generated. There
  is no `example_config/` and no `<addr> <R|W>` frontend.
- **Build:** `cmake .. -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++ &&
  make -j24` with g++ 13.3 / cmake 3.31.9 / python 3.12 (dev headers present):
  FetchContent pulled yaml-cpp 0.9.0, fmt 10.2.1, nanobind 2.4.0; 0 warnings.
  Side effect: the codegen target rewrites the 14 generated `.cpp` (formatting
  only, clang-format absent) -- the fetch recipe must `git checkout --
  src/ramulator/dram/impl` after a build, or install clang-format.
- **Run:** `PYTHONPATH=python python3 examples/example_config.py` matches the
  README (81,302 cycles, 45.2 avg latency, 6 reads, 3 hits / 3 misses);
  `pytest tests/smoke -q` 15 passed; DDR3 1Gb x16 @800, channel_width 16, on a
  4,095-line LoadStoreTrace: 1,570 of 1,600 MB/s, 4,000 row hits.
- **Devices shipped:** DDR3, DDR4 (+PUM, +VRR), DDR5 (+VRR), GDDR6, GDDR7,
  HBM1-4, LPDDR5, LPDDR6. **DDR2 and LPDDR2 absent.** DDR3 timing names: rate,
  nBL, nCL, nRCD, nRP, nRAS, nRC, nWR, nRTP, nCWL, nCCD, nRRD, nWTR, nFAW,
  nRFC, nREFI, nCS, tCK_ps (CK integers). A spec is: levels / commands /
  states, a `TimingConstraint(level, preceding, following, latency="expr",
  window, sibling)` list, `resolve_secondary_timings` (nRRD / nFAW from a
  (page, rate) table, nRFC from density, nREFI = 7.8 us / tCK), `org_presets`
  {density, dq, channel_width, rank, bank, row, column}, `timing_presets` per
  speed bin; any key overridable per instance. No tRTW parameter: RD->WR is
  `nCL + nBL + 2 - nCWL`, WR->RD is `nCWL + nBL + nWTR`, tFAW is `nFAW` with
  `window=4`. BL is `nBL` (BL/2 CK) PLUS a class attribute
  `internal_prefetch_size` that sets the transfer bytes -- BL4 vs BL8 is a
  class, not a parameter.
- **Plug-ins** (Python object; the YAML `impl` string is its name): controller
  GenericDDR (wr_low/high_watermark 0.2 / 0.8, read/write_buffer_size 32) plus
  LPDDR5/6, HBM, GDDR7, PUM, PRAC, BlockHammer; scheduler FRFCFS and
  FRFCFS-RowHit (a 40-line .cpp adds one); refresh AllBank (scatter_interval,
  scope), PerBank, NoRefresh; row_policy Open, ClosedCAP(cap); addr_mapper
  RoBaRaCoCh, ChRaBaRoCo, MOP4CLXOR, PassThrough, RIT; controller_plugins
  CommandCounter (CSV), CmdTraceRecorder, BinTraceRecorder. Trap: `all_bank.cpp`
  hard-codes the REFab scope by standard name, so a DDR2 class needs
  `AllBank(scope="Rank")`.
- **Trace frontends:** LoadStoreTrace `LD <addr>` / `ST <addr>` (one request
  per tick, cyclic); ReadWriteTrace `R <ch>,<rank>,<bank>,<row>,<col>` (no
  mapping); SimpleO3 `<bubble> <load> [<store>]`; LatencyThroughputTrace
  (synthetic); External. **No timestamped frontend**, and the run loop stops
  when the frontend has SENT its last line (2,021 of 2,047 served in the test
  run) -- a ~100-line `TimedLoadStoreTrace` (`<cycle> <LD|ST> <addr>`, drains
  completions; PUMTrace is the template) is the first thing to write. Clock
  ratio for granite: frontend 1, GenericDRAM 2.
- **Stats:** per channel cycles, row hits / misses / conflicts (read / write
  split), requests issued / served, queue lengths, avg read latency, read /
  write / total MB/s; per-command counts via CommandCounter.
  `tests/device_timings/harness.py::DeviceUnderTest` (`probe` / `issue` /
  `assert_earliest_ready_at`) checks a device class constraint by constraint.
- **DDR2 draft** (scratch `ramulator2/draft_ddr2/ddr2.py`, validated on the
  Python side for four class / preset points, C++ codegen not yet run): copy of
  `ddr3.py` with `internal_prefetch_size = 4`, `nBL = 2` (BL4) and a `DDR2_BL8`
  subclass (8 / 4); `nCWL = nCL - 1`; RD->PRE and RDA->ACT `nBL + nRTP - 2`;
  `nCCD = 2` with 2-CK floors on nRTP / nRRD / nWTR; tRFC 75 / 105 / 127.5 /
  195 / 327.5 ns by density; nRRD / nFAW primary in the preset; org
  `DDR2_1Gb_x16 = {1024, dq 16, channel_width 16, rank 1, bank 8, row 8192,
  column 1024}`; presets DDR2_300_CL3 (CK 150: nRCD / nRP 3, nRAS 7, nRC 9,
  nWR 3, nFAW 7, nRFC 20, nREFI 1169), DDR2_400_CL3 (CK 200: nRAS 9, nRC 12,
  nFAW 9, nRFC 26, nREFI 1560), DDR2_800_CL6 (rated). Numbers from the repo's
  `pumice_device.py::DDR2_MT47H64M16_NS`; **flag:** that table carries tRRD
  7.5 ns where JEDEC x16 says 10 ns -- check both against JESD79-2F
  (`/mnt/data/github/dfi-specs/ddr2-lpddr2/jedec/DDR2_JESD79-2F.pdf`, a
  sibling of the repo) before trusting either. Model-vs-RTL caveat: the model
  is CK-granular ceil, the RTL adds a 2-CK phase margin, so expect the model
  about 1 CK tighter per constraint.

**JEDEC check (JESD79-2F Tables 40-43, clause 3.9 / 3.9.1).** Every constraint
in `ddr2.py` names its clause. Findings against the repo's numbers:
- tRRD and tFAW are by PAGE SIZE: 1 KB 7.5 / 37.5 ns (35 at DDR2-800), 2 KB
  10 / 50 ns (45 at DDR2-800). The x16 part with 1K columns is a 2 KB page.
  The repo's `DDR2_MT47H64M16_NS` carries tRRD 7.5 ns (the 1 KB value): both
  values round to 2 CK at CK 150 / 200 MHz, so nothing moved on the board;
  one MC cycle short at the DDR2-800 span config. **memory-controllers
  BUG-003** (filed, not fixed here: the table is shared by the pumice DV
  matrix). tFAW 45 ns and tWTR 7.5 ns in that table are the part's rating-bin
  values and are right.
- tRPall = tRP + 1 tCK on an 8-bank device (Table 41 note 1): the rank-level
  PREab terms carry `nRP + 1`. RD->PRE is `BL/2 + max(tRTP, 2) - 2` (clause
  3.9.1), WL = CL - 1 (clause 3.9).
- Presets: JEDEC bins DDR2_400B / 533B / 667D / 800E (tRRD / tFAW resolved from
  the organization's page size) and the PART presets `DDR2_MT47H64M16_300_CL3`
  / `_400_CL3` / `_800_CL6` carrying the part's own ns limits (the board runs a
  DDR2-800 part below every bin). The board points resolve to the RTL
  derivation's CK counts (tRCD/tRP 3, tRAS 7/9, tRC 9/12, tFAW 7/9).

**First answers to the exploration questions.**
1. *Scheduler's share vs the DRAM's, per pattern.* On the row-hit streams
   granite is at the refresh-limited ceiling (within 1 %). On `col_major`
   (every burst a page miss in one bank) granite trails the CK-granular ideal
   by 1.07-1.15 MC cycles per burst on reads and ~1.6 on writes -- and the
   `open32_mc2` column, the same ideal controller with every constraint
   rounded up to 2 CK, reproduces granite's cells to within 2 MB/s (418/521 vs
   416/520). That gap is the MC-cycle granularity of the RTL's timers, i.e.
   the DRAM's share as the RTL can count it, not scheduling. `mixed` is the
   same story (327 vs 330).
2. *Where the scheduler's share is.* `col_major_interleaved`, `row_thrash` and
   `random` -- the bank-parallel miss patterns -- sit 12-21 % below the ideal
   and the 2 CK rounding explains none of it (mc2 still reads 780). Granite's
   gap there is ~1.1 MC cycle per burst at every burst length. The structural
   candidate is the command slot: the board build issues one DRAM command per
   MC cycle (`mc_dfi_cmd_path` legacy single-command path, `DUAL_ISSUE = 0` in
   every granite build), and at BL4 a column command every MC cycle is the
   whole data rate, so each ACT (and each PRE that is not an auto-precharge)
   costs one data slot. The ideal issues them in the other CK of the pair.
   The DUAL_ISSUE row lane that already exists for pumice (TASK-047) is
   exactly that second slot; the model puts its ceiling at +92 MB/s (bl8) to
   +165 MB/s (bl4) on the interleaved family, +93 on row_thrash, +110 on
   random -- to be confirmed on granite, not assumed.
3. *Does the model reproduce LiteDRAM's lead where it wins?* LiteDRAM wins no
   cell in the sku100 table (3 ties on row-hit streams, granite ahead on the
   rest), so there is nothing to reproduce; the model confirms LiteDRAM's
   row-hit cells are also at the refresh ceiling and its interleaved cells
   (241-500) are far below what the DRAM allows -- its per-bank FSM with
   round-robin, not the device.
4. *Policies worth RTL.* Dual issue first (above, cheapest to test: a build
   switch). Queue depth: the model's 8-deep queues (granite's seam depth) lose
   nothing on the one-injector families and 40 MB/s on `mixed` / `random`, so
   depth is not where the gap is. Close-page per column access (cap 1) costs
   the model 70 % on streams -- the board's close_page cells (80 / 89) are a
   further 3x below even that and are a board-side pathology outside this
   task. Write-drain thresholds, refresh placement and per-bank vs pooled
   queues are MC-013.

**Not modelled.** The half-burst families (read-combiner stress, sub-burst AXI
transactions). The host path (the model's read latency is command accept to
data return). The injector's exact LFSR (a maximal 16-bit stand-in with the
same region shape).
