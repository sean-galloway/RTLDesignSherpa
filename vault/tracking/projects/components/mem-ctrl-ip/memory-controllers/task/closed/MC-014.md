# MC-014: a row lane on granite's bank-pick core (dual issue for the product controller)

> Filed from MC-013 item 1 (2026-11-12): the single DRAM command per MC
> cycle is the measured ceiling on granite's bank-parallel miss families, and
> pumice's existing row lane recovers it on the same DFI command path.

**Priority:** P2 -- the largest single bandwidth item left on granite's sku100 cells.
**Status:** CLOSED 2026-11-12 -- built, proved, simulated and measured on the board at 100 MHz under the timing budget (five builds: the lane as first built missed by 1.7 ns, four register-only cuts and one liveness fix later it closes at +0.059 with the main pick as the critical path); board cells below and in `char_results/board_mc014_granite_row_lane_sku100_2026-11-12.md`
**Owner:** TBD

## Why

The sku100 board cells sit at 684-688 MB/s on `col_major_interleaved` and
`row_thrash` and 635 / 661 on `random`, against 780 for the ideal controller
(MC-012). The 2026-11-12 sim traced the gap on granite itself: the scheduler
plane fires in 97 % of MC cycles there and the ACT recurs every 9 cycles,
eight columns plus one ACT per burst through one command slot per cycle
(`char_results/sim_mc013_command_slot_dual_issue_2026-11-12.md`). A second,
row-only slot beside the column is what pumice TASK-047 built as `DUAL_ISSUE`
(`mc_cmd_arbiter` row2_* -> `mc_scheduler_plane` cmd2_* -> `mc_dfi_cmd_path`
`g_row2` on `row_phase`): on pumice at the same point it moves
`col_major_interleaved` reads 680 -> 767 and writes 613 -> 682, `row_thrash`
682 -> 769 / 615 -> 683, `random` 642 -> 703 / 578 -> 623, and leaves
`col_major` alone.

Granite cannot use that lane today: `granite_core` with the bank-FIFO store
(`STORE_BACKEND=1`) requires `SCHED_CORE = MC_SCHED_BANK_PICK`, and the plane
ties `a2_act / a2_pre` to 0 for that core. The plane and the DFI path are
already lane-capable; only the pick core lacks the second nomination.

## What

1. `mc_bank_pick`: beside the column winner, nominate one demand ACT or PRE
   for a *different* bank whose timers are ready (the per-bank head records
   already carry the row and the hit / miss / conflict state), on
   `row2_act_o / row2_pre_o / row2_bank_o / row2_row_o`, gated by
   `dual_issue_en_i`. The FR-FCFS core's rules apply unchanged: never the
   column's bank, tRRD / tFAW counted on the lane's ACT (the plane already
   feeds `evt2_act_i` to the rank timers), one row command per cycle.
2. `mc_scheduler_plane`: connect the BANK_PICK branch's `a2_*` to the new
   outputs instead of the constant 0; `DUAL_ISSUE` keeps the word format.
3. `granite_core` / `granite_top*`: a `DUAL_ISSUE` parameter through to the
   plane and the DFI plane, `dual_issue_en_i` from `SCHED_POLICY.dual_issue`
   (the CSR field exists in the shared regblock), `row_phase` = 1 as pumice.
4. Sim first: the granite perf proxy at the sku100 point with the lane on,
   `PERF_CMD_TRACE=1`, the four families above; expect `col_major_interleaved`
   and `row_thrash` within a few percent of 780 and occupancy well under 0.9.
   Then the board: sys100 build with the lane, timing (the pick's fire cone
   is the near-critical path at 100 MHz, MC-011), the char `every` + `windows`
   suites.

## Done when

The granite sku100 `col_major_interleaved`, `row_thrash` and `random` cells
are re-measured on the board with the lane on and the numbers sit in
`char_results` beside the 2026-11-09 ones, or the task records why the lane
does not fit the pick core's timing at 100 MHz.

## Results log

### 2026-11-12: built, sim at the sku100 point

Full table and recipe:
`ddr2-characterization/char_results/sim_mc014_granite_row_lane_2026-11-12.md`.

- `mc_bank_pick` `DUAL_ISSUE`: a second winner register, row commands only,
  picked from the same registered request set (a row request whose bank has
  no column request and is not the main winner's; ACT before PRE, age and
  rotor inside the class), fired beside a main COLUMN or an idle main lane on
  the live gate, held on a timer within the lookahead, released otherwise;
  its pair stale-masked for its life in the lane plus one cycle, its fire
  hinting the pair's next op when the main lane raised none. The main select
  treats "a row can ride" as "after a row command" (columns first). The
  plane's BANK_PICK branch connects `a2_*`; `granite_core` carries
  `DUAL_ISSUE`, the wider command word and pumice_core's effective-enable
  gate; `granite_top_geared` wires `SCHED_POLICY.dual_issue` and
  `DFI_PHASE.row_phase` (two new CSR fields, regblock regenerated); the three
  char-harness layers and the perf proxy take `TEST_DUAL`.
- Lane off is bit-identical: the formal `equiv` / `equiv_n4` lockstep proofs
  against the golden copy pass with the lane's code present; the new `dual`
  task proves the word invariants at `DUAL_ISSUE = 1`. Granite top, pumice

### 2026-11-12 (evening): the board half

Full account: `ddr2-characterization/char_results/board_mc014_granite_row_lane_sku100_2026-11-12.md`.

- `GRANITE_DUAL_ISSUE=1` (env -> define, `targets/granite` create_project.tcl
  and `granite_char_top.sv`) builds the lane into the sys100 SKU. The first
  build missed the 0.2 ns budget by 1.715 ns with 462 failing endpoints: the
  lane pick had been put in series with the main select (it excluded the
  main's fresh row pick from `w_sel_src`), and the lane fire sat on the
  plane's command-valid cone into the DFI path (the idle-slot fire). Four
  register-only cuts over three more builds -- no same-cycle exclusion, fire
  beside a main column only (the plane keeps the pick core's `a2_*` out of

  -0.105, and +0.059 ns with 0 failing endpoints, 36 345 LUT (+618); the
  worst path is now the main pick itself, the pre-lane critical path.
- One cut created a liveness hole the formal `dual` task cannot see: a held
  lane pair, stale-masked from the main select, had no way out when no
  column was available once the lane could fire only beside a column.

  correct. The hold mask now applies only while a column is pending
  somewhere; otherwise the main select takes the held pair itself. `mixed`
