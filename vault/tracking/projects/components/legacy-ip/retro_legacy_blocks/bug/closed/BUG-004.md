# BUG-004: PRD.md gives the subsystem base address as 0x4000_0000; the RTL uses 0xFEC00000

**Priority:** P2
**Status:** CLOSED 2026-09-29 -- fixed, and the bug UNDERSTATED its own scope;
see the Outcome.
**Owner:** done
**Filed:** 2026-09-28

`PRD.md` states the base address three times and is wrong every time:

- `:473` -- "Base address: `0x4000_0000` (1GB region in typical 32-bit system)"
- `:478` -- the address-map table row `0x4000_0000 - 0x4000_0FFF | HPET`
- `:514` -- "**Single APB slave port** at base address 0x4000_0000"

The RTL is `parameter logic [ADDR_WIDTH-1:0] BASE_ADDR = 32'hFEC00000`
(`rtl/rlb_top/rlb_top.sv:64`), and the module header says the same at `:14`
("Address Map (4KB windows from BASE_ADDR 0xFEC00000)"). 0xFEC00000 is the
conventional location for this class of block, and every window in the DV
suite is computed from it -- `rlb_top_tb.BASE_ADDR = 0xFEC00000`.

**This is not an internal contradiction.** `grep FEC00000 PRD.md` returns
NOTHING: the PRD never states the real base anywhere, so a reader has no way
to notice the disagreement from the document alone. The whole address-map
section is describing a layout the design does not have.

**Expected:** the PRD's base address and its address-map table agree with
`BASE_ADDR`, or state explicitly that the base is a parameter and give the
default.

**Repro:** `grep -n '0x4000_0000' PRD.md` against
`grep -n 'BASE_ADDR' rtl/rlb_top/rlb_top.sv`.

**Why it was not caught:** nothing checks a PRD's prose against RTL parameter
values. `check_doc_examples.py` validates PORT NAMES in examples, not
parameter VALUES in prose.

## Outcome (2026-09-29)

Fixed in two files, 17 edits. **This bug described a base-address typo; the
document was wrong about the address map in four distinct ways.**

**1. The base was wrong in ELEVEN places, not three.** The three cited
(`:473/:478/:514`, actually `475/480/516` -- the line numbers had drifted) plus
seven per-block `**Address:**` headers and the decoder snippet's
`localparam BASE_ADDR = 32'h4000_0000`. That last one is the spelling THIS
BUG'S OWN REPRO COMMAND could not match: `grep -n '0x4000_0000' PRD.md` misses
`32'h4000_0000`. A repro that cannot see part of the defect understates it.

**2. Three SHIPPED blocks were documented as reserved space.** The map gave
`0x4000_7000 - 0x4000_EFFF` as "*Reserved* 32KB / Future expansion", but GPIO
(window 7), UART 16550 (window 8) and the cascade SLAVE 8259 (window 9) all
live there. GPIO and UART additionally carried
`**Address:** TBD (not in primary ILB address map)`.

**3. A block that does not exist was documented at an impossible window.**
Section 3.12 "Interconnect ID / Version Registers" claimed `0x4000_F000`, and
the decoder snippet had `psel_id = (block_sel == 4'hF)`. The shipped decoder is
the generated `apbx_xbar_1to10` -- ten windows, `0x0000`-`0x9FFF`. Window `0xF`
is unreachable. The section is legitimately marked Planned, so it was kept, but
its address is now recorded as unallocated with the reason.

**4. Six sections claimed "Status: Planned" for blocks that ship and are
tested** -- 8259, PIT, GPIO, SMBus, PM/ACPI, IOAPIC -- while section 6.2 of the
SAME document lists every one of them as Implemented. Fixed from 6.2, which is
the in-document authority. SPI, I2C and Watchdog remain Planned with `TBD`
addresses, correctly: a blanket replace would have corrupted those three, and
an early attempt that would have done so was caught by an anchor-count guard.

**A second file was wrong the same way.**
`docs/RLB_FPGA_IMPLEMENTATION_GUIDE.md` carried its own "Example Address Map
for FPGA" at the `0x4000_0000` base -- and with the block ORDER scrambled (PIT
at window 1, RTC at 2, PIC at 3; the real order is PIC 1, PIT 2, RTC 3), and
window 9 labelled "(Reserved)" rather than the cascade slave. Rebased and
reordered. `docs/gpio_mas/ch05_registers/01_register_map.md` already had
`0xFEC00000` correct and was left alone.

**Authority.** Three independent sources agree and were used as ground truth:
`rlb_top.sv`'s header map, the generator invocation recorded at `rlb_top.sv:399`
(`num_slaves=10, base_addr=0xFEC00000`), and the TB's slave constants
(`SLAVE_HPET..SLAVE_PIC_SLAVE = 0..9`).

**The sweep was wider than these two files.** An initial version of this
Outcome claimed zero `0x4000_` occurrences remained under
`projects/components/retro_legacy_blocks/`. That was asserted from having fixed
the two files this bug named, NOT from a measurement, and it was wrong by 33
occurrences across six more files:

| File | Sites | Same structural errors? |
|---|---|---|
| `CLAUDE.md` | 18 | yes -- Interconnect at `0xF000` in a table AND a diagram |
| `README.md` | 9 | yes -- Interconnect at `0xF000` |
| `rtl/{ioapic,pic_8259,pit_8254,pm_acpi,rtc}/README.md` | 5 | base only |
| `docs/pit_8254_mas/ch03_interfaces/01_top_level.md` | 1 | a HYPOTHETICAL example base, not a claim about this design |

See the verification block at the end for the final measured state.

**Why it was not caught, unchanged from the original report and still true:**
nothing checks a PRD's prose against RTL parameter values. `check_doc_examples.py`
validates PORT NAMES in examples, not parameter VALUES in prose. That remains
unfiled -- it is a tooling gap, not an RLB one.
