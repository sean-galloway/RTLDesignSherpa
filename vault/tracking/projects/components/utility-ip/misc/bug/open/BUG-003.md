# BUG-003: monbus_tally_axil cfgw write ignores WSTRB — a 4-byte-strided high-half write clobbers the register

**Date:** 2026-10-27
**Priority:** P3
**Status:** open
**Owner:** TBD
**Where:** `projects/components/utility-ip/misc/rtl/monbus_tally_axil.sv` (the cfgw write wrapper around `tally_regs_top`)
**Found by:** amber-mesi-l1 BUG-003 root-cause, 2026-10-27

## What

The tally's config-write port is 64-bit; the wrapper feeds the generated
regblock `wdata[31:0]` with `wr_biten = {32{1'b1}}` and never looks at
WSTRB. A host that decomposes a 64-bit access into lo/hi 32-bit writes
hits the register twice: the +4 (high-half) write aliasing onto the same
register overwrites it with the low-half data and re-fires its swmod
actions. On the CAM registers that means CAM_KEY zeroed before every load
and CAM_LOAD re-fired with INDEX=0/VALID=0 (entry 0 invalidated) — the
mechanism behind amber BUG-003's empty tally CAM.

The block comment claims the 8-byte register spacing makes 4-byte-strided
accesses safe ("can never land on an empty high half"). That holds for
reads; for writes it does not.

## Expected

A partial (WSTRB-selected) write either updates only the selected half or
is rejected; a swmod action must not fire on a write whose strobe covers
none of the acting field's bytes.

## Reproduce

Program the tally CAM through the amber pair harness's 32-bit host bridge
with a lo/hi write64 decomposition and read the CAM back
(`amber-mesi-l1 BUG-003`'s closure has the probe evidence:
`r_valid = 0x7fe`, all keys 0 after 11 {CAM_KEY, CAM_LOAD} pairs).

## Notes

- Amber's DV works around it test-side (single 32-bit writes, the CAM
  registers are 32-bit). Stream's hosts write 32-bit at 8-byte stride and
  never hit the high half, so the wart is latent everywhere else.
- Fix options: honor WSTRB in the wrapper (partial-write semantics need
  care with swmod), or reject/mask addr[2]=1 writes and document
  "32-bit-aligned writes only".
