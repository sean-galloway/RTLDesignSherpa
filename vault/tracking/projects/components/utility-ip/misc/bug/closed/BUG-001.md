# BUG-001: error_injector CLUSTERS mismatch on seed 33472

**Priority:** P3
**Status:** CLOSED 2026-10-16 — mechanism named, fixed in RTL, verified at
gate (4/4 configs on the filing seed, 20-seed sweep), full (2 configs), and
func (3/4 configs; see ISSUE-001 for the fourth).
**Filed:** 2026-10-16

`dv/tests/test_error_injector.py::test_error_injector[8-2-15-4-gate]` failed
with SEED=33472: "CLUSTERS block 0 beat 0/1" got != expected, 2 mismatches of
4028 checks.

## Mechanism

The mode 4/5/6 cluster-table draw is serialized through an FSM (`r_draw_busy`,
~2*MAXB+2 cycles per walk). The block-start beat is held in stage B until the
walk completes, released by `w_draw_wait = w_app_mode && r_b_v && r_b_first
&& !r_draw_done`. Two facts collide:

1. Snapshots fire for **every** mode — `if (w_a_fire && r_first)` is not gated
   by `w_app_mode`, so non-app phases (NONE/COUNT/BURST/RATE/DEBUG) each leave
   a walk running into the following phase.
2. A block-start beat can be **accepted into empty stage A during a walk**
   (`w_a_ready = !r_a_v || ...` ignores `w_draw_hold` when A is empty).

When an app-mode block's first beat was accepted while a stale walk still ran
(seen in probes: CLUSTERS block 0 snapshot at `busy=1`), the stale walk's
end-of-walk pulse set `r_draw_done=1` for one cycle — before the pending
walk's start branch could clear it — and the held beat decided against the
**previous** table (`r_n_burst=0`, all lengths 0: no injections at all, raw
data out). The following beat decided mid-walk with a partial table. Beats
after the real walk completed matched, and later blocks snapshot at
`busy=0` and were correct — which is why a single seed, single block, two
beats. The RTL's own comment claimed the start branch's invalidation "keeps
done honest"; that invalidation only fires one cycle *after* `busy` clears,
leaving the one-cycle stale-done window.

## Fix

`error_injector.sv` `w_a_ready`: never accept a block-start beat while a walk
runs — `&& !(w_app_mode && r_draw_busy && r_first)`. Every snapshot then
lands at `draw_busy==0`, the mid-walk snapshot (and the stale-done race)
becomes unreachable, and the existing pending/start machinery handles the
rest. Steady state is unaffected: a block's own first beat already occupies A
for the whole walk, so the new term only bites in the race above. The
single-beat-block corner (N<=S) is also covered: the next block's first beat
now waits at the master instead of leapfrogging into A mid-walk.
