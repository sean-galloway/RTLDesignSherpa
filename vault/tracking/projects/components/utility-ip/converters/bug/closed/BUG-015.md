# BUG-015: axi4_to_apb4_convert misaddresses every beat after the first of a sub-word burst

**Date:** 2026-10-24
**Priority:** P1
**Severity:** HIGH
**Status:** CLOSED 2026-10-24 (fixed; verified in sim and on the board)
**Owner:** unassigned
**Found by:** the Genesys 2 bridge stress model's `bridge_bs_mixed_b` build, `narrow` and `chaos` profiles in the harness sim: `cpu.rd RD_DATA id=0x23 addr=0x40014164 exp=0xe47fc863 act=0xf47ed067` at the APB5 slave, and `S_WDATA` on writes
**Affects:** `axi4_to_apb4_convert`, so `axi4_to_apb4_shim`, `axi4_to_apb5_shim` and every bridge APB/APB5 slave port, whenever a burst narrower than the APB word starts at a non-zero word offset

## Summary

On the IDLE to READ/WRITE transition the converter loaded `r_apb_paddr` with
the start address ALREADY aligned down to the APB word, and `axi_gen_addr`
stepped every later beat from it by AxSIZE. The first beat's PADDR was right
(it was masked anyway), but each later beat was one beat behind. An 8-beat
halfword WRAP at 0x162 went out as PADDR 0x160, 0x160, 0x164, 0x164, 0x168,
0x168, 0x16c, 0x16c instead of 0x160, 0x164, 0x164, 0x168, 0x168, 0x16c,
0x16c, 0x160. Beat 1 (0x164) read the 0x160 word, and writes landed in the
previous word under that beat's strobes. Full-width bursts and single beats
were not affected, which is why it survived: the shim test never drove a
multi-beat narrow burst.

The failing read was traced in the waves. The returned word differs from the
expected one by exactly the stress hash of an address 4 bytes away. The APB
bus showed each word read twice and the slave answering correctly for every
PADDR.

## Fix

Seed `r_apb_paddr` with the true start address. PADDR was already masked to
the APB word at `w_apb_cmd_pkt_paddr`, so the bus never sees the low bits. With
an 8-bit APB the mask is zero, so that configuration is unchanged.

## Regression

`test_axi2apb4_shim.py::run_narrow_burst_test`: 5 directed sub-word bursts
(the 0x162 WRAP verbatim, plus INCR and WRAP at byte and halfword size) and 8
/ 32 / 96 random ones at gate / func / full. Each direction is checked against
full-word single beats. A narrow write read back by the same narrow burst
cannot see this bug, because both directions misaddress identically. RED on
the pre-fix RTL (the 0x162 case fails at beat 1, exactly as in the bridge),
GREEN after: 6/6 cells.

## Limit (stated, not fixed)

The scenario does not run on the ratio>1 cell (32-bit AXI, 8-bit APB). It
logs NOT RUN. On a ratio>1 converter a narrow beat is decomposed into
AXI2APBRATIO slices stepped by AxSIZE, and that path has never placed narrow
lanes. No instance in the tree builds a ratio>1 converter: every
`axi4_to_apb4/5_shim` instance is 32/32.

## Verified on the board

`build-mixb` rebuilt with the fix (routed WNS +0.346 ns): every profile x seeds 1-3, 20000 bursts per master direction, 30/30 PASS (`projects/fpga-systems/Genesys2/bridge-stress/reports/board/bridge_bs_mixed_b_20261024_051300.csv`). The pre-fix bitstream, same host, same day: 21/27, `narrow` and `chaos` 0/6 with RD_DATA at the cpu and S_WDATA at p4s / p5s, exactly as in sim (`..._20261024_045157.csv`).
