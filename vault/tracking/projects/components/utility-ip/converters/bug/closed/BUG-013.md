# BUG-013: axi4_to_axi3_wr deadlocks a slave that waits for WVALID before AWREADY

**Date:** 2026-10-20
**Priority:** P1
**Severity:** HIGH
**Status:** CLOSED 2026-10-20 (fixed; verified in sim and on the board)
**Owner:** unassigned
**Found by:** the Genesys 2 bridge stress model's mixed build (`build-xmix`), `w_first` profile on the board: every master's writes stopped within a few bursts; the AXI3 slave (mem1) took none
**Affects:** `axi4_to_axi3_wr` (and `axi4_to_axi3`), so every bridge AXI3 slave port

## Summary

An unchopped AW goes straight to the AXI3 port, and its W descriptor (WID,
beat count) was queued only at that port's AW handshake. WVALID needs the
descriptor, so a slave that waits for WVALID before it raises AWREADY (legal,
AXI A3.3.1) never sees either: the write -- and every later one -- hangs.
Bridge BUG-020's class, in a converter that fix did not touch (the stress
slaves' W_FIRST mode found it once an AXI3 slave was in a W_FIRST build).

## Reproduction

bridge-stress harness sim, `BS_PROFILES=w_first`, `bridge_bs_axi3`: before the
fix cpu.wr issued 8, completed 0, timed out; after, it passes.

## Fix

The direct AW's descriptor is queued when the AW is OFFERED (`aw_direct`), so
its W can go first; `r_dpush` marks it queued (once) and holds AWVALID up to
the handshake even if the descriptor queue fills. Converters func 184 passed,
1 xfail (pre-existing); build-xmix board every profile 30/30 including
`w_first`.
