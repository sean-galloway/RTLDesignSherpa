Teaching Notes

Hardware serial CRC vs software table CRC. A hardware serial CRC engine usually shifts in one bit per clock, LSB-first when REFIN=1. A software table-driven CRC usually works MSB-first. Both can produce the same final checksum for the same standard, but the internal register values look different along the way: the LSB-first path uses the bit-reversed polynomial as its effective tap mask and sees each byte reflected.

Why the same polynomial can look different. The polynomial in the parameter list is the non-reflected form (e.g. 0x04C11DB7 for CRC-32). When REFIN=1 the engine effectively uses 0xEDB88320, the bit-reversed polynomial. The two conventions meet at the end because REFOUT=1 mirrors the input reflection back out. Pick the convention your protocol specifies and keep all five parameters together.

Common agreement bugs.

  • Forgetting CRC_XOROUT: many standards use 0x00, but CRC-32 inverts the output with 0xFFFFFFFF.
  • Wrong CRC_INIT: CRC-16/CCITT-FALSE starts at 0xFFFF; ARC starts at 0x0000.
  • Byte order: the CRC is computed over the raw byte order on the wire, not the host endianness.
  • Reflected polynomial: use the standard non-reflected form for CRC_POLY; REFIN/REFOUT handle the reflection.

RTL mapping. This app uses the same five parameters as rtl/common/dataint_crc.sv: CRC_POLY maps to POLY, CRC_INIT to POLY_INIT, CRC_XOROUT to XOROUT, CRC_REFIN to REFIN, and CRC_REFOUT to REFOUT.
