# DFI v3.1 Master Interface, and the v2.1.1 Delta

## The revision decision

scoria targets **DFI v3.1** (decision D1). pumice's DFI layer was built to
v2.1.1, so this chapter is the delta between them, measured across the two
specifications: 126 distinct `dfi_*` signal names in v2.1.1, 151 in v3.1.

The decision was not obvious and the reasoning is on the record: v3.1's *gain*
for a DDR3/LPDDR3 controller is the leveling rework, the low-power split and
`dfi_init`. Everything else it adds is DDR4/LPDDR4. Building to v2.1.1 and
hand-adding write leveling would reuse pumice's layer more directly. v3.1 wins
because the per-CS leveling scheme is what the DDR4 controller will need too,
and paying for it once here is cheaper than paying twice.

## What does NOT change, and a diff that lies about it

**The datapath is inherited entirely.** One async-FIFO CDC, bubble-free, the
unit of transfer a DFI word, `DFI_RATE = 4`.

**Important.** A naive signal-name diff between the two specifications reports
`dfi_address_p2`, `dfi_cs_n_p3`, `dfi_bank_n_p2`, `dfi_odt_p3` and their siblings
as **removed in v3.1**. They are not removed. v2.1.1 enumerates phase variants
explicitly; v3.1 generalises the notation to `_pN` — `dfi_address_pN`,
`dfi_cs_n_pN`, `dfi_odt_pN`, `dfi_bank_pN` — and shows `_p0`/`_p1` only as
examples. The 1:4 frequency ratio remains a defined mode (v3.1 §3.2.4, §3.3.4).

pumice runs four phases. An implementer who trusted that diff would rewrite a
working, measured datapath for no reason, so the trap is recorded here rather
than left for them to fall into.

## What changes and matters

### Leveling: reworked outright

| v2.1.1 | v3.1 |
|---|---|
| `dfi_rdlvl_mode`, `dfi_rdlvl_load`, `dfi_rdlvl_delay*`, `dfi_rdlvl_gate_mode` | **removed** |
| `dfi_wrlvl_mode`, `dfi_wrlvl_load`, `dfi_wrlvl_delay*` | **removed** |
| `dfi_rdlvl_cs_n`, `dfi_wrlvl_cs_n` | **removed** |
| — | `dfi_phylvl_req_cs_n`, `dfi_phylvl_ack_cs_n` (request/ack, per chip select) |
| — | `dfi_phy_wrlvl_cs_n`, `dfi_phy_rdlvl_cs_n`, `dfi_phy_rdlvl_gate_cs_n` (which leveling) |
| — | `dfi_lvl_pattern`, `dfi_lvl_periodic` |

: Table 4.1: The leveling interface, v2.1.1 against v3.1

This is the change scoria cannot route around, because DDR3 adds write leveling.
`scoria_wrlvl_ifc` (Chapter 3.3) drives this interface, and because the search
is firmware-driven the block is an interface and a set of timing windows rather
than a state machine.

### Low power: one request becomes two, and nothing consumes either

`dfi_lp_req` splits into `dfi_lp_ctrl_req` and `dfi_lp_data_req`, letting the
command path and the data path be put to sleep independently.

**In practice, on this PHY family, the channel is unused.** `s7ddrphy`
implements no DFI low-power interface, and LiteDRAM's generated DDR3
controller drives none. Nor does it power down by DRAM command: measured in
the generated core, there is no self-refresh or power-down engine at all, and
CKE is a CSR bit software raises during init. scoria
exposes both requests for spec compliance and for a future PHY that consumes
them, with the specified behaviour that an unacknowledged request times out and
reports rather than blocking power-down. See Chapter 3.1.

### Initialization and errors

`dfi_init` appears, giving initialization its own interface — which pairs with
DDR3's `RESET#` pin. `dfi_parity_error` becomes `dfi_error` plus
`dfi_error_info`, a wider surface that mostly carries DDR4 CA-parity detail;
scoria uses the error indication and ignores the DDR4-specific encodings.

## What scoria does NOT implement

Named explicitly so their absence is a decision on the record:

| Group | Signals | Why not |
|---|---|---|
| DDR4 command encoding | `dfi_act_n*`, `dfi_bg*`, `dfi_cid*` | DDR3 has no dedicated ACT pin, no bank groups, no chip ID |
| CA parity, CRC, alert | `dfi_alert_n*`, `dfi_parity_in_p*` | DDR4-era |
| Data Bus Inversion | `dfi_rddata_dbi*` | DDR4/LPDDR4 |
| CA training | `dfi_calvl_*`, `dfi_ca_capture`, `dfi_phy_calvl_cs_n` | LPDDR4-era |

: Table 4.2: DFI v3.1 features deliberately unimplemented

That is the majority of v3.1's growth over v2.1.1. Targeting the newer revision
does not mean implementing all of it.
